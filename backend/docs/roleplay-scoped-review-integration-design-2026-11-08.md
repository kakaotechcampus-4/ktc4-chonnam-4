# 범위 고정 검수의 운영 평가 연결 설계

작성일: 2026-11-08\
상태: 승인 범위 구현·전체 오프라인 검증·실제 두 평가 완료. 통합 평가의 정상 수용은 0/2이며 문제는 미해결.

## 목표와 선택

분석 전용 elice-p1-scoped-review-01은 A의 타당한 사건 분석을 승인하고 B의 잘못된 감정 관찰만 거절했다.
요청별 관찰 키와 현재 목표·활동 목표·다음 전략의 구조 분리가 실제 두 사례에서 동작했다.
이 구조를 기존 운영의 독립 평가 1회 안에 연결한다. 정상 경로는 분석→생성→평가 3회다.

별도 분석 검수 호출을 추가하는 4회 경로는 이번에 도입하지 않는다.
호출을 분리하면 지연·토큰과 재시도 카운터·분석 검수 결과 재사용의 설계가 추가로 필요하다.
현재 근거는 새 분석 전용 구조의 단건 성공까지이며, 통합 평가 성공이나 호출 분리 필요성은 입증되지 않았다.

이번 구현은 후보 대사·후보 품질 검사·최종 판정과 함께 사용할 때의 검증을 포함한다.
통합 검수에서 같은 혼동이 재발할 수 있다는 한계를 결과에 명시한다.

## 변경할 내부 제공자 계약

| 대상 | 현재 | 변경 |
| --- | --- | --- |
| 제공자 출력 스키마 | evaluation-output/v3, 고정 스키마 | evaluation-output/v4, 요청별 스키마 |
| 안내자/캐릭터 평가 프롬프트 | 각각 v6 | 각각 v7 |
| 분석 입력 | analysis_result 하나 | 성공한 진단의 범위별 입력 구조 |
| 관찰 리뷰 | 일반 배열·모델이 참조 ID 생성 | 요청 키를 필수로 가진 객체·서버가 원본 참조로 복원 |
| 분석 논리 리뷰 | analysis_logic_review 하나 | current_goal_review와 interpretation_strategy_review 분리 |
| 활동 검수 | goal_observation_review 안의 activity_review | 최상위 activity_review |
| 분석 ID | goal_observation_review.analysis_id | 최상위 analysis_id |
| 내부 목표 검수 | evaluation-result/v2 | 유지 |
| 내부 EvaluationResult·공개 API·DB | 기존 형태 | 유지 |

checks 11개, decision, failure_codes, revision_instruction과 candidate_id는 기존 평가 책임을 유지한다.
다른 단계인 분석/생성의 프롬프트·출력 계약은 변경하지 않는다.
모델 라우팅·timeout·출력 토큰 상한도 바꾸지 않는다.

## 요청 구성과 동적 스키마

테스트용 ScopedAnalysisValidation에서 확인한 입력 변환·키 바인딩·스키마 조립·검증을 운영용 구성요소로 옮긴다.
운영 코드가 테스트 클래스나 build/eval 산출물에 의존하지 않도록 한다.
JSON 전체를 여러 번 읽는 진단용 왕복 검사는 테스트에서 수행하고, 운영에서는 같은 변환 규칙을 사용한다.

평가 요청은 기존 상태·승인 시나리오·발화·최근 대화·확정 관찰·지원 맥락을 유지하고 다음 분석 객체를 구성한다.

- observation_tasks: 이번 분석 관찰을 o0/o1 등 요청 내 식별 키에 연결한다.
- current_goal_assessment: 현재 질문 목표의 ID·설명·required_evidence·제안 learning_state.
- activity_assessment: 승인 활동 learning_goal·제안 activity_goal.decision·basis.
- interpretation_strategy: 발화 해석·격차·confidence·next_strategy·적용된 서버 지원 보정.
- candidate_response: 기존 후보 대사와 해당 필드. 새 범위별 분석 객체와 함께 독립 검수한다.

원본 analysis_result를 다시 중복 추가하지 않는다. 모델이 검수할 사실·이력은 임의로 생략하거나 새로 만들지 않는다.
분석 입력 변환 전후의 전체 필드 대응은 회귀 검사로 보장한다.
새 프롬프트의 후보 checks도 새 객체 경로를 참조하도록 갱신한다. 캐릭터·안내자·마스코트의 기존 역할 기준을 유지한다.

동적 스키마와 원본 참조 바인딩은 같은 준비된 요청에 묶는다.
제공자에 보내는 스키마와 수신 검증 스키마도 그 요청에서 동일해야 한다.
후보/분석 ID, 현재 목표 ID·학습 상태, 활동 판정은 해당 요청 값 하나만 enum으로 제한한다.
관찰 키 객체는 이번 키만 properties/required에 넣고 additionalProperties=false로 고정한다.
임의 키를 삭제하거나 비슷한 키로 추정 복원하지 않는다.
바인딩·원문·동적 스키마를 요청 밖 전역 캐시에 보관하지 않는다.

현재 관찰이 0개이면 정상 경로의 observation_reviews는 빈 객체 {}이며 새 관찰을 만들지 않는다.
기존처럼 검수할 제안이 없다는 뜻으로 관찰 승인 true를 구성하되 활동 달성으로 해석하지 않는다.
빈 객체 스키마와 다중 기준의 로컬 직렬화·검증도 검사한다.

## 서버 검증과 내부 결과

원본 관찰을 키로 복원한 뒤 기존 인용·분류/사유·참조 집합 검사를 유지한다.
현재 목표·활동·해석/전략은 성공한 범위별 검수 구조와 기존 검증 규칙을 사용한다.
현재/이전 관찰·도움 이력을 섞지 않고 ACHIEVED의 기존 참조·긍정 basis 조건과 저장 전 검사도 유지한다.

일반 경로의 전체 분석 승인은 다음과 같다.

```text
analysis_supported = observations_supported
                     AND current_goal_supported
                     AND activity_supported
                     AND interpretation_strategy_supported
```

모델에게 이 요약 Boolean을 다시 출력시키지 않는다.
내부 GoalObservationOutput.Review는 원본 분석 ID·계산한 관찰 승인·활동 승인으로 기존 v2 형태를 구성한다.
현재 목표와 해석/전략 승인은 전체 분석 게이트에 반영한다. 둘 중 하나라도 거절됐는데 내부 목표 검수만 보고 PASS하지 않는다.

전체 분석 거절이면 기존 UNSUPPORTED_CAUSE_ANALYSIS를 서버가 추가한다.
해석/전략 검수의 사유가 STATE_STRATEGY_MISMATCH면 기존 해당 코드도 추가한다.
이 두 코드는 계속 모델 failure_codes에서 제외한다. 후보·안전 코드의 허용 목록과 코드/check 일관성 검사는 유지한다.

- 분석 거절은 유효한 REANALYZE여야 하며 후보만 재생성하거나 PASS하지 않는다.
- 분석이 모두 승인되면 일반 경로의 REANALYZE는 모순으로 거절한다. 후보 문제면 유효한 재생성과 수정 지시를 요구한다.
- PASS는 네 분석 검수와 후보 checks가 모두 승인되고 기존 코드/안전 게이트를 통과해야 한다.
- 근거 없는 인용·키/참조 오류·모순은 INVALID_OUTPUT_FORMAT이다. 같은 분석·후보를 재평가한다.
- 정보 부족은 기존 INDETERMINATE_OUTPUT이다. 승인/학습 실패로 변환하지 않고 같은 후보를 재평가한다.
- 모델 decision이나 활동 판정을 임의로 고쳐 수용하지 않는다.

관찰 배열 내부의 명시적 거절/판단보류 혼합과 다른 검수의 정보 부족 처리 우선순위는 현재 v3 규칙을 유지한다.

## 안전·입력 확인 우선순위

유효한 SAFETY_ESCALATION/CONFIRM_INPUT은 학습 검수보다 우선한다.
동적 스키마에서 네 학습 검수 객체는 null도 허용한다. 일반 경로에서는 null을 허용하지 않는다.
안전/입력 확인 경로에서는 모두 null이어도 허용하고 내부 관찰·활동 승인은 false로 둔다.
검수가 객체로 제공됐다면 스키마 구조는 검증하되 학습 판단을 완료시키려고 재평가하지 않는다.
기본 스키마·요청 ID·허용 코드·필요한 실패 코드 등 기존 안전 분기 조건은 유지한다.
위험 입력이나 기술 실패를 목표 달성·관찰 성취로 저장하지 않는다.

## 재시도·관측·개인정보

오케스트레이터의 단계·분석/후보/평가 상한과 STT/TTS를 포함하는 공유 60초 예산을 바꾸지 않는다.
새 검수 루프나 SDK/Advisor 재시도를 추가하지 않는다. 같은 후보의 기술/출력 재평가는 기존 최대 3회다.
새 분석·후보에는 이전 요청의 바인딩이나 오류 피드백을 섞지 않는다.
동적 스키마를 재평가 때 사용할 경우에도 현재 요청의 분석·후보·키에 일치해야 한다.

키/대상 오류에 대한 고정 재평가 코드·한글 수정 조건을 추가하고, 기존 피드백의 폐기된 필드 경로를 갱신한다.
모델 원문·발화·자유 설명을 retry 지시로 복사하지 않는다.
상세 검수 설명·인용·새 키 매핑은 검증 중에만 쓰고 내부 결과 변환에서 버린다.
공개 DTO·DB·일반 로그·지표 태그에 원문/새 설명/개인 식별 값을 추가하지 않는다.
기존 사용량·프롬프트/스키마 버전·판단보류·실패/시간 측정은 유지한다.

## 과거 진단·테스트 보존

v1~v3 실제 결과·원본 프롬프트/스키마·고정 입력은 그대로 보존한다.
과거 진단 v1의 스키마 생성이 현재 운영 스키마를 선택하는 부분은 기록된 계약에 고정해 버전 의미가 바뀌지 않게 한다.
실제 과거 응답을 새 버전 정답 출력으로 바꾸지 않는다. 합성 제공자만 현재 계약에 맞게 갱신한다.
기존 ScopedAnalysisValidation의 검증 규칙은 운영 구성요소를 재사용하는 어댑터로 정리하되
이전 진단 명령을 자동 재실행하거나 기존 결과 폴더를 덮어쓰지 않는다.

## 구현·검증 범위

구현 대상은 평가 입력/DTO·요청별 스키마와 바인딩·검증/변환·평가 프롬프트·고정 오류 피드백·관련 합성 제공자/진단이다.
오케스트레이터·분석/생성 계약·완료 정책·프론트엔드·DB·배포·모델 교체는 범위 밖이다.
주석은 필요한 내용과 핵심만 한글로 작성한다.

관련 검사 뒤 전체 check를 한 번 수행한다. 새 실패나 새 코드 변경이 없으면 반복하지 않는다.
필수 사례는 다음과 같다.

- A 사건 승인·B 감정 거절, 현재 목표와 활동 목표의 구분, 올바른 내부 v2 변환.
- 0개 관찰, 여러 관찰/여러 기준, 같은 입력의 다중 목표, 기존 긍정 근거 사용.
- 다른 요청/후보/분석의 바인딩·ID·키·상태, 누락·추가 키·허구 인용 차단.
- 현재 목표/해석 검수만 거절된 경우도 재분석하며 PASS 차단.
- 정보 부족·계속된 의미 모순에서 같은 후보 재평가, 시도 상한·예산·피드백 초기화.
- 안전/입력 확인의 null 학습 검수 우선 처리와 오류 출력 무조건 수용 금지.
- 후보 checks·코드·수정 지시·캐릭터/마스코트·지원 정책·TTS/저장 게이트의 기존 경계 유지.
- 이전 보고서 읽기·진단 계약 보존, 인용·설명이 새 내부/공개 결과나 일반 로그에 남지 않음.

## 오프라인 검증 후 실제 통합 진단

같은 고정 A/B와 같은 후보, Elice gpt-5.4-nano를 사용해 운영 평가 v4를 각각 한 번 호출한다.
이번에는 후보 대사·11개 후보 checks·최종 decision도 함께 평가한다.
정상 역할극 전체를 실행하는 실험은 아니며 분석·생성·STT·TTS·저장은 호출하지 않는다.

최대 2회·공유 60초·SDK/진단 재시도 0회, 기존 timeout·출력 토큰 상한 유지다.
제공자·시간·JSON 스키마 실패면 중단한다. 의미/근거/판정 일관성 실패는 기록하고 예정된 다른 사례도 한 번만 수행한다.
실패를 수정하려고 운영 코드를 추가 변경하거나 호출을 늘리지 않는다.

- A: 네 분석 검수는 승인되는 것이 사전 기대값이다.
  최종 PASS를 강제하지 않는다. 후보 문제로 재생성을 택하면 실제 문제·check·코드·수정 지시의 타당성을 따로 검토한다.
- B: 사건 승인·감정 거절을 유지해야 한다. 나머지 세 분석 검수와 후보 품질 판단을 관찰 오류와 구분한다.
  전체 분석은 승인될 수 없으며 유효한 REANALYZE와 서버의 분석 실패 코드로 연결돼야 한다.
- 두 사례 모두 올바른 키 집합·출처·현재/전체 목표 판정과 전체 평가 수용을 각각 보고한다.

결과 폴더는 build/eval/elice-p1-scoped-integrated-01이다. 원본·바인딩·스키마·프롬프트·응답·시간/토큰·해시를 보존한다.
이전에 성공한 분석 전용 단건을 통합 평가 성공의 증거로 대신 사용하지 않는다.
실제 진단은 P1 A/B 범위이며 다른 모든 동적 스키마/음성/지원 이력의 실 모델 검증을 완료한 뜻은 아니다.

## 승인 요청

## 구현·오프라인 검증 결과

ScopedAnalysisContext를 운영 코드에 추가하고 요청별 EvaluationOutputSchema·평가 입력·v4 출력 파서/DTO에 연결했다.
관찰 키를 원본 참조로 복원하고, 네 분석 검수의 승인으로 기존 내부 EvaluationResult를 구성한다.
안전/입력 확인의 null 학습 검수와 일반 경로의 필수 검수, 현재 목표/해석 거절의 PASS 차단을 유지했다.
안내자·캐릭터 평가 프롬프트는 v7이다. 분석·생성 계약, 오케스트레이터, 공개 API·DB·프론트엔드는 바꾸지 않았다.

과거 분석 전용 v1 스키마를 기록된 계약에 고정했고, 범위 고정 진단은 운영 구성요소를 사용하는 어댑터로 정리했다.
기존 A/B 진단의 기록 스키마와 동일한지 스냅샷 검사도 추가했다.
합성 제공자·HTTP 검사·서비스 입력 진단을 새 평가 구조에 맞췄으며 실제 과거 응답은 변경하지 않았다.

- 관련 검사 365개: 실패·오류·건너뜀 0개.
- 첫 전체 check에서 이전 analysis_result 필드를 기대하던 P1DiagnosticsTest 두 건이 실패했다.
  실제 새 입력의 네 분석 객체와 후보가 기록되는지 확인하도록 검사 대상을 수정했다.
- 최종 `./gradlew --no-daemon spotlessApply check`: 2분 59초에 성공.
- XML 기준 167개 스위트, 총 2,517개 중 통과 2,511개, 실패·오류 0개, opt-in 제외 6개.
- 제외 항목은 실제 ML API 1개와 실제 ffmpeg 검사 5개다. 코드 형식·차이 검사와 JaCoCo 보고서도 완료했다.
- 빈 관찰·같은 목표의 다중 기준·다른 요청/후보 바인딩 차단·네 학습 검수 null의 우선 처리를 확인했다.

전체 검사를 재실행한 이유는 첫 실행에서 발견한 위 두 실패의 수정 때문이다. 성공 후 전체 검사를 추가 반복하지 않았다.

## 실제 통합 평가 결과

실행: `AI_MODEL=gpt-5.4-nano ./gradlew --no-daemon integratedEvaluationDiagnostic`

결과 위치는 build/eval/elice-p1-scoped-integrated-01이다.
기존 고정 A/B와 같은 후보를 사용하고, 평가 v7·wire v4에서 후보 checks와 최종 decision까지 한 번에 반환받았다.
Elice 요청 2회·재시도 0회이며 공유 예산 안에 끝났다. 추가 호출은 하지 않았다.
반환 모델 버전은 기존과 같은 gpt-5.4-nano-2026-03-17이다.

합계 9.132초, 입력/출력 15,879/1,139토큰이다. 전체 역할극 시간이나 실제 금액을 뜻하지 않는다.

A의 사건 관찰은 EXPLICIT이며 SUPPORTED/MATCHED_EXPRESSION으로 승인했지만 evidence_quote=null이었다.
현재 계약은 이 조합에 실제 아동 발화 인용을 요구하므로 모델이 PASS를 반환했어도 서버가 거절했다.
explanation의 인용처럼 보이는 문장을 evidence_quote로 대신 사용하지 않았다.

B는 활동 검수의 criterion_reference를 오기해 실제 관찰에 없는 참조를 반환했다. 이 검증에서 먼저 거절됐다.
별도로 원문을 대조하면 사건/감정 인용 모두 아동 발화에는 없고 후보 대사에만 있는 구절이다.
해석/전략 검수는 PRIMARY_GAP_MISMATCH로 거절하면서 후보 대사의 감정 단서 부족을 이유로 들었다.
이는 후보 품질 판단이 다시 분석 논리 검수에 섞인 출력이다.
서버가 먼저 거절한 사유 외의 이 문제들은 저장된 원문·요청을 대조해 확인했다.

두 응답에서 불필요한 관찰 추가는 없었고 현재 사건 목표와 활동 IN_PROGRESS를 구분한 승인 값이 나왔다.
그러나 올바른 키/대상·raw verdict만으로 검수 전체가 유효해지는 것은 아니다.
보고서의 observation_discrimination_success=true는 세 관찰 verdict의 사전 기대값 일치만 뜻한다.
인용·참조·범위별 설명·최종 판정 수용까지 성공했다는 뜻이 아니다. 실제 유효 평가 수용은 0/2다.
특히 B의 해석/전략 거절은 사전 기대값과도 일치하지 않았다.
