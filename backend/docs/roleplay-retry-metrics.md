# 역할극 LLM 재시도 지표와 상한 결정

## 현재 정책

- 분석: 턴 전체 최대 3회.
- 생성·평가: 후보별 최초 호출 포함 최대 3회.
- 후보: 턴 전체 최대 3개.
- 조합상 단계 시도 최대 21회. 정상 최소 경로는 3회다.
- 전체 시간 예산 최대 60초와 기존 복구 경로는 유지한다. 추가 전체 호출·비용 상한은 아직 미정이다.

## 기록 위치와 지표

`RetryingRoleplayTurnExecutor`는 캐시 결과 재사용을 제외한 단계 실행을 계측한다.
`RoleplaySpeechTurnPipeline`의 HTTP 운영 경로에 Micrometer 관측 포트를 주입한다.
기존 생성자는 관측 없는 구현으로 호환성을 유지한다.

| 이름 | 내용 | 태그 |
|---|---|---|
| roleplay.llm.stage | 단계 시도 횟수(Timer count)·시간 | operation, outcome |
| roleplay.llm.failure | 실행기가 판단한 실패 및 재시도 가능 여부 | operation, failure, retry_allowed |
| roleplay.llm.rejected | 평가가 전달을 거절한 횟수 | decision |
| roleplay.llm.turn | LLM 구간 종료 횟수·시간 | outcome, calls |
| roleplay.llm.calls | 턴의 단계별 시도 횟수 분포 | operation, outcome |
| roleplay.llm.candidates | 턴에서 할당한 후보 수 분포 | outcome |

outcome은 성공·예산 만료·실패 종류 또는 종료 사유의 고정된 값이다. calls는 기존 제한에 따라 0~21 범위다.
retry_allowed는 기술적 실패 유형과 횟수 제한에 따른 결정이다. 다음 시도 전 시간 만료 등이 있으면
실제 재시도는 일어나지 않을 수 있다. 후보 수는 생성 성공 수가 아니라 후보 ID를 할당한 수다.

APPROVED는 분석·생성·평가를 통과한 상태다. 이후 TTS·DB 저장·FE 전달의 성공을 의미하지 않는다.
시간은 STT·입력 검사·TTS·DB·업로드·큐 대기 시간을 제외한 LLM 실행 구간이다.
외부 HTTP 송신 횟수 또는 과금 횟수와 동일하지 않다. 프롬프트 준비·검증에서 끝나는 시도도 포함된다.
메타데이터의 토큰 수나 모델별 비용은 이번 지표에 포함하지 않는다.

실제 작업자가 종료될 때 종료 지표가 기록된다. HTTP 호출자가 먼저 시간 초과 응답을 받으면
지표가 늦게 기록될 수 있으며, 작업자가 돌아오지 않거나 프로세스가 종료되면 완료 표본이 빠진다.
해당 편향을 고려해 HTTP 오류·작업자 점유 지표도 함께 확인해야 한다.

요청·아동·세션·후보 ID, 발화, 프롬프트, 후보 내용, 제공자 오류 원문을 기록하지 않는다.
계측의 RuntimeException은 업무 처리에 전파하지 않는다. 누락 가능성이 있으므로 계측 장애는
운영 수집 체계에서도 확인해야 한다.

Micrometer 레지스트리에 등록하며, 기존 모니터링 수집 설정을 따른다. 이번 변경은 metrics나
Prometheus 엔드포인트를 공개하거나 보안 설정·대시보드·내보내기 시스템을 추가하지 않는다.

## 시간·호출·비용 기준을 정하는 방법

1. 시간: 허용 가능한 아동 대기 시간에서 업로드·큐·저장·음성·응답 전달 여유를 빼고 LLM 예산을 잡는다.
   현재는 전체 60초 제한을 유지하며, CloudFront 여유 관련 R3은 보류 상태다.
2. 호출: 총 시도 수별 종료 분포와 단계별 실패를 확인한다. 추가 시도로 늘어난 성공과 지연·사용량을 비교한다.
   고호출 요청만 골라 성공률을 비교하면 어려운 입력이 몰리는 편향이 있으므로, 변경 전후의 입력 구성·부하도 확인한다.
3. 비용: 허용 가능한 아동/수업 사용량과 월 예산으로 턴당 예산을 산정한다. 정확한 산정에는 별도 토큰·모델·과금 데이터가 필요하다.
4. 정책: 추가 전체 호출 상한을 설정으로 주입하고 단계별 상한과 함께 적용하는 방안을 결정한다.
   처음의 분석·생성·평가 경로(3회)는 제공할 수 있어야 하며, 재시도 뒤 평가할 자원도 고려한다.
   안전 검사나 평가를 생략해 상한을 맞추지 않는다. 한도 도달 시 검증하지 않은 후보 대신 기존 복구 경로를 사용한다.
5. 관측 후 조정: 시범 적용으로 성공률·지연·사용량을 비교한다. 관측 자료만으로 새로운 상한의 효과를 확정하지 않는다.

특정 전체 호출 상한(예: 9회)은 검토 예시이며 확정 정책이 아니다. 현재 단계에서는 재시도 정책을 바꾸지 않는다.

## 검증 범위

서식과 제품·기존 테스트 코드 컴파일만 확인한다. 사용자 요청에 따라 테스트 실행은 생략한다.
실제 운영 수집과 외부 제공자 호출·과금의 일치 여부는 검증하지 않았다.
