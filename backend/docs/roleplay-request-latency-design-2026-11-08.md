# 실제 역할극 요청의 지연 원인 관측 설계

상태: 설계 승인 후 구현·관련 검사·최종 전체 검사 완료. push·서버 배포는 미수행.
현재 완료한 요청/AI 호출 관측과 별도 원문 진단에 추가하는 최소 범위다.

## 해결할 질문

브라우저 Network에서 TTFB가 18.8초에서 35.6초로 늘었을 때,
AI 한 번의 호출 지연·재시도 증가·작업자 큐 대기·문맥 조회·입력 처리·TTS·결과 저장을 구분한다.
TTFB만으로 모델 추론 부하를 원인으로 확정하지 않는다.
브라우저 측 TTFB에는 네트워크 왕복과 앞단 전달 등도 포함되며 앱 필터에서 잰 시간과 경계가 다르다.

## 현재 확인할 수 있는 범위와 부족한 부분

- 기존 X-Trace-Id, LLM_CALL, LLM_VALIDATION, ROLEPLAY_REQUEST로 요청·호출 수·단계·시도·토큰·검증 결과·HTTP 전체 시간을 연결한다.
- AI 호출 시간은 제공자 호출 경계에서 관측한 시간이다. 제공자 네트워크·대기·추론을 내부적으로 분해한 수치가 아니다.
- 작업자 큐 대기·문맥 준비·TTS/STT·저장 시간을 각각 분리하지 못한다.
- 원문 파일의 capture_elapsed_ms는 수집 시작 후 위치이며 단계별 소요 시간을 대신하지 않는다.

## 추가할 시간 기록

요청 ID에 연결한 단조 시계 기준 시작 위치·소요 시간·결과를 기록한다.
각 실행 구간에 span_id와 parent_span_id를 부여해 포함 관계를 표시한다.
아래 이름은 설계상 단계 구분이며 최종 코드의 고정 enum/로그 필드로 대응한다.

| 구간 | 실제 코드 경계 | 얻는 정보 |
| --- | --- | --- |
| 요청 준비 | 입력 서비스의 세션 범위 조회·보존 게이트 등 | worker에 도착하기 전 앱 처리 시간 |
| 음성 업로드/검사 | 기존 uploads.create 호출 경계 | 전송된 입력 읽기·파일 검사 시간. 음성 요청만 해당 |
| 작업 대기 | RoleplayTurnRunner 작업 제출 직전→worker 실제 시작 | 제한된 worker/큐에서 기다린 시간 |
| 턴 준비/요청 처리권 | 체크포인트 실행기의 입력 준비·중복 확인/처리권 획득·기존 결과 조회 경계 | 중복 요청과 신규 처리의 경로·지연 |
| 문맥 준비 | ScopedText/VoiceTurnExecutor의 contexts.prepare/prepareVoice 및 진행 상태 조회 | 프롬프트에 쓸 문맥을 준비하는 앱/DB 호출 시간 |
| 입력 처리 | SpeechTurnPipeline의 STT 및 입력 검사 경계 | STT와 텍스트 입력 판정/전처리 구분 |
| AI 호출 | 실제 LlmProvider 호출 경계 | 단계·시도별 시간·호출 수. 입력 판정 호출도 포함 |
| 출력 검증 | StructuredLlmExecutor의 parser 호출 경계 | 외부 호출 이후 서버 파싱/도메인 검증 시간 |
| 음성 합성 | 기존 TTS 호출 경계 | 텍스트 입력 후 음성 응답을 만드는 경로도 포함 |
| 결과 확정 | checkpoint store의 commitApproved 호출 경계 | 저장 요청과 트랜잭션 완료를 포함한 관측 시간 |

이 표의 구간은 코드 실행 순서와 포함 관계에 맞춰 배치한다. 체크포인트·입력 처리 등 부모 구간 안에
DB/AI 호출이 포함될 수 있으므로 부모 시간과 자식 시간을 모두 더하지 않는다.
각 구간의 포함 시간과 겹침을 제외한 자체 시간을 구분한다. 루트 구간 중 분류하지 못한 시간도 남긴다.
관측되지 않은 시간을 모두 DB나 네트워크 시간이라고 부르지 않는다.
각 SQL·DB 연결 풀 대기·외부 제공자 내부 추론 시간을 이 단계에서 새로 계측하지 않는다.
저장/문맥 구간이 느리다는 근거가 나온 경우 그 구간을 후속 조사한다.

기술 로그 예시(수치는 가상):

```text
ROLEPLAY_STAGE request=... span=... parent=... stage=WORKER_QUEUE start_ms=... duration_ms=... outcome=COMPLETED
```

기술 로그에는 고정 단계·시간·결과·기존 요청 ID와 AI 단계/시도 연결 정보만 사용한다.
사용자 입력·세션/아동 식별자·프롬프트를 새 기술 로그에 추가하지 않는다.
request ID는 로그 상관키로만 사용하며 지표 태그로 쓰지 않는다.
각 요청의 전체 시간·단계별 호출 수·재시도 여부를 읽을 수 있는 요약을 기존 기술 로그에 연결한다.

## 비동기·실패 경계

- worker에는 요청 관측 문맥을 명시적으로 전달한다. 다른 스레드의 MDC에 의존하지 않는다.
- 큐 거절·시작 전 취소·실행 중 timeout을 구분한다. 시작하지 않은 단계를 0ms 성공으로 기록하지 않는다.
- HTTP 응답 시 worker가 계속 실행 중이면 해당 구간을 미완료로 표시한다.
  응답 후 종료한 작업의 시간을 사용자 대기 시간에 그대로 더하지 않는다.
- 멱등 재전달이면 replayed를 표시하고 새 모델 실행 표본과 분리한다.
- 관측 비활성 상태는 no-op이며, 활성화해도 모델 호출·재시도·예산·저장 순서는 바꾸지 않는다.
- 시간 수집의 예외가 사용자 처리 실패로 이어지지 않도록 기록 경계를 격리한다.

## 활성화와 원문 진단의 관계

단계별 기술 시간은 기존 neuringo.ai.call-log 설정에 연결한다.
원문 진단을 켜지 않아도 지연 원인을 조사할 수 있어야 한다.
원문 수집을 함께 켠 제한된 Dev 실험에서는 같은 요청 ID로 기록을 연결한다.
프론트엔드 코드 수정·새 조회 API·모니터링 제품 설치·운영 로그 상시 원문 수집은 추가하지 않는다.

## 검증과 전달

가짜 시계와 제어 가능한 worker/제공자로 큐 대기·AI 재시도·TTS·저장 지연이 구분되는지 검사한다.
부모/자식 시간 중복 집계·동시 요청 혼선·예외/취소/timeout·멱등 재전달·관측 비활성 경로를 검증한다.
벽시계 sleep에 의존한 느리고 불안정한 시간 임계치 테스트는 피한다.
실제 AI 호출 없이 관련 검사를 수행하고 최종 변경본에서 필요한 전체 검사를 완료한다.

기존 4개 커밋 이후 별도 목적의 커밋으로 추가하고 PR 본문·실제 입력 관측 절차를 갱신한다.
push·PR·배포는 기존 승인 범위를 따른다.

## 구현과 관련 검사

RoleplayTiming의 요청별 구간 트리와 단조 시계를 사용한다. 요청 스레드의 문맥은 범위 종료 시 복원하며,
worker 제출 시 Submission 객체로 명시적으로 전달한다. 별도 전역 요청 목록은 두지 않는다.
수집 구간은 요청당 256개로 제한하며 초과 시 truncated를 표시한다.
부모 자체 시간은 직계 자식의 시간 구간 합집합을 제외해 계산한다.
응답 시 스냅샷을 기록하고 응답 후 종료한 구간은 STAGE_LATE로 분리하며 기존 요약을 변경하지 않는다.

가짜 시계·제어된 worker로 큐 대기·포함/자체 시간·겹침·호출 실패/반복·큐 거절·시작 전 timeout·호출자 중단·늦은 작업·동시 요청 격리·기록 실패·한도를 검사했다.
실제 HTTP 회귀 검사에서는 요청 ID→단계별 기록→AI 호출 수→최종 결과를 연결하고 멱등 재전달의 AI 0회를 확인했다.
관련 검사 130개 통과(36초). 실제 외부 AI를 추가 호출하지 않았다.
최종 `./gradlew --no-daemon spotlessApply build` 성공(2분 57초).
총 2,865개 중 2,859개 통과, 선택 실행 항목 6개 제외, 실패 0개다.
실제 입력 판정 모델 경로의 HTTP 검사도 기술 관측을 켜고 입력 판정 호출 집계와 원문 비노출을 확인했다.
