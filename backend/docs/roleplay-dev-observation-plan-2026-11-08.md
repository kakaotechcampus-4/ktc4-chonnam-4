# 팀 AWS Dev 서버 실제 입력 관측 계획

작성일: 2026-11-08
상태: 승인된 관측 구현·최종 로컬 검사 완료. 공식 저장소 refactor 브랜치 push 승인 완료. PR·배포·실제 서버 입력 관측은 미수행.

## 오늘의 완료 기준

검증한 커밋을 팀 AWS Dev 서버에 배포하고, 팀원이 실제 화면에 직접 입력한 제한된 테스트 대화에서
요청→AI 단계→최종 응답→저장 결과를 연결해 확인한다.
각 결과에 배포 커밋·모델·추론 설정·단계별 지연·호출 수·실패 분류를 연결해 재현 가능한 기록을 남긴다.
모든 모델 품질 문제 해결이나 전체 부하 시험 완료를 오늘의 선행 조건으로 만들지 않는다.
다만 잘못된 출력의 전달 차단, 재시도 상한·60초 예산, 안전/입력 복구, 저장 정합성은 배포 전 검사 대상이다.

## 계획 수립 시 확인한 사실

- 현재 브랜치: refactor/evaluation-output-retry. HEAD는 9ffa124이며 운영 코드·검증·진단 변경이 미커밋 상태다.
- 캐릭터용 P1 독립 실행 3건은 첫 PASS 3/3, 평균 21.161초다. 잘못된 분석/후보 거절 능력이나 HTTP·DB·음성까지 검증한 것은 아니다.
- 배포 시 사용할 운영 평가 계약은 현재 v5/v7이다. 테스트 전용 검수 분리·근거 전체 참조·역할 검수 실험을 운영 적용한 것으로 취급하지 않는다.
- 팀 배포는 .github/workflows/deploy.yml에 정의된 develop CI 통과 후 배포 경로다.
- .github/workflows/dev-server.yml은 fork PR의 미리보기 배포를 명시적으로 건너뛴다.
- 서버 설정은 deploy/host/params.txt에 등록된 Parameter Store 값만 컨테이너로 전달된다. 로컬 .env.local은 서버에 반영되지 않는다.
- 현재 목록에는 AI_MODEL·AI_TIMEOUT·AI_MAX_RETRIES가 있지만 AI_REASONING_EFFORT·AI_MAX_OUTPUT_TOKENS·호출 로그 설정은 없다.
- 기존 CallLoggingLlmProvider는 목적·모델·시도·시간·토큰·제공자 결과를 기록한다. 요청 상관키와 파서/도메인 검수 결과는 이 로그만으로 부족하다.
- Actuator는 있으나 현재 웹 노출은 health/info다. 지표 대시보드가 준비됐다고 전제하지 않는다.
- 프로젝트 Spring AI는 2.0.1이고 현재 공식 reference 기본 페이지는 2.0.2다. 문서 기능을 적용하기 전에 사용 버전 API를 확인한다.

## push 시점과 순서

push는 서버 관측 전에 수행한다. 서버에서 나타난 문제를 수정한 뒤에는 별도 커밋으로 다시 검증·push·배포한다.
서버 검증 결과를 로컬 미커밋 상태와 연결하지 않는다.

1. 이번 배포에 포함할 운영 변경과 관련 회귀 검사·재현 문서를 확정한다.
2. 기존 오류 재생·정상/거절 분기·재시도/예산·HTTP/저장 관련 검사를 확인한다. 이미 있는 회귀 사례를 우선 재사용한다.
3. 서버 관측에 필요한 최소 설정 전달·로그 연결을 설계 승인 후 보완한다.
4. 원격 develop과의 차이·충돌을 확인하고 필요한 동기화 후 최종 build/형식 검사와 관련 가드를 완료한다.
   전체 검사는 최종 변경본에서 한 번 수행하고 새 수정/실패가 없으면 반복하지 않는다.
5. 목적별 커밋과 PR 본문을 준비해 변경 파일·검증 결과·미해결 사항을 검토 가능하게 만든다.
6. 사용자에게 정확한 push 대상과 커밋을 제시하고 최종 승인을 받은 후 공식 저장소(upstream)의 refactor 브랜치에 push한다.
7. 팀 develop 대상 PR의 CI·검토를 거쳐 배포 경로를 진행한다.

커밋 목적 예시:

- refactor: 역할극 평가 출력 계약과 재시도 정합성 개선
- test: 캐릭터 P1 진단과 평가 오류 회귀 검증 추가
- feat: Dev 서버 역할극 관측 연결 및 설정 전달
- docs: 측정 결과와 서버 재현 절차 정리

구현과 그 동작을 입증하는 핵심 테스트는 함께 검토 가능해야 한다. 파일 종류만 기준으로 억지로 나누지 않는다.
backend/env.local, .env.local, 키·사용자 데이터와 무차별적인 실험 산출물은 커밋 대상으로 일괄 추가하지 않는다.
기존 작업·측정 결과는 보존한다.

## 공식 저장소 refactor push와 실제 배포 경로

공식 저장소 refactor push만으로 팀 develop 서버가 바뀌지는 않는다.

기본 경로:

upstream refactor push → 같은 저장소 develop 대상 PR → CI/리뷰 → 승인된 merge → Deploy 성공 확인 → 서버 관측

머지 전 서버 검증을 원하면 팀 저장소 내부 브랜치의 PR 미리보기가 대안이다.
현재 워크플로는 fork PR을 거절하므로, 팀 저장소에 브랜치를 올릴 권한과 팀 서버 사용 조율이 필요하다.
사용자가 공식 저장소 refactor 브랜치 push를 명시적으로 지시했다. develop 직접 push·merge·배포 승인은 별도다.
다른 PR이 미리보기 자리를 쓰고 있거나 서버가 꺼져 있으면 배포가 건너뛰어질 수 있으므로 Actions Summary를 확인한다.
배포 후 이미지/커밋과 화면의 X-Neuringo-Release를 대조한다. 화면 헤더만으로 백엔드 이미지 일치를 단독 입증하지 않는다.

## 오늘 필요한 최소 관측

새 대시보드 구축을 선행 조건으로 삼지 않고, 먼저 서버의 구조화 로그와 브라우저 네트워크 기록을 연결한다.
로그에 필요한 최소 항목:

| 범위 | 기록 |
| --- | --- |
| 실행 환경 | 배포 커밋, 요청/응답 모델, 추론 수준, timeout, 출력 상한, 프롬프트·스키마 버전 |
| 요청 연결 | 관측용 요청 상관키, 단계, 시도 번호. 개인정보를 지표 태그로 쓰지 않음 |
| 외부 호출 | 성공/제공자 오류, HTTP 오류 분류, 시간, 토큰, 종료 이유 |
| 출력 검증 | JSON/스키마/도메인 정합성 실패, 판단보류. 제공자 OK와 분리 |
| 턴 결과 | 정상/재생성/재분석/복구/예산 초과, 호출 수, 전체 시간, 저장 성공 여부 |
| 사용자 체감 | 브라우저 요청부터 응답 표시까지. 음성 사용 시 STT/TTS·재생 구간도 구분 |

처음부터 모든 파이프라인을 범용 관측 프레임워크로 바꾸지 않는다.
오늘은 요청 전체·LLM 각 단계·검증/최종 결과·저장 여부를 연결하고, 음성 경로를 쓸 때 해당 단계 관측을 확인한다.
현재 LLM_CALL outcome=OK는 delegate.complete 성공이며 StructuredLlmExecutor의 파싱 성공이나 최종 PASS가 아니다.

서버에는 모델뿐 아니라 low 설정과 출력 상한·로그 설정을 전달할 수 있는지 점검한다.
필요한 Parameter Store 이름·환경변수 전달은 최소 변경으로 설계하고, 실제 적용값을 재배포 후 확인한다.
로컬과 다른 모델 옵션으로 나온 결과를 동일 조건 비교로 집계하지 않는다.
서버 전역에서 프롬프트/완성 원문 로그를 켜지 않는다. 팀원이 직접 입력한 재현 문장과 화면 결과는 접근을 제한한 실험 기록으로 관리한다.
오류 로그는 정제된 코드와 상관키 중심으로 남기고 위험 사건·실명·발화를 지표 태그나 영구 오류 원문으로 축적하지 않는다.

## 실제 입력 검증 순서

먼저 동시 요청 없이 팀원이 화면에서 직접 입력한다. 상태가 다른 세션을 섞어 같은 입력의 결과로 해석하지 않는다.

1. 로그인·시나리오 진입·역할극 시작부터 진행해 서비스가 실제로 조립하는 목표/지원/질문 이력을 사용한다.
2. 사건 파악 입력: 사건 목표 판단과 다음 감정 목표로의 전환을 확인한다.
3. 감정 표현 입력: 실제 문맥에 맞는 감정 관찰과 다음 응답을 확인한다.
4. 도움 요청: 학습 실패와 기술 실패를 구분하고 지원 정책을 지키는지 확인한다.
5. 오해 입력: 시나리오에 없는 의도/사실을 맞다고 강화하지 않는지 확인한다.
6. 새로고침·대화 조회로 승인된 결과가 저장됐는지 확인한다. 제한된 동일 요청 재전송은 멱등성 검증 항목으로 분리한다.
7. 필요하면 같은 소수 사례를 실제 음성 경로로 수행해 텍스트 관측과 구분한다.

처음 목표는 소수의 실제 대화에서 경로를 끝까지 연결하는 것이다. 대규모 부하·다중 JVM·모든 입력 커버리지는 이후 과제다.
빈 입력·제공자 실패·검수 모순·재시도 소진·예산 초과는 배포 전 자동 검사와 제어된 재현으로 확인한다.
팀 서버에 예고 없이 장애를 주입하지 않는다.

## 문제 발생 시 공식 문서 기반 처리

| 관찰 문제 | 우선 조사/해결 |
| --- | --- |
| 401/403/404/400 | 실제 서버 설정·권한·주소·요청 모델·지원 옵션. provider OpenAI 호환 연결 문서와 Elice 계약 대조 |
| JSON/필수 필드/스키마 오류 | 원본을 정제해 재현하고 네이티브 구조화 출력 및 수신 스키마 검증 점검 |
| 재시도/지연/예산 소진 | SDK·애플리케이션·Advisor 반복의 중첩과 실제 호출 수 점검. 기존 상한·60초 유지 |
| 역할/지원/학습 판정 오류 | 기획·원문·도메인 검증·반례 평가. 스키마 통과가 의미 정확성을 보장한다고 보지 않음 |
| 로그인/저장/중복/음성/화면 오류 | 해당 HTTP·트랜잭션·멱등성·음성 전달 경로. Spring AI만의 문제로 분류하지 않음 |

한 번에 한 원인을 재현 → 실패 지점 분류 → 사용 버전과 공식 문서 대조 → 최소 수정 설계/승인
→ 관련 검사 → 필요한 최종 검사 → 별도 커밋/승인 후 push·배포 → 같은 입력 재확인 순서다.
사용자 요구에 따라 구현 변경 전 설계 승인을 받고 push도 최종 별도 승인을 받는다.

문서 링크:

- [Spring AI Observability](https://docs.spring.io/spring-ai/reference/observability/index.html): ChatModel 관측·토큰·로그/추적. 기본 원문 로그는 비활성화다.
- [Provider-Native Structured Output](https://docs.spring.io/spring-ai/reference/api/structured-output/native.html): 제공자 측 스키마 제약과 지원 범위. 현재 평가에 이미 적용된 계약을 우선 점검한다.
- [Schema Validation & Self-Correction](https://docs.spring.io/spring-ai/reference/api/structured-output/validation.html): 검증 실패 피드백과 자동 재호출. 기존 외부 재시도에 그대로 더하지 않는다.

공식 문서를 근거로 선택하되 앱 기획·실제 Elice 지원·프로젝트 2.0.1 API와 대조해 적용한다.
오늘 전체 Spring AI 버전 업그레이드나 ChatClient/Advisor 전면 전환을 선행 작업으로 추가하지 않는다.


## 진행 기록

- 기존 서버 오류 차단·재시도·예산 회귀 검사 133개 통과.
- 최초 최소 반례 평가 2회: 후보 거절은 유효했으나 감정 관찰 거절의 사유/인용 충돌로 최소 기준 미충족.
- 추가 설계 승인 후 v5 관찰 조합 제약 구현, 관련 검사 340개 통과.
- 승인된 추가 반례 평가 2회: 잘못된 분석 REANALYZE, 잘못된 후보 REGENERATE가 각각 유효한 이유로 수용됨.
- 서버 설정 전달과 X-Trace-Id→AI 호출→출력 검증→HTTP 결과 연결을 구현했다.
- 추가 승인으로 dev 한정 원문 파일 수집을 구현했다. 기본 비활성·15분·10요청·총 20MiB·사건 1MiB이며 일반 콘솔과 분리한다.
- 공식 develop `d6f7e06` 동기화 후 최종 build 성공: 2,855개 중 2,849개 통과, opt-in 제외 6개, 실패 0개.
- DEBUG 예외 메시지 노출 회귀를 검사에서 발견해 고정 코드로 수정했다. 배포 스크립트·마이그레이션 가드는 Linux에서 통과했다.
- 검수 계약·평가 실행기·Dev 요청 관측을 목적별 로컬 커밋으로 나누고 [PR 본문](pr-roleplay-evaluation-output-retry.md)을 준비했다.
- 사용자의 대상 정정에 따라 공식 저장소 refactor 브랜치 push를 진행한다. 서버 관측의 실제 실행 절차는 [runbook](roleplay-dev-observation-runbook-2026-11-08.md)을 따른다.
- 후속 승인으로 큐·문맥·입력·AI·검증·STT/TTS·저장 구간의 시간 관측을 추가했다.
  포함/자체 시간·반복 호출·응답 시 미완료·응답 후 종료를 구분하고 원문 진단 없이도 시간 로그를 남긴다.
  최종 추가 변경본 전체 build 성공: 총 2,865개, 통과 2,859개, 선택 실행 제외 6개, 실패 0개(2분 57초).
