## 남은 의존성과 완료 확인 순서

1. 프론트엔드의 모의 시작 호출을 실제 시작 API로 교체하고 신규 201·복원 200, 메시지 중복 제거와 중단 상태를 반영한다. 동일 키·새 키의 기존 세션 복원 정책은 사용자 결정으로 확정했다.
2. 운영 `RoleplayContextSource.load`를 구현해 후속 음성 턴에 승인된 시나리오·작은 목표·현재 S·진행 상태·보존된 대화 이력을 일관된 체크포인트로 공급한다. 첫 질문은 시작 API에 연결돼 있다. 후속 턴에서 최초 입력 조회를 다시 적용하지 않는다. 음성 경로는 `roleplay.http.enabled=true`와 AI·STT·TTS 공급자 및 전달 설정이 필요하며, 플래그만 켜서는 운영 준비가 끝나지 않는다.
3. 승인 자료 공급 측에서 학급·조건 해시·버전 정보를 채운다. 기존 공용 자료는 자동으로 학급에 귀속하지 않으므로, 조건을 갖춘 승인본이 실제 공급되기 전에는 연결 후보가 없을 수 있다.
4. 프론트엔드 후속 변경 후 퀴즈 완료·미연결 복구·역할극 시작·동일 요청 재시도·세션 복귀를 실제 경로로 검증한다.

위 항목은 종단 완료를 위한 연동 의존성이다. AI 생성 전체·승인 화면·프론트엔드 전체를 이 Task에서 새로 구현하겠다는 범위 확장이 아니다.

`InitialScenarioPreparationService.prepare(activityId, authentication)`은 담당 강사 권한으로
최초 결합 활동의 확정 난이도와 해당 활동에 연결된 목표를 읽는다.
시나리오 생성·승인·배정이나 외부 AI 호출은 수행하지 않는 서버 내부 준비 경계다.
이 조회 자체는 읽기 전용이며 독립 HTTP API로 노출하지 않는다. 승인본 연결 소비자와 공개 역할극 시작 API가 이 저장 근거를 사용한다.

입력은 활동 ID와 검증된 인증 주체뿐이다. 아동·목표·학급·L/S·목표 조건 해시는 서버 저장값에서 구한다.

| 준비 결과 | 소비 용도 |
|---|---|
| `initialDifficulty.activityId` | 최초 결과 스냅샷과 연결된 활동 식별 |
| `initialDifficulty.childId`, `goalId` | 대상 아동·목표 일치 확인 |
| `initialDifficulty.scenarioLevel` | 시나리오 난이도 L |
| `initialDifficulty.initialSupportLevel` | 역할극 시작 지원 S |
| fallback 여부·사유·정책 버전·유효/첫 정답 수 | 판단 근거 보존 |
| `learningGoal` | 저장된 제목·상황·범주·등장인물·필수/금지 조건 |
| `reuseKey` | 학급 ID + 목표 조건 해시 + L 난이도 |

재사용 키는 승인 후보 조회 조건의 일부다. 실제 조회는 승인 상태·불변 버전·아동의 과거 제시 이력도 확인해야 한다.
키가 같다는 이유만으로 콘텐츠를 승인하거나 배정하지 않는다.

생성 입력에는 `learningGoal`의 교육 조건과 L만 매핑한다.
준비 결과 전체를 프롬프트로 직렬화하지 않으며 추적 ID와 S/fallback 근거는 서버에서 별도로 유지한다.

## 차단과 저장

- 권한 밖 활동은 `ACTIVITY_NOT_FOUND`로 숨긴다. 목표 조회는 담당 강사 전용 권한을 적용한다.
- 미완료·독립 퀴즈·미사용 결과·활동과 불일치하는 난이도는 `INITIAL_DIFFICULTY_NOT_READY`로 차단한다.
- 다른 아동의 목표 또는 빈 조건 해시는 `INITIAL_SCENARIO_INPUT_NOT_READY`로 차단한다.
- 내부 근거 조회·준비 입력 조립은 읽기 전용이며 난이도를 다시 계산하거나 목표·활동·결과를 변경하지 않는다. 공개 결과 GET은 아래 복구 조건에서 활동의 시나리오 연결만 재시도한다.
- 과거 정책과 fallback 사유를 유지한다. 사유가 없는 과거 fallback은 `LEGACY_UNSPECIFIED`다.

오류 코드는 이 내부 경계의 동작이며, 신규 공개 시나리오 API의 최종 HTTP 계약을 확정한 것이 아니다.

## 최초 결과 저장 알림

`QuizAttemptService`는 최초 난이도를 실제 적용하는 분기에서
`FirstQuizCompleted(activityId, childId, scenarioLevel)`를 발행한다.
승인 브랜치와 같은 이벤트 타입·필드를 사용한다. 유효 문항이 없어 기본값을 적용한 최초 결과도 대상이다.
미완료 퀴즈, 독립 퀴즈, 계산 실패와 이미 확정된 답안의 재전송은 새 완료 알림을 만들지 않는다.

소비자는 `@TransactionalEventListener(phase = AFTER_COMMIT)`로 받아야 한다.
이벤트 발행 시점에는 아직 저장 트랜잭션이 열려 있으므로 일반 `@EventListener`에서 배정이나 외부 호출을 실행하면 안 된다.
커밋 후 활동·최초 결과·목표 조건을 다시 확인하고 승인 후보 연결은 별도 트랜잭션으로 처리한다.
이벤트의 L만으로 승인본을 선택하거나 학급·목표 해시 검증을 생략하지 않는다.

`ScenarioAttachmentService`가 알림을 받아 `REQUIRES_NEW` 트랜잭션에서 실제 연결을 수행한다.
활동 → 아동 순서로 잠그고 최초 결과의 적용값·목표 소유 아동·저장된 조건 해시를 재확인한다.
이미 연결됐거나 완료된 활동, 비활성 아동, 불일치하는 이벤트는 변경하지 않는다.

`ScenarioRepository`는 학급·목표 조건 해시·L이 일치하는 `APPROVED` 버전 중 이 아동의 활동에 배정된 이력이 없는 후보를 고른다.
완료되지 않은 과거 배정도 사용 이력으로 간주한다. 생성 시각·ID 순으로 하나를 고르고, 연결 커밋까지 승인 상태를 공유 잠금으로 보호한다.
이미 연결된 활동의 시나리오를 바꾸지 않으며 초기 S·fallback·결과 스냅샷은 다시 쓰지 않는다.

후보가 없으면 활동의 시나리오는 비워 둔다. 연결 저장이 실패하면 새 트랜잭션만 롤백하고 이미 확정된 퀴즈 응답은 성공으로 유지한다.
AI 생성이나 미승인 초안 연결로 대신 진행하지 않는다. `scenario_source` 값은 이번 경계에서 새로 확정하지 않는다.

이는 프로세스 내 이벤트이며 영속 큐가 아니다. 자동 주기 재시도는 없고, 재조회로 연결을 복구한다.

## 결과 재조회 복구

## 세션 생성·복원 트랜잭션

2026-10-28 사용자는 같은 활동의 새 키 요청도 기존 세션을 복원하는 정책을 선택했다.
`RoleplayStartService.start(activityId, requestKey, authentication)`은 본인 아동만 허용하고 다음을 수행한다.

1. 활동 → 활성 아동 → 세션 순으로 잠근다. 요청 키가 다른 활동·아동에 사용됐으면 `IDEMPOTENCY_KEY_REUSED`로 차단한다.
2. 기존 세션이 있으면 현재 S·작은 목표·마지막 턴 ID/번호·체크포인트 버전·상태를 반환한다. 새 키는 같은 세션의 별칭으로 저장한다. 세션과 마지막 활동 시각은 변경하지 않는다.
3. 기존 세션이 없을 때만 최초 입력을 읽고 승인 버전을 공유 잠금으로 재확인해 세션과 요청 키를 함께 저장한다. 신규 생성은 현재 최초 결합 활동의 준비된 경로를 지원한다.
4. 반환값 `created`는 신규 생성 여부다. `RoleplaySessionState`는 내부 상태이며 공개 시작 메시지나 실제 AI 출력은 포함하지 않는다.

중단·완료 세션도 저장된 상태 그대로 반환하며 자동 재개·재시작하지 않는다.
내부 메타 상태 복원은 새 AI 호출을 뜻하지 않는다. 공개 응답 문구는 아래 문구 준비 경계가 같은 트랜잭션 안에서 확인하며 운영 대화 문맥 연결은 별도다.
과거 같은 활동에 세션이 여러 개 있으면 `ROLEPLAY_SESSION_AMBIGUOUS`로 차단하며 임의로 합치거나 삭제하지 않는다.

V17의 `roleplay_start_request`는 요청 키를 이 역할극 시작 저장소 안에서 고유하게 유지한다.
다른 활동의 동시 동일 키 INSERT가 충돌하면 트랜잭션 전체를 롤백하고 409로 변환한다. ORM merge로 기존 연결을 덮어쓰지 않는다.
키는 연결된 세션 삭제 시 FK cascade로 함께 삭제되며 임의 시간 TTL이나 다른 API와의 영구 통합 키 정책은 추가하지 않았다.
세션 생성의 활동별 직렬화는 활동 행 잠금을 따르는 서비스 경로가 보장한다. 기존 세션 데이터를 보존하기 위해 세션 표에 활동 ID UNIQUE를 추가하지 않았다.
