# 역할극 판정 정합성과 정상 경로 지연 개선 설계

상태: 2026-11-09 사용자 승인 후 백엔드 구현·로컬 회귀 검증 완료. 실제 AI 비교·push·배포는 미실행이다. 기존 사용자 문서 변경은 보존한다. 결과는 [구현 결과](roleplay-latency-improvement-results-2026-11-09.md)에 기록한다.

## 1. 목표와 현재 근거

재분석 반복을 줄이는 것과, 재시도가 없는 분석·생성·검수 자체를 빠르게 만드는 것을 함께 다룬다. 단일 문구를 맞히는 예외 처리는 만들지 않는다.

새 버전 cac1fa8의 Dev 요청에서 첫 외부 호출은 입력 판정 4.347초, 분석 8.520초, 생성 6.210초, 검수 13.024초였다. 합계 32.101초다. 생성 시간이 0초라고 가정해도 다른 세 호출에 25.891초가 남는다. 생성만 최적화해서 충분히 빨라진다고 설명할 수 없다.

첫 거절은 현재 목표를 달성하지 않고 다음 목표를 다룬다는 이유였다. 확정 기획의 비순차 목표 정책과 충돌한다. 두 번째 거절은 도움 제안을 부분 이해로 인정하지 않는 판단이었다. 현재 캐릭터 분석 규칙과 검수의 적용 기준이 일치하지 않았다.

EvaluationOutput에서 내부 EvaluationResult로 변환할 때 세부 검수 사유가 대부분 사라진다. analysisRetry는 failure_codes와 revision_instruction을 사용하지만 이번 REANALYZE는 revision_instruction=null이었다. 특히 두 번째 거절은 구체적인 LEARNING_STATE_MISMATCH·RESPONSE_ACT_MISMATCH가 아닌 UNSUPPORTED_CAUSE_ANALYSIS만 다음 분석에 전달되는 구조다.

이전 P1 세 건의 재시도 없는 내부 흐름도 19~22초였다. 이 값은 HTTP 입력 판정·TTS·저장을 포함하지 않는다.

## 2. 1차 변경: 같은 정책과 구체적인 수정 대상 전달

### 공통 캐릭터 정책

- 캐릭터 역할극과 안내자 문답의 정책을 분리한다. 캐릭터 분석에 안내자 기준을 모두 붙이고 뒤에서 예외로 덮는 현재 조합을 정리한다.
- 목표 순서 없음, 질문 초점 변경과 달성 처리 구분, 도움 제안과 도움 요청 구분, 걱정·도움 제안의 부분 이해 기준을 짧은 공통 정책으로 구성해 분석·검수에 동일하게 전달한다.
- 지원 이력·S3 정답 제공·독립 달성·완료·안전·판정 불가 규칙은 보존한다. 아동 발화를 키워드나 물음표로 강제 분류하지 않는다.
- 목표 건너뛰기 거절은 ‘미관찰 목표를 달성했다고 처리함’과 ‘활동을 부당하게 종료함’ 등 실제 위반을 구조화해 받는다. 단순한 초점 변경은 허용된 정책이므로 이를 위반 근거로 수용하지 않는다. 서버가 확인 가능한 상태·대상·제안 판정과 대조한다. 자연어 후보의 의미가 옳다는 것까지 자동 확정하지 않는다.

### 재분석 피드백

- 거절된 검수 영역, 허용된 사유 코드, 분석의 수정 대상 경로를 내부 결과에서 AnalysisRetry까지 보존한다.
- 원문 설명은 필요한 경우 짧은 비신뢰 자료로 취급한다. 모델 설명을 새로운 시스템 지시로 승격하거나 예외 원문을 그대로 프롬프트에 복사하지 않는다.
- 세부 사유가 같은데 같은 분석이 재생성되는지 진단에서 비교할 수 있도록 한다. 첫 승인을 캐시하거나 실제 분석 거절을 무시하지 않는다.

이 변경을 먼저 고정해 정상 경로와 유효한 거절 경로를 만든다. 이후 속도 비교에서도 같은 정책을 유지한다.

## 3. 2차 변경: 분석·생성의 모델 출력 축소

기존 SpringAiLlmProvider는 요청별 JSON Schema를 제공자에 보내는 기능이 있다. 이를 캐릭터 분석·생성에도 사용한다. 라이브러리 업그레이드나 별도 재시도 Advisor는 추가하지 않는다.

### 분석 출력

모델이 반복 출력하는 turn_id·analysis_id·내부 버전·관찰별 UUID/긴 criterion_reference는 서버가 이미 알고 있다. 이 값들을 작성하게 하는 대신 승인된 기준에 요청별 키를 부여한다.

예: 모델은 observations의 o0/o1/o2에 상태를 반환하고 서버는 각각을 요청에 고정된 원래 관찰 참조로 복원한다. 필수 키 누락·추가·모르는 키는 거절한다. 목표 선택은 승인 목표 enum으로 제한하고, 활동 달성 근거도 기존 승인 참조 검증을 유지한다.

학습 상태·응답 행위·대표 격차·다음 전략 등 의미 판단은 모델이 수행한다. 판단 근거는 짧게 남기며 진단 원문을 없애지 않는다. 복원 후 기존 분석 검증·지원 보정을 그대로 수행한다.

### 생성 출력

모델에는 캐릭터 text와 필요한 경우 mascot_hint를 작성하게 한다. 후보 ID·턴 ID·확정 목표·전략·지원·이전 실패 후보 ID·계약상 응답 유형은 서버가 구성한다.

모델이 잘못 주장한 유형을 조용히 바꾸는 방식이 아니다. 해당 메타데이터를 모델 출력 계약에서 제외하고 서버가 책임지는 방식으로 변경한다. 실제 대사가 S3 답 제공에 해당하는지, 주체가 맞는지는 독립 검수가 계속 확인한다. 타입만 맞는 간접 단서나 역할이 뒤집힌 문장을 자동 통과시키지 않는다.

외부 HTTP와 DB의 CandidateResponse 계약은 유지하고 모델 전용 wire schema와 서버 복원기를 둔다. 안내자 경로를 함께 바꾸지 않는다. 새 모델 출력 버전과 프롬프트 버전을 기록한다.

## 4. 3차 변경: 분석·검수 입력과 설명량 축소

- 승인 기준은 한 곳의 정의로 전달하고 현재 판단 대상에서는 그 정의를 참조한다. 현재 관찰·확정된 과거 증거·목표별 사전 지원의 구분은 유지한다.
- ScopedAnalysisContext의 서버 원본·검증용 바인딩은 유지한다. 모델에 보내는 표현만 투영해 같은 기준·참조를 여러 곳에 반복 직렬화하는 부분을 줄인다.
- 검수 스키마가 이미 제한하는 필드 구조·허용 코드 설명과 긴 출력 예시의 중복을 줄인다. 구조 규칙과 교육 정책을 구분한다.
- 검수 explanation은 짧은 근거 한 문장으로 정리한다. 거절 사유와 실제 인용을 없애거나, 길이 초과만으로 새 의미 재시도를 만드는 방식은 피한다.
- 전체 이력을 LLM으로 다시 요약하는 추가 호출, 단순 최근 N건 절단으로 필수 지원 근거 제거, 관찰 누락을 허용하는 방식은 사용하지 않는다.

문자 수·바이트·제공자 토큰을 구분해 전후를 기록한다. 스키마를 API로 옮긴 것만으로 전체 입력 토큰이 반드시 감소한다고 가정하지 않는다.

## 5. 수정할 백엔드 지점

| 지점 | 책임 |
|---|---|
| RoleplayPromptFactory 및 캐릭터 정책 리소스 | 모드별 정책 선택, 동일 정책 전달, 작은 입력 구성 |
| EvaluationOutput·AnalysisReview·관련 Schema·EvaluationResult | 실제 거절 근거 검증, 내부 세부 사유 보존 |
| StructuredRoleplayTurnSteps·AnalysisRetry | 다음 분석에 수정 영역·사유 연결 |
| 캐릭터 분석·후보 전용 출력 Schema/Parser 신규 | native 제약, 요청별 바인딩 복원, 기존 업무 검사 호출 |
| ScopedAnalysisContext | 원본 검증과 모델 입력 투영 구분 |
| 기존 평가 실행기·관련 테스트 | 같은 사례·설정의 전후 비교, 정상·거절·예산 경로 검사 |

캐릭터 정책과 피드백, 작은 모델 출력, 입력 투영을 목적별 동작·커밋으로 나눈다. 새로운 DB 테이블·캐시·대시보드·프론트엔드 변경은 예상하지 않는다. 진행 중 이 범위를 넘어서는 구조 변경이 필요하면 별도 설계한다.

## 6. 검증과 성능 해석

1. 합성 도움 제안, 현재 목표 미달성 상태의 초점 변경, 실제 잘못된 달성/종료, 역할 주체가 뒤집힌 후보를 고정 사례로 만든다. 실제 Dev 문장만으로 원래 승인 목표·지원 이력 전체를 재현했다고 주장하지 않는다. 기존 재현 가능한 P1도 유지한다.
2. 외부 AI 없이 스키마·키 바인딩·지원 이력·원래 의미 필드 보존·세부 거절 사유 전달·예산과 안전 우선·저장 전 확정 경로를 검사한다.
3. 출력·입력 축소 전후 같은 정책과 모델·추론 설정·케이스로 비교한다. 우선 로컬 내부 흐름을 비교하고, Dev에서는 입력 판정·TTS·저장까지 포함한 HTTP 시간을 따로 본다.
4. 실제 AI 초기 검증 제안은 고정 합성 사례의 축소 전 1턴/축소 후 1턴과 잘못된 후보의 단일 검수 1건이다. 유료 호출은 사용자 승인 후 수행한다. 추가 반복은 결과를 확인한 뒤 정한다. 단건 비교로 p95나 안정성을 주장하지 않는다.
5. 호출 수, 첫 후보/첫 검수 시간, 최종 전달/복구 시간, 단계별 입력·출력 토큰, 정상 거절 유지와 최종 대사 품질을 함께 기록한다. 호출이 빨라도 실패가 늘면 개선으로 채택하지 않는다.
6. 관련 검사를 동작별로 실행하고 변경이 모인 최종 상태에서 전체 필수 검사를 마친다. 같은 상태의 전체 검사를 확인 목적으로 반복하지 않는다.

성능 완료는 ‘소스 코드가 짧아짐’이나 ‘timeout에 빨리 도달함’이 아니다. 같은 조건에서 의미 품질을 유지하면서 정상 처리 시간이 감소한 증거가 필요하다. 10초 같은 목표값 달성은 측정 전 보장하지 않는다. 60초 상한은 그대로 유지한다.

## 7. 남는 경우의 후속 선택

입력·출력량을 줄여도 충분하지 않으면 단계별 모델·추론 설정을 비교한다. 기존 목적별 라우팅 기반을 재사용하되 Elice 모델의 옵션 지원과 환경변수·배포 전달을 확인한다. reasoning=none 같은 옵션을 지원 확인 없이 적용하지 않는다.

분석→서버 지원 보정→생성→독립 검수의 의존성이 있으므로 단순 병렬 호출이나 분석·생성 통합은 이번 범위에 넣지 않는다. 특히 지원 보정이 분석 결과를 사용하므로 통합은 별도 업무 계약 검토가 필요하다. 검수 전 대사를 스트리밍해 전달하는 방식도 사용하지 않는다.

## 공식 문서 근거

- [Provider-Native Structured Output](https://docs.spring.io/spring-ai/reference/api/structured-output/native.html): API 수준 스키마 제약, 프롬프트의 중복 구조 설명 축소, 제공자별 지원 한계.
- [Schema Validation & Self-Correction](https://docs.spring.io/spring-ai/reference/api/structured-output/validation.html): 수신 검증과 구체적 실패 조건을 전달하는 제한된 수정 재시도.
- [Observability](https://docs.spring.io/spring-ai/reference/observability/index.html): 호출 시간·토큰·모델 정보의 관측.

웹 문서는 현재 2.0.2, 프로젝트는 2.0.1이다. 현재 설치된 API를 기준으로 기존 제공자 경로를 확장하며 문서의 새 예제를 복사하는 프레임워크 교체를 목표로 삼지 않는다.
