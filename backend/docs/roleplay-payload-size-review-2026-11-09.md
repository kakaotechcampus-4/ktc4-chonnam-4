# 역할극 입력·출력 크기 조사

조사일: 2026-11-09. 실제 AI 추가 호출 없이 저장된 합성 P1 결과 3건과 사용자가 전달한 Dev 로그를 집계했다. 원문·키·음성 데이터는 이 문서에 복사하지 않는다.

세 건 모두 각 단계를 한 번 호출했다. 평균은 분석 7.567초, 생성 5.309초, 검수 8.138초, 전체 21.161초다. 이 실행기에는 실제 HTTP 입력 판정·TTS·저장이 포함되지 않는다.

Dev의 60초 요청은 입력 판정 1.442초, 첫 분석 12.274초, 첫 생성 5.611초, 첫 검수 15.368초로 첫 거절 판정까지 외부 호출 합계 34.695초였다. 이후 추가 호출로 남은 예산을 소모했다. 첫 후보의 거절을 없애더라도 이 요청이 10초 안에 완료된다고 결론 낼 수 없다.

이 Dev 요청에서 큐 대기 0ms, 컨텍스트 준비 35ms, LLM 호출 구간 59.834초가 관측됐다. 단건의 우선 개선 대상은 AI 경로다. 다른 요청이나 동시 부하에서도 DB·큐가 빠르다는 뜻은 아니다.

## 2. 모델 사용량과 로컬 문자 수 구분

| 단계 | P1 입력 토큰 범위 | P1 출력 토큰 범위 | Dev 첫 입력/출력 토큰 |
|---|---:|---:|---:|
| 분석 | 7,137~8,550 | 740~847 | 15,602 / 1,281 |
| 생성 | 4,350~5,083 | 331~369 | 4,739 / 445 |
| 검수 | 10,011~10,106 | 764~1,049 | 18,946 / 1,525 |

위 토큰은 제공자가 보고한 값이다. 입력·시나리오·이력 등이 다른 실험이므로 토큰 증가가 지연 증가를 일으켰다고 확정하지 않는다. 추론 토큰과 보이는 출력의 세부 비중은 이 집계만으로 분리하지 못한다.

아래 문자 수는 로컬 diagnostics.jsonl의 input 객체를 `json.dumps(input, ensure_ascii=False, separators=(',', ':'))`로 직렬화한 크기다. 출력은 저장된 파싱 전 문자열의 `len(output)`이다. 토큰 수나 실제 HTTP 바이트 수와 다르다.

| 단계 | 입력 JSON 문자 수 | 출력 원문 문자 수 |
|---|---:|---:|
| 분석 | 세 건 모두 3,348 | 1,751~1,981 |
| 생성 | 2,876~3,052 | 329~344 |
| 검수 | 5,397~5,576 | 1,833~2,065 |

입력 JSON 크기가 같아도 시스템 지침·제공자 스키마를 포함한 전체 요청이 동일하다는 뜻은 아니다. 저장된 로컬 진단의 native_schema는 불리언이므로 그것의 문자열 길이를 스키마 크기로 계산하지 않았다. 전체 제공자 입력을 구성별 토큰으로 정확히 분해한 결과는 아니다.

각 값은 필드 값만 직렬화한 문자 수다. 키·구분자와 다른 필드도 있으므로 전체 입력 크기와 단순 합산해서 같아지는 표는 아니다.

P1에서는 최근 대화가 작다. 긴 대화 전체를 보내는 것이 이번 P1의 주원인이라는 설명은 맞지 않는다. 코드에서도 최근 대화는 MAX_DIALOGUE_LINES로 제한한다.

관찰 맥락·목표별 요약·이번 검수 항목은 겹치는 정보를 담지만 역할이 다르다. 기존 확정 근거, 독립 달성 판단, 현재 관찰 검수, 참조 검증을 담당하므로 중복이라는 이유만으로 전체를 지우면 안 된다.

Dev의 분석·검수 전체 MODEL_REQUEST는 이번 발췌에 없어서 동일한 구성별 분해는 수행하지 못했다. 다음 Dev 관측에서 이미 존재하는 제한된 원문 진단을 이용해 이력 개수와 각 구성 크기를 확인하면 된다. 새 수집 체계는 추가하지 않았다.

## 4. 지침 크기와 이번 변경의 비용

공식 develop ccb95d8의 리소스를 실제 조합 순서와 빈 줄로 연결한 문자 수다. 새 구현의 값도 같은 방법으로 집계했다.

이번 수정은 판정 모순 차단이 목적이며 지침 축소가 아니다. 공통 계약 입력·검수 근거 필드도 추가돼 첫 호출 비용이 늘 수 있다. 재시도 감소가 이를 상쇄하는지 실제 호출 수·토큰·시간으로 확인해야 한다. 성능이 개선됐다고 보고하지 않는다.

## 5. 다음 변경 후보와 비교 방법

1. 지침에 반복된 출력 구조 설명을 native 스키마와 역할을 나눠 축소한다. 의미 판단 규칙은 보존하고 구조 준수를 지시하는 중복 문장부터 조사한다. 현재 생성·분석은 검수와 같은 native 스키마 경로가 아니므로 일괄 삭제하지 않는다.
2. 검수의 기존 관찰 맥락과 범위별 검수 입력을 대조해 같은 증거를 중복 직렬화하는 부분을 줄인다. 참조 ID·승인 목표 기준·독립 달성/정답 제공 구분은 보존한다.
3. 분석·검수의 장황한 explanation을 줄인다. 실제 인용과 판단 사유는 남긴다. max-output-tokens만 낮추는 방식으로 자르지 않는다.
4. 위 변경을 각각 같은 고정 사례에서 비교한다. 동시 변경하지 않는다. 단계별 모델 비교는 Elice 옵션 지원 확인과 역할극 환경변수·배포 전달 연결을 별도로 설계한 뒤 수행한다.

각 비교에서 첫 후보까지/첫 검수까지/전체 전달까지의 시간, 호출 수, 재시도 사유, 제공자 토큰, 최종 응답 품질을 같이 본다. 실패가 빨라진 것을 성능 개선으로 계산하지 않는다. 입력 조건에는 대사뿐 아니라 목표·지원·확정 이력도 포함한다.

이 조사는 다음 축소 대상을 고르는 근거다. 모델 내부 추론·게이트웨이 큐·네트워크 시간을 분리한 측정이나 p95 추정, 비용 계산은 아니다. 운영 설정·입력 축소·모델 변경은 이번 작업에서 적용하지 않았다.
