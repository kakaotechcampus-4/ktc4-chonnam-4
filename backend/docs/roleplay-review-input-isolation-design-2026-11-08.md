# 분석 검수의 후보 입력 유무 비교 설계

작성일: 2026-11-08\
상태: 승인 범위의 테스트용 구현·관련 검사·실 API 비교 완료. 후보 제거만으로 해결되지 않음.

## 이번에 확인할 질문

v3 통합 평가의 A에서 모델은 후보 대사를 아동 발화로 인용했고, 활동·분석 논리 검수 사유에도 후보 판단을 넣었다.
이는 해당 출력에서 확인된 혼동이다. 모든 실패의 원인이 후보 입력이라는 뜻은 아니다.
이전 analysis-review-diagnostic/v1에서는 후보를 제거하고도 사건/활동 거절·전략 정보 부족이 있었다.

운영 검수를 바로 두 호출로 바꾸기 전에, 분석 검수만 하는 동일 작업에서
현재 후보가 있는 경우와 없는 경우를 비교해 입력 분리의 타당성을 확인한다.
현재 v3 운영 코드는 유지하며 테스트용 진단만 추가한다.

## 비교 조건

기존 고정 A 하나를 사용한다. 잘못된 감정 관찰을 추가하는 기존 B 실험과 다른 비교다.

| 조건 | 모델 입력 | 모델의 작업 |
| --- | --- | --- |
| candidate-absent | 기존 A에서 candidate_response만 제거 | 아동 발화·관찰·활동 판정·분석 논리 검수 |
| candidate-present | 기존 A 그대로 | 위와 같은 분석 검수만 수행 |

두 조건에 같은 분석 검수 전용 프롬프트와 같은 출력 스키마를 사용한다.
시나리오·승인 기준·상태·아동 발화·최근 대화·확정 관찰/지원 이력·분석 결과·식별자는 동일하다.
순서는 absent → present로 고정하고 각각 1회만 호출한다.
absent 요청의 시스템·사용자 메시지에 현재 후보 본문이나 후보 판단 지시를 복사하지 않는다.
기존 최근 대화와 발화 당시 지원 이력은 필요한 분석 맥락이므로 임의로 삭제하지 않는다.

분석 검수 전용 지시에서는 후보 품질 검사와 후보에 대한 decision·revision_instruction을 요구하지 않는다.
동일한 검수 전용 지시 아래 두 입력을 비교하므로 조건 간 차이는 candidate_response의 유무다.
현재 v3 통합 평가와 비교할 때는 작업 범위·프롬프트·출력 계약도 달라졌다는 점을 명시한다.

## 출력과 검증

새 진단 버전은 roleplay-analysis-isolation-diagnostic/v1, 스키마는 analysis-isolation-diagnostic/v1이다.
v3에서 다음 세 필드의 스키마를 그대로 선택해 제공자 네이티브 제약과 수신 검증에 사용한다.

- observation_reviews: 현재 관찰 한 개의 분류·실제 아동 발화 인용.
- goal_observation_review: 요청 분석 ID와 activity_review.
- analysis_logic_review: 발화 해석·학습 상태·격차·전략/지원의 논리 검수.

checks·decision·failure_codes·revision_instruction·candidate_id는 출력 스키마에서 제외한다.
이 진단은 후보 평가나 전달 판정을 수행하지 않는다. 없는 후보 검사 값을 만들어 운영 PASS를 구성하지 않는다.
요청은 후보 없는 독립 호출로 구성하며, Spring AI의 기존 strict 네이티브 출력 경로·SDK 재시도 0회를 사용한다.

서버의 기존 관찰 검증기와 활동/논리 검증기를 테스트용 어댑터에서 직접 사용한다.
기존 분석/검수 경계를 검증하기 위해 운영 규칙을 느슨하게 바꾸거나 별도의 유리한 검증 규칙을 복제하지 않는다.
필수 필드·허용 값·분석 ID·정확한 관찰 집합·인용 출처·사유/활동 상태·관찰 참조를 모두 검사한다.
전용 어댑터는 src/test에만 두며 의미 판단·형식/근거 검증·판단보류를 분리해 반환한다.

### 이 사례의 사전 기대값

| 검수 | 기대값과 이유 |
| --- | --- |
| 사건 관찰 | SUPPORTED. 아동이 멈추고 앉았다는 사건을 실제로 말함 |
| 활동 IN_PROGRESS 판정 | SUPPORTED. 사건을 알아차린 것만으로 승인 활동 목표 ‘친구의 감정을 이해하고 공감하기’를 달성했다고 확정하지 않음 |
| 분석 논리 | SUPPORTED. 현재 사건 근거를 반영하고 다음 질문 초점을 감정으로 이동하는 것은 고정 순서 강제나 목표 건너뛰기가 아님 |

기대값과 이유는 결과 채점에만 사용하고 모델 요청에 넣지 않는다.
모델이 거절하면 실제 사유를 읽고 기대값의 타당성과 대조한다. 서버가 결과를 정답으로 고치지 않는다.
이 P1 기대값을 다른 시나리오의 모든 작은 목표 달성 규칙으로 일반화하지 않는다.

## 호출 상한과 산출물

- 제공자/요청 모델: 기존 Elice ML API / gpt-5.4-nano. 모델·기존 timeout·출력 상한을 바꾸지 않는다.
- 전체 최대 2회, 공유 60초, SDK/진단 재시도 0회. 분석·생성·후보 검수·음성 호출 없음.
- 제공자 실패·기한 종료·JSON 스키마 실패면 남은 호출을 중단한다.
- 잘못된 인용·추가 관찰·거절 판정 등 의미/근거 결과는 기록하고 다른 조건도 예정된 1회만 수행한다.
  이런 결과 자체가 비교 대상이므로 첫 의미/근거 실패만으로 반대 조건을 생략하지 않는다.
- 결과 위치: build/eval/elice-p1-review-isolation-01. 기존 폴더가 있으면 호출 전에 중단한다.
- 두 요청의 차이가 candidate_response 삭제뿐인지, 같은 프롬프트·스키마인지 오프라인 검사한다.
- 호출 직후 요청/프롬프트/스키마/출처·해시/원문/사용량·시간/검증 결과를 저장한다.
- 합성 데이터 로컬 진단으로 한정하며 키·인증 정보는 기록하지 않는다.
- 채점은 정확한 관찰 집합·인용 출처를 포함한다. 기대한 한 항목의 verdict만 맞는 것을 전체 관찰 성공으로 보고하지 않는다.

## 결과에 따른 다음 판단

| absent | present | 해석 |
| --- | --- | --- |
| 타당 | 후보 혼동 | 이 사례·같은 검수 작업에서 후보 제거가 유용했을 가능성. 반복성·일반화는 미확인 |
| 타당 | 타당 | 축소된 검수 작업에서는 둘 다 가능. 후보 입력만이 원인이었다고 단정할 수 없음 |
| 실패/보류 | 실패/보류 | 후보 제거만으로 충분하지 않음. 운영 호출 분리 구현으로 자동 확대하지 않음 |
| 실패/보류 | 타당 | 후보 제거의 개선 근거가 없음. 단건 변동·검수 기준과 설명을 재검토 |

어떤 결과도 전체 역할극 PASS율·p95·지연 개선의 증거로 사용하지 않는다.
단건 두 조건의 비교이므로 후보 유무의 일반적인 인과 효과를 입증한 실험이라고 주장하지 않는다.

## 운영 분리의 비용과 보류 범위

분석 검수와 후보 검수를 운영에서 분리하면 정상 경로가 현재 3회에서 일반적으로 4회 호출로 늘어난다.
우선 후보 생성 뒤 두 검수를 수행하는 형태라면 분석→생성→분석 검수→후보 검수이며,
분석 검수를 생성 전에 옮길지는 안전·진행 우선순위와 함께 별도 설계한다.
기존 60초 안에서 추가 지연과 토큰을 감당하는지는 새 측정이 필요하다. 기존 단건 시간을 더해 예측하지 않는다.

현재 평가 재시도는 후보당 최대 3회다. 그 안에 두 호출을 단순히 넣으면 재시도마다 둘 다 반복될 수 있다.
운영 연결 전에는 분석 ID·입력/정책에 묶인 요청 내 검수 결과 재사용, 각 검수의 물리 호출 상한,
새 분석/후보의 무효화 규칙, 안전/입력 확인 우선순위, 최종 전달 게이트를 정해야 한다.
이번에는 이 운영 상태 머신을 수정하지 않는다.

## 승인 요청

테스트용 진단 추가 → 관련 오프라인 검사·형식 검사 → 위 두 실제 호출까지 승인 요청한다.
운영 코드가 바뀌지 않고 새 문제가 없다면 이미 통과한 전체 check는 반복하지 않는다.
이전 전체 검증은 2,479개 중 통과 2,473개, 실패·오류 0개, 조건부 건너뜀 6개다.
운영 프롬프트·평가 계약·재시도·완료 정책·DB·프론트엔드·모델 변경·commit/push는 포함하지 않는다.
추가 호출이나 운영 분리 구현은 결과를 보고 별도 승인받는다.

## 실행 및 검증 결과

ReviewIsolationDiagnostic, 테스트용 AnalysisIsolationValidation 어댑터와 reviewIsolationDiagnostic 작업을 추가했다.
운영 코드·운영 프롬프트는 바꾸지 않았다. 분석 전용 프롬프트는 src/test/resources에 두었다.
관련 65개 테스트가 실패·오류·건너뜀 없이 통과했고 spotlessCheck와 차이 검사도 통과했다.
이번 범위에서는 기존 전체 check를 반복하지 않았다.

실행: `AI_MODEL=gpt-5.4-nano ./gradlew --no-daemon spotlessCheck reviewIsolationDiagnostic`

실제 두 요청을 비교해 candidate_response 삭제 외의 JSON 차이가 없고, 시스템 프롬프트와 스키마가 같은 것을 확인했다.
두 요청 모두 기존 모델 버전 gpt-5.4-nano-2026-03-17을 반환했다.
실제 호출 2회, 재시도 0회, 중도 중단 없음. 두 호출 합계 11.615초, 입력/출력 6,626/1,466토큰이다.
전체 역할극 처리 시간이 아닌 두 진단의 시간 합계이며 단가가 없어 달러 비용은 계산하지 않았다.

| 결과 | 후보 없음 | 후보 있음 |
| --- | --- | --- |
| 진단 시간 | 5.942초 | 5.673초 |
| 제공자 호출 시간 | 5.926초 | 5.671초 |
| 입력/출력 토큰 | 3,258 / 663 | 3,368 / 803 |
| JSON 스키마 | 통과 | 통과 |
| 사건 관찰의 인용 출처 | 실제 아동 발화 | 실제 아동 발화 |
| 관찰 검수 수 | 요청 1개, 반환 3개 | 요청 1개, 반환 3개 |
| 첫 서버 거절 | observation review references do not match | 동일 |
| 모델의 활동 검수 | UNSUPPORTED / CONTINUATION_NOT_GROUNDED | 동일 |
| 모델의 분석 논리 검수 | UNSUPPORTED / LEARNING_STATE_MISMATCH | 동일 |
| 최종 진단 분류 | INVALID_EVIDENCE | INVALID_EVIDENCE |

두 조건 모두 사건의 실제 발화 인용과 SUPPORTED는 맞았다. 그러나 현재 분석이 제안하지 않은 감정·연결 리뷰를 추가했다.
후보 없는 조건은 추가 두 항목을 정보 부족으로, 후보 있는 조건은 근거 없음으로 표시했다.
이 추가 항목 자체가 이번 검수 대상이 아니므로 판단보류나 유효한 관찰 거절로 집계하지 않고 참조 집합 오류로 처리했다.

모델의 짧은 사유에서 목표 범위를 섞는 문제가 드러났다.

- 후보 없음: 현재 learning_state의 GOAL_ACHIEVED를 거절하면서 감정/이유 근거가 없다고 설명했다.
  활동 IN_PROGRESS의 거절 사유에도 GOAL_ACHIEVED와 활동 전체 달성 근거의 부재를 연결했다.
- 후보 있음: 현재 사건 목표가 아닌 감정·연결 목표 ID를 지목하며 GOAL_ACHIEVED를 거절했다.
  활동 IN_PROGRESS는 현재 사건 목표의 증거가 충족됐다는 이유로 거절했다.

이 사례에서 learning_state는 현재 질문 초점인 사건 목표의 판정이고, activity_goal은 활동 전체 판정이다.
사건 표현만으로 현재 사건 목표를 달성하고 활동은 IN_PROGRESS로 두는 조합은 그 자체로 모순이 아니다.
다른 목표의 증거 부재를 현재 사건 목표의 실패 근거로 쓰거나 현재 사건 달성을 전체 활동 달성과 동일시하면 안 된다.
새 사유는 이 구분이 출력에 반영되지 않은 근거이며 모델 내부 사고 과정을 관측한 결과는 아니다.

진단의 checks 내 승인 Boolean들은 검증이 실패해 null이다. 각각 승인/거절을 확정했다는 의미가 아니다.
모델이 반환한 raw verdict와 서버가 받아들인 검수 결과를 구분해야 한다.

## 이번 결론과 다음 경계

후보가 없어도 같은 관찰 범위 오류와 목표 수준 혼동이 나타났다.
따라서 후보 제거만으로 충분하다는 근거를 얻지 못했고 운영 호출을 4회로 늘리는 변경도 진행하지 않았다.
이번 두 조건에서는 이전 후보 대사 인용 문제가 재현되지 않았지만, 변경된 분석 전용 작업에서 나온 단건 결과다.
이전 통합 프롬프트와 비교해 후보 제거 하나의 효과나 지속적인 개선을 주장하지 않는다.

현재 확인된 다음 검토 대상은 검수할 관찰의 정확한 집합과 현재 목표·활동 목표의 범위를
입력 구조·출력 제약·서버 규칙으로 어떻게 명확히 연결할지다.
이번 결과만으로 특정 구조 변경이나 모델 교체를 정답으로 확정하지 않는다.
운영 코드 추가 수정·추가 실제 호출·commit/push는 수행하지 않았다.
산출물은 build/eval/elice-p1-review-isolation-01에 보존했다.
