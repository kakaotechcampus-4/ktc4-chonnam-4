# 운영 평가 v2의 실제 모델 검증 계획

작성일: 2026-11-08\
상태: 승인 범위 구현·관련 검사·실 API 진단 완료. 첫 호출의 검증 실패로 중단.

## 확인할 질문

관찰 전용 진단에서는 동일 Nano가 A 사건·B 사건을 승인하고 B의 잘못된 감정 관찰을 거절했다.
이제 관찰 검수를 운영 평가 프롬프트 v5의 다른 검사와 함께 수행해도 같은 구분이 유지되는지 확인한다.
운영 코드의 오프라인 전체 check는 성공했지만 실제 모델의 통합 판단은 아직 측정하지 않았다.

기존 roleplayEval의 캐릭터 P1은 질문 횟수·최근 대화가 서비스 첫 입력 상태와 맞지 않는 이전 합성 입력을 사용한다.
이번에는 해당 실행기를 그대로 재호출하지 않는다. 서비스 조립 경로에서 확보해 고정한 기존 A/B 입력을 사용한다.

## 실험 범위

| 항목 | 조건 |
| --- | --- |
| 제공자·모델 | 팀 Elice ML API, 요청 모델명 gpt-5.4-nano |
| 입력 | 기존 analysis-review-observation-pair-p1-v1.json과 ObservationPairDiagnostic.cases()의 A/B |
| A | 실제 발화에 근거한 사건 EXPLICIT 관찰 |
| B | A에 발화에 없는 감정 EXPLICIT 관찰만 추가 |
| 공통 고정 | 발화·서비스 상태·승인 기준·시나리오·후보 응답·활동 판정·다음 전략 |
| 요청 생성 | 운영 RoleplayPromptFactory.responseEvaluation 경로, 현재 캐릭터 평가 v5 |
| 출력 검사 | 운영 evaluation-output/v2 네이티브 스키마와 현재 서버 파서·관찰 검증기 |
| 호출 수 | A 1회 → B 1회, 최대 2회. 분석·생성·음성 호출 없음 |
| 재시도 | 진단 재시도 및 SDK 재시도 0회. 실패 시 자동 추가 실행 없음 |
| 시간 | 두 호출을 합쳐 공유 60초 예산, 각 요청에 남은 예산 적용 |
| 변경 금지 | 운영 코드·프롬프트·모델·토큰 상한·timeout·저장 스키마 변경 없음 |

A/B 후보는 동일하게 유지한다. 분석/생성을 다시 호출하면 검수 대상도 달라져 이번 비교가 어려워진다.
분석·후보·목표 참조를 기존 고정 입력에서 복원해 운영 요청 생성기에 전달하고, 결과 요청과 원본의 의미 필드를 대조한다.
원본에 없는 학습 이력이나 질문을 채워 넣지 않는다. 객체 복원에 필요한 누락 필드는 의미에 영향을 주는지 확인하며,
근거 없이 새 상태를 가정해야 한다면 호출 전에 중단하고 설계를 조정한다.
기대 정답은 모델 요청에 넣지 않는다.

## 결과 해석

| 관측 | 기대 또는 해석 |
| --- | --- |
| A 사건 SUPPORTED | 기존 관찰 전용 진단과 같은 결과 |
| B 사건 SUPPORTED, 감정 UNSUPPORTED | 올바른 관찰과 허위 관찰을 구분 |
| 인용·기준 참조·reason_code | 현재 운영 검증을 통과해야 함 |
| A 관찰 승인 | 내부 observations_supported=true. 최종 PASS를 강제하지 않음 |
| B 관찰 거절 | 내부 observations_supported=false, analysis_supported=false 및 UNSUPPORTED_CAUSE_ANALYSIS·유효한 REANALYZE와 일치해야 함 |
| 관찰별 결과는 맞고 다른 판정과 모순 | 관찰 구분 성공과 운영 결과 수용 실패를 각각 기록 |
| INSUFFICIENT_CONTEXT | 판단보류. 형식 실패·제공자 실패와 별도 기록 |
| 잘못된 구조·인용·참조·판정 일관성 | INVALID_OUTPUT_FORMAT. 단건 진단이므로 재평가하지 않고 종료 |
| 제공자 실패·시간 초과 | 실패 위치와 사용량을 기록하고 종료. 모델 판단 능력의 실패로 단정하지 않음 |

A가 다른 활동·전략·후보 검사 때문에 REANALYZE를 반환할 수도 있다.
관찰 승인과 전체 평가 통과를 따로 판단하고, 다른 실패를 관찰 로직의 성공으로 덮지 않는다.
통합 스키마 통과·관찰 판정 일치·전체 판정 일관성을 각각 보고한다.
이 실험은 전체 역할극의 재시도·응답 전달 성공률이나 분석→생성→평가 총 지연을 측정하지 않는다.
두 단건의 결과로 일반 정확도나 p95를 추정하지 않는다.

## 구현 및 산출물

승인 후 테스트용 고정 진단 실행기와 별도 Gradle 실행 작업만 추가한다.
오프라인에서 물리 호출 상한·공유 예산·실패 후 중단·운영 요청/파서 사용·A/B 입력 차이를 검사한 뒤 실제 호출한다.
새 테스트 코드만 추가한 단계에서는 관련 검사와 형식 검사를 수행한다.
운영 코드 변경이나 새로운 실패가 없다면 이미 통과한 전체 check를 반복하지 않는다.

결과 폴더: build/eval/elice-p1-integrated-evaluation-01

- 기존 파일이 있으면 덮어쓰거나 자동으로 다른 이름으로 재실행하지 않는다.
- 요청·스키마·프롬프트·고정 입력의 출처/해시·응답·서버 수용 결과·호출별 시간/토큰을 보존한다.
- 각 호출 직후 결과를 저장하고 제공자 실패·시간 초과·출력 검증 실패가 나면 후속 호출을 중단한다.
- 합성 입력의 로컬 진단 산출물로 한정한다. 키·접속 인증 정보는 출력/기록하지 않는다.
- 이번 코드가 미커밋 상태라는 점과 프롬프트/스키마 버전, 이전 관찰 전용 결과와의 차이를 요약한다.

## 승인 범위와 다음 판단

승인 요청은 위 테스트용 진단 구현·오프라인 관련 검사·최대 2회의 실제 Elice 평가 호출이다.
실패해도 수정·추가 호출·모델 교체로 자동 확대하지 않고 결과와 다음 설계를 제시한다.
통합 검수가 타당하면 다음 단계로 서비스 상태를 사용한 전체 텍스트 턴 실행을 별도 설계한다.
운영 기능 추가·DB/프론트엔드 변경·commit/push는 포함하지 않는다.

## 실행 결과

테스트용 IntegratedEvaluationDiagnostic과 별도 Gradle 작업을 추가했다.
운영 요청을 고정 입력과 JSON 전체 비교해 동일성을 확인했다.
입력 객체 복원에 쓰는 기존 State 생성자의 마스코트 기본값(0/false)은 평가 요청에 직렬화되지 않으므로,
실제 모델 입력을 바꾸거나 새로운 이력으로 제시하지 않는다.

- 관련 테스트: 새 진단 9개, 기존 관찰 근거 진단 25개, 기존 A/B 진단 12개, 총 46개 통과.
- 코드 형식 검사 통과. 이 단계에서는 운영 코드를 변경하지 않아 전체 check를 반복하지 않았다.
- 실제 실행: `AI_MODEL=gpt-5.4-nano ./gradlew --no-daemon spotlessCheck integratedEvaluationDiagnostic`
- 실제 요청 1회, SDK/진단 재시도 0회. A 실패 후 B는 호출하지 않았다.
- 요청 모델명 gpt-5.4-nano, 반환 모델 버전 gpt-5.4-nano-2026-03-17.
- 평가 프롬프트 roleplay-response-evaluation-character/v5, 스키마 evaluation-output/v2.
- 미커밋 상태의 코드에서 실행했다. 코드 기준·입력/프롬프트/스키마 해시는 결과 폴더 source.json에 기록했다.

| A 결과 | 값 |
| --- | --- |
| 진단 전체 시간 | 4.384초 |
| 제공자 호출 시간 | 4.357초 |
| 입력/출력 토큰 | 6,279 / 329 |
| JSON 스키마 | 통과 |
| 사건 관찰 | SUPPORTED, MATCHED_EXPRESSION, 실제 발화 전체 인용 |
| 관찰 기대값 | 1/1 일치 |
| analysis_supported | true |
| activity_goal_supported | false |
| goal_aligned | false |
| failure_codes | GOAL_SKIPPED, STATE_STRATEGY_MISMATCH |
| 모델 decision | REANALYZE |
| 서버 결과 | INVALID_OUTPUT_FORMAT |
| 서버 거절 사유 | goal review contradicts analysis check |

원인은 JSON 문법·enum 실패가 아니다. 서버는 유효한 사건 관찰을 먼저 승인했지만,
활동 판정을 거절한 결과와 analysis_supported=true가 모순돼 전체 평가를 수용하지 않았다.
현재 계약은 활동 판정이 근거 없다고 거절하면 분석 승인도 false로 두도록 요구한다.
입력의 활동 판정은 ACHIEVED가 아닌 IN_PROGRESS다. activity_goal_supported는
“활동을 달성했는가”가 아니라 “분석의 IN_PROGRESS/ACHIEVED 판정이 근거에 맞는가”를 검수하는 값이다.

단건에서 통합 평가의 사건 인용·분류는 유지됐다. 하지만 활동 판정·분석 체크·실패 코드·판정 사이의 일관성 문제는 남았다.
모델이 활동 판정을 왜 거절했는지는 별도 사유를 반환하지 않아 확인할 수 없다.
IN_PROGRESS를 미달성과 혼동했거나 현재/다음 목표를 혼동했을 가능성은 가설이며, 이번 출력만으로 확정하지 않는다.
프롬프트에는 이미 두 의미의 구분과 현재 목표에서 다음 목표로 넘어가는 조건이 적혀 있다.
같은 지시를 더 반복하는 것만으로 해결됐다고 볼 근거는 없다.

B 미실행이므로 감정 거절과 A/B 구분 능력은 이번 통합 진단에서 검증하지 못했다.
보고서의 observation_discrimination_success=false는 두 사례 검증이 완료되지 않았다는 뜻이며,
A의 관찰 판정이 틀렸다는 뜻이나 B에서 실패했다는 뜻이 아니다.
Gradle BUILD SUCCESSFUL은 진단 실행·저장이 끝났다는 뜻이며 AI 평가가 통과했다는 뜻이 아니다.
이번에는 재평가를 수행하지 않았으므로 운영의 최대 3회 재평가가 복구할지도 측정하지 않았다.

산출물: build/eval/elice-p1-integrated-evaluation-01의 summary.md, result.json, source.json 및 A/B 요청·스키마·프롬프트.
B에는 호출 전 준비한 요청만 있고 응답 결과는 없다.
자동 수정·추가 실제 호출·모델 변경·commit/push는 수행하지 않았다.
다음 설계에서는 활동 판정 검수의 근거와 전체 판정 사이의 중복 Boolean을 어떻게 줄일지 검토한다.
활동 판정을 임의로 승인하거나 모순 검사를 완화하는 변경은 하지 않는다.
