# 분석 검수와 후보 검수의 호출 분리 진단 설계

작성일: 2026-11-08\
상태: 승인 범위의 테스트용 구현·관련 검사·실제 최대 3회 진단 완료. 분석 구별 성공, 후보 검수 품질 문제는 남음. 운영 미적용.

## 해결할 문제와 가설

직전 근거 선택 진단은 형식·서버 검증 2/2를 통과했지만 의미 판단에 실패했다.
A는 후보 대사의 부족을 아동 분석의 오류로 판단했고, B는 후보의 ‘멍해졌어’를 아동의 감정 근거로 사용했다.
원문 전체 참조를 서버가 연결하는 방식은 이 혼동을 기존 인용 검사에서 감췄으므로 채택하지 않는다.

이번 가설은 한 호출에서 두 작업을 구분하도록 지시하는 대신,
분석 검수 요청에 현재 후보를 전달하지 않으면 현재 후보를 아동 발화의 증거로 사용하는 경로를 차단할 수 있다는 것이다.
이 구조도 현재 목표와 활동 목표의 혼동, 이전 대화의 출처 혼동, 모델 자체의 오판을 모두 막지는 못한다.
앞선 분석 전용 실험 중 실패 사례도 있었으므로 호출 분리만으로 해결된다고 전제하지 않는다.

## 현재 구현과 운영 반영 시의 목표 흐름

현재 StructuredRoleplayTurnSteps와 RetryingRoleplayTurnExecutor는 다음 순서를 사용한다.

분석 → 생성 → 통합 검수 → 전달 조건 확인

RoleplayPromptFactory.responseEvaluation은 ScopedAnalysisContext.input()에 candidate_response를 추가한다.
그래서 출력 필드를 범위별로 나눴어도 동일한 모델 호출은 분석 입력과 후보를 모두 볼 수 있다.

장기적으로 검증할 흐름은 다음과 같다.

분석 → 분석 전용 검수 → 승인된 분석으로 생성 → 후보 전용 검수 → 서버 전달 조건 확인

분석 검수에서 타당하지 않다고 확정하면 생성 전에 재분석한다.
판단보류·출력 형식·제공자 오류는 학습 실패나 의미적 분석 거절로 바꾸지 않는다.
후보가 기준을 충족하지 못하면 승인된 분석을 유지하고 후보만 다시 생성한다.
후보 검수는 이미 승인한 아동 관찰을 덮어쓰거나 재분석을 지시할 수 없다.

이 운영 흐름은 아직 구현 승인 범위가 아니다. 우선 아래 테스트 전용 진단을 수행한다.

## 1. 분석 전용 호출의 입력과 출력

입력은 기존 범위 분리 분석 입력을 재사용하되 명시적인 필드 목록으로 구성한다.
canonical_utterance, 명확히 역할을 표시한 과거 대화, 시나리오·승인 목표·기준,
현재 질문 목표·지원 이력·이전 확정 관찰, 이번 분석의 네 검수 범위만 포함한다.
후보 객체를 만든 뒤 한 필드를 지우는 방식으로 격리를 보장하지 않는다.

현재 후보 본문·ID, 후보 검수 결과, 후보 대사를 인용한 재시도 설명을 전달하지 않는다.
현재 후보는 생성 전 흐름의 데이터이므로 분석 검수 입력의 의존성에도 포함하지 않는 것을 목표로 한다.
이전 AI 대화는 당시 맥락으로 유지하며 이번 아동 발화와 출처를 구분한다.
이번 고정 실험에는 재시도 이력을 추가하지 않는다.

테스트 실행기는 기존 RESPONSE_EVALUATION 요청 운반 객체를 재사용한다. 이 객체는 추적 정보의 candidateId를 필수로 요구하므로,
분석 검수의 해당 칸에는 현재 후보에서 읽지 않는 별도 진단 식별자를 사용한다. 이는 모델 메시지·스키마에 전달되지 않는다.
생성됐거나 검수된 후보로 간주하지 않으며 도메인 실행기·재시도 기록에도 연결하지 않는다.
이 테스트의 단계는 별도 stage와 프롬프트/스키마 버전으로 구분한다. 운영의 새 단계 식별자는 별도 통합 설계 사항이다.

출력은 다음 다섯 항목만 허용한다.

- analysis_id: 요청에 고정된 분석 식별자.
- observation_reviews: 고정 o0/o1 키별 관찰 검수.
- current_goal_review: 현재 질문 목표와 제안된 학습 상태 검수.
- activity_review: 활동 판정과 실제 근거 참조 검수.
- interpretation_strategy_review: 발화 해석·격차·다음 전략·지원 논리 검수.

candidate_id, 후보 checks, 최종 decision, safe_to_send는 분석 검수 출력에 없다.
현재 ScopedAnalysisContext.schema()/validate()와 기존 관찰·활동 검증 규칙을 재사용한다.
구체 evidence_quote를 요구하고 이번 아동 원문의 실제 부분 문자열인지 검사한다.
u0 원문 전체 자동 연결은 사용하지 않는다. 누락 인용·틀린 참조를 서버가 보충하지 않는다.
활동 근거는 기존 실제 reference 계약을 유지해 분리 효과와 근거 계약 변경을 섞지 않는다.

## 2. 후보 전용 호출의 입력과 출력

분석 검수에서 네 범위 모두 승인된 A에 대해서만 실행한다.
기존 고정 A 후보를 사용해 생성 변동을 제거한다. 이번 실험에서 생성 호출은 하지 않는다.
따라서 실제 분석→생성→검수 전체 흐름이나 생성 시점의 품질을 검증한 결과로 주장하지 않는다.

입력에는 아동 원문·역할 구분 대화·시나리오·지원 정책·검수 승인된 분석·후보를 넣는다.
분석 승인은 서버가 별도 검수 결과와 같은 analysis_id를 확인한 사실로 연결한다.
모델에 분석 검수 정답이나 B의 기대값을 알려주지 않는다.
후보 검수는 승인된 분석과 후보의 일치·안전·응답 품질만 판단한다.

새 테스트 전용 네이티브 스키마는 다음 필드만 허용한다.

- analysis_id, candidate_id: 두 식별자를 각각 요청 값에 고정.
- checks: 기존 후보 품질 11개 항목 유지.
- decision: PASS, REGENERATE, SAFETY_REGENERATE, CONFIRM_INPUT, SAFETY_ESCALATION.
- failure_codes, revision_instruction: 기존 후보 검수에 해당하는 코드·수정 지시 계약 유지.

REANALYZE, 분석 검수 객체와 분석 승인 플래그는 허용하지 않는다.
후보 모순은 analysis_response_consistent=false와 후보 재생성으로 처리한다.
분석 전용 UNSUPPORTED_CAUSE_ANALYSIS와 STATE_STRATEGY_MISMATCH는 모델 출력 enum에서 제외한다.
PASS는 11개 검사 전부 통과·식별자 일치·별도 분석 승인일 때만 가능하다.
실패 코드와 검사 항목의 모순, 안전·입력 확인 우선순위, 기존 수정 지시 필수 조건을 약화하지 않는다.
안전 문제는 분석 승인 여부와 무관하게 전달을 차단하며 기존 상위 입력·안전 검사도 유지한다.

후보 전용 스키마와 검증기는 기존 조각·규칙을 재사용하고, 통합 출력의 빠진 네 검수 필드를
모델이 출력한 것처럼 만들어 기존 파서에 넣지 않는다. 두 실제 결과를 별도로 보존한다.
서버 조합 결과에서만 기존 내부 EvaluationResult/GoalObservationOutput.Review 호환성을 확인한다.

## 3. 서버 조합과 사전 기대값

| 조건 | 기대 처리 |
| --- | --- |
| 분석 검수 형식·근거 오류 | 기술적 검증 실패. 분석 거절 확정이나 후보 전달로 바꾸지 않음 |
| 분석 검수 판단보류 | INDETERMINATE_OUTPUT. 학습 실패로 기록하지 않음 |
| 분석 검수에서 하나 이상 UNSUPPORTED | 분석 거절. 후보 검수 호출 생략 |
| 분석 네 범위 승인, 후보 기준 실패 | 후보 재생성 또는 안전/입력 확인 경로. 분석 승인 유지 |
| 분석 네 범위 승인, 후보 PASS | 기존 내부 전달 게이트까지 통과해야 전달 가능 |

A의 기대값은 사건 관찰·현재 사건 목표 GOAL_ACHIEVED·활동 IN_PROGRESS·해석/전략 승인이다.
B는 사건 승인·추가 감정 관찰 거절이며, 정상인 현재 사건 목표·활동 IN_PROGRESS·해석/전략과 구분해야 한다.
활동 IN_PROGRESS 승인에 모든 미세 목표 달성을 요구하지 않는다. 고정 순서·새 완료 조건을 도입하지 않는다.

A의 후보 PASS를 정답으로 강제하지 않는다. 후보는 답변 유형·지원·목표 기준에 따라 별도로 검토한다.
후보 실패 시 거절 사유가 후보 품질에 해당하는지 원문과 함께 확인한다.
B는 단순히 최종 거절됐는지가 아니라, 잘못된 감정 관찰 때문에 거절됐는지 확인한다.

## 4. 승인받을 구현·실행 범위

테스트 전용 SplitReviewDiagnostic, 후보 검수 스키마·검증/조합 보조 코드,
프롬프트 스냅샷, 실행 작업과 관련 테스트만 추가한다.
기존 ScopedAnalysisContext 및 분석 전용 진단 자원을 재사용하고 과거 산출물은 수정하지 않는다.
새 실험의 입력·프롬프트·스키마는 실행 전에 고정하고 버전·해시를 보존한다.

오프라인 검증은 다음을 확인한다.

1. 고유 표식이 있는 현재 후보를 바꿔도 분석 요청·스키마·프롬프트가 동일하고 현재 후보 데이터가 유입되지 않음.
2. 과거 대화의 역할·순서 보존, 기존 분석 입력과 관찰 대상·목표·지원 조건의 일치.
3. 분석 인용·참조·상태/사유 규칙, 누락·타 요청 식별자·판단보류의 거절.
4. B 분석 거절 시 후보 호출 0회. 후보 출력이 분석 검수를 덮어쓰거나 REANALYZE를 선택할 수 없음.
5. PASS 조건, 후보 불일치 재생성, 안전/입력 확인 우선순위와 내부 결과 조합.
6. 공유 예산 만료·취소·늦은 응답 폐기, 최대 호출 수와 추가 재시도 없음.

관련 검사와 형식 검사만 실행한다. 운영 코드를 수정하지 않으므로 전체 검사는 반복하지 않는다.

실제 호출은 Elice gpt-5.4-nano로 다음 순서다.

1. A 분석 전용 검수 1회.
2. B 분석 전용 검수 1회.
3. A/B 모두 사전 분석 기대값과 일치하고 기존 근거 검증까지 통과한 경우에만 A 후보 검수 1회.

최대 3회, 각 1회, SDK·진단 재시도 0회, 전체 진단 공유 예산 60초다.
기존 모델·호출 timeout·출력 토큰 상한은 유지한다.
제공자·스키마·시간·실행 실패는 즉시 중단한다.
의미/인용/참조 오류는 기록 후 예정된 다른 분석 사례를 한 번만 확인하고 후보 호출은 생략한다.
모델이 형식상 거절했다는 이유로 즉시 프롬프트를 바꿔 재호출하지 않는다.

결과 폴더는 build/eval/elice-p1-split-review-01이다. 이미 있으면 호출 전에 중단한다.
원문 응답·단계별 검증·판단 근거·조합 결과·생략 이유·호출 수·시간·토큰·입력 해시를 남긴다.
실제 사용자 전달·저장·추가 유료 호출·운영 변경·commit/push는 범위에 포함하지 않는다.

## 5. 시간·비용과 운영 통합 시 별도 결정할 사항

일반 정상 경로의 외부 호출은 기존 분석/생성/평가 3회에서 분석/분석검수/생성/후보검수 4회로 증가한다.
실패 분석은 생성 전에 거절할 수 있지만 정상 경로에는 추가 왕복과 중복 문맥 비용이 발생한다.
짧아진 개별 출력이 전체 지연을 줄인다고 가정하지 않는다.
이 진단은 두 분석·한 후보 측정이므로 전체 턴 지연, p95, 비용 절감 여부는 판단할 수 없다.
단가 미설정이면 토큰만 기록하며 금액을 추정하지 않는다.

운영 통합은 별도 설계 승인 후 진행해야 한다. 최소한 다음 결정을 포함한다.

- 별도 분석 검수 단계·메타데이터·실패 집계 추가. 현재 RESPONSE_EVALUATION 지표에 숨기지 않음.
- 분석·분석검수·생성·후보검수 각각의 시도 상한 및 총 외부 호출 상한.
  현재 분석 최대 3회·후보당 평가 최대 3회를 새 단계에 무조건 복제하지 않음.
- 승인된 분석의 요청 내 재사용: 같은 분석/입력/지원 맥락에서만 재생성에 재사용하고 재분석 시 폐기.
- 분석 거절이 생성 전에 발생할 수 있도록 현재 RejectedCandidate 기반 재시도 기록과 단계 인터페이스 변경.
  존재하지 않는 후보나 평가를 만들어 기존 실행기를 속이지 않음.
- STT·TTS·저장까지 포함하는 기존 턴 60초와 남은 예산 전달·취소·복구 경로 유지.
- 안전/입력 확인이 분석 검수 단계에서 감지되는 경우의 우선 경로와 결과 계약 명시.
- 백엔드 내부 결과·평가 실행기·계측·기존 회귀 검사 연결. 필요한 프론트엔드 변경은 최종 정리에서 안내.

이번에는 이 운영 변경까지 승인받거나 실행하지 않는다.
고정 A/B의 구조적 격리·근거 검증·의미 구별 결과를 먼저 보고 다음 범위를 결정한다.

## 실행 결과

SplitReviewDiagnostic, 테스트 전용 SplitReviewValidation, 분석/후보 프롬프트 스냅샷과 별도 실행 작업을 추가했다.

형식 검사와 git diff --check도 통과했다. 이번 단계의 운영 코드 수정·전체 검사 반복은 없다.

외부 진단은 예정된 순서대로 정확히 3회 실행됐으며 재시도·추가 호출은 없다.
요청은 Elice gpt-5.4-nano, 응답 모델은 gpt-5.4-nano-2026-03-17이다.

분석 A/B의 기대값과 기존 인용·참조 검증이 모두 일치해 예정된 후보 검수까지 수행했다.
A/B 모두 사건 인용은 실제 이번 아동 원문이었으며 B의 감정 거절은 NO_MATCHING_EXPRESSION·null 인용이었다.
현재 사건 목표 GOAL_ACHIEVED와 활동 IN_PROGRESS도 구분했다. 후보를 볼 수 없는 분석 검수의 이번 결과는 긍정적이다.

그러나 후보 검수의 품질 문제는 남았다.
검수는 AI 캐릭터가 직접 말한 ‘그때 좀 멍해졌어’를 상대 친구의 감정을 대신 단정한 것으로 설명했다.
실제 scenario.ai_character는 바로 발표하다 멈추고 앉은 친구다. 자기 상태를 말한 대사와 타인 감정 단정을 혼동했다.
REINFORCES_INCORRECT_ANSWER 코드를 출력했지만 educationally_correct=true여서 코드와 검사 항목도 모순됐다.
기존 검증기가 명시적으로 검사하는 코드/check 연결은 일부뿐이므로 이 모순은 기술적으로 수용됐다.
이를 정확한 후보 검수라고 기록하지 않는다. 이번 승인 범위 밖에서 검증 규칙을 추가해 재호출하지 않았다.

한편 후보의 지원 수준은 S0이고 ‘멍해졌어’ 같은 직접 상태 표현이 있다.
난이도/지원 불일치 거절 자체는 별도 검토할 수 있으므로, 이 고정 후보가 반드시 PASS여야 한다고 결론내리지 않는다.
문제는 후보 거절 여부만이 아니라 거절 이유의 출처·역할·검사 항목이 일관되는지다.

최종 조합 결과는 safe_to_send=false, REGENERATE, retry_target=RESPONSE_GENERATION,
critical_failure_count=1이다. 분석 관찰·활동 승인은 유지됐다. 실제 사용자 전달·저장·재생성은 수행하지 않았다.
분석 판단을 후보 결과가 덮어쓰지 않는 구조는 확인했지만 후보 의미 판단의 정확성까지 확인된 것은 아니다.
