# 역할극의 복수 목표 관찰과 활동 달성 종료

## 적용 기준

- 세부 목표는 고정 순서의 단계가 아니다. 한 발화에서 여러 승인 목표의 증거를 관찰하고, 아직 질문하지 않은 목표의 근거도 사용할 수 있다.
- 활동 목표는 이번 발화와 이전 확정 관찰을 함께 판단한다. 전체 세부 목표 목록의 일괄 통과를 추가 완료 조건으로 만들지 않는다.
- 현재 질문 목표의 학습 상태와 활동 전체 달성은 구분한다. 일부 근거가 과거 턴에 있거나 다른 목표를 먼저 표현해도 승인된 활동 목표를 충족할 수 있다.
- 서로 다른 사건·감정 표현을 합쳤다는 이유만으로 아동이 인과관계까지 표현했다고 만들지 않는다. 도움·정답 제공 이력과 독립 도달의 기존 구분도 유지한다.

근거: `roleplay-goal-observation-design.md`의 적용 기준과 2026-11-09 사용자 확인. 한 번에 여러 목표를 표현하거나 여러 턴에 나누어 표현하는 경우를 모두 허용한다.

## 변경한 실행 흐름

1. 기존 분석 호출이 모든 승인 기준의 관찰 상태와 활동 판정을 제안한다. 근거 없는 달성·외부 목표 참조 등 기존 출력 검사는 유지한다.
2. `RoleplayActivityCompletion`은 유효한 분석의 활동 판정이 `ACHIEVED`일 때 다음 전략을 현재 목표·현재 지원 수준의 `CLOSE_ROLEPLAY`로 연결한다. 학습 상태·목표별 관찰·활동 판정·참조 근거는 바꾸지 않는다. `NOT_ASSESSABLE`과 활동 달성의 충돌은 거절한다.
3. 후보 생성은 연결된 분석으로 마무리 응답을 만든다. 독립 검수는 달성 근거와 마무리 대사를 여전히 검사한다. 전략 연결을 근거의 승인으로 취급하지 않는다.
4. 검수가 잘못된 달성을 반려하면 기존 재분석 경로를 따른다. 정상 분석에서 대사만 문제가 있으면 기존 재생성 경로를 사용할 수 있다. 재시도 상한과 공유 60초 예산을 바꾸지 않는다.
5. 저장 단계에서는 활동 달성 또는 기존 턴 상한 종료에 `CLOSE_ROLEPLAY`·`CLOSING`이 모두 있어야 한다. 불일치하면 턴·관찰·보상·기록을 롤백한다. 정상 완료·발화 삭제·재전송 처리의 기존 트랜잭션을 재사용한다.

목표별 관찰과 확정 이력 공급은 기존 구조를 재사용한다. 추가 LLM 호출·DB 테이블·공개 API 필드는 없다. 분석이 `IN_PROGRESS`이면 긍정 관찰 수만 세어 서버가 달성으로 바꾸지 않는다. 승인된 활동 목표에 대한 의미 판단과 독립 검수는 계속 필요하다.

## 프롬프트와 버전

캐릭터 분석·검수의 공통 정책 및 간결/기존 프롬프트에서 모든 목표의 일괄 통과와 현재 목표 상태를 활동 달성의 필수 조건처럼 읽을 수 있는 표현을 정리했다.

| 구간 | 버전 |
|---|---|
| 기본 분석 프롬프트 식별자 | `roleplay-cause-analysis/v6` |
| 간결 캐릭터 분석 | `roleplay-cause-analysis-character/v2` |
| 기존 캐릭터 검수 | `roleplay-response-evaluation-character/v14` |
| 간결 캐릭터 검수 | `roleplay-response-evaluation-character/v15` |

출력 스키마·저장 계약은 변경하지 않았다. 분석 프롬프트의 기본 식별자는 기존 캐릭터 지시 결합 변경을 포함해 갱신했다. 서버의 달성→마무리 연결과 저장 검사는 역할극 공통 경로에 적용한다.

## 검증 범위와 한계

새 회귀 검사는 한 발화의 복수 관찰, 이전·현재 근거의 참조 보존, 현재 질문 목표의 부분 이해와 활동 달성 구분, 근거 없는 달성의 독립 검수 반려, 정상 세 호출 경로, 판정 불가 입력의 달성 거절을 확인한다. 실제 PostgreSQL 완료 검사는 달성인데 마무리가 아닌 응답을 저장하지 않는지 확인한다.

가짜 AI 응답을 사용하는 검사는 서버의 연결·검증·저장 규칙을 검증한다. 실제 모델의 교육적 판단 정확도나 지연 개선을 입증하는 결과는 아니다. 기존 통합 테스트의 합성 달성 응답도 마무리 전략·대사를 사용하도록 맞췄다.

2026-11-09 Dev의 시간 초과 요청은 재분석 반복이 확인됐지만 원문 파일이 없어 세부 반려 사유를 확인하지 못했다. 이 변경으로 해당 실제 사례가 해결됐다고 확정하지 않는다.

## Dev에서 이어서 확인할 것

1. 원문 진단이 활성이고 수집 시간·공유 요청 수 한도가 남았는지 먼저 확인한다. 설정 변경은 담당자의 배포 절차로 적용한다.
2. 실제 승인된 활동 목표·난이도를 확인하고 한 세션을 처음부터 기록한다. 각 입력의 `X-Trace-Id`와 최종 활동 상태를 함께 남긴다.
3. 한 발화로 여러 목표를 표현하는 경우, 여러 턴에 나누는 경우, 현재 질문과 다른 목표를 먼저 표현하는 경우를 관찰한다. 사용하지 않은 미래 대사를 이전 판정의 근거로 쓰지 않는다.
4. 이번/이전 관찰, 활동 판정, 다음 전략, 독립 검수, 저장·화면 완료 결과를 대조한다. 서버가 생성 전에 연결한 분석은 생성·검수 요청에서 확인하고 모델이 반환한 원래 분석과 구분한다.
5. 실제 모델이 근거를 놓쳐 `IN_PROGRESS`로 남기는 경우에는 이 변경의 서버 연결만으로 해결되지 않는다. 승인 기준·컨텍스트 전달·분석·독립 검수 중 문제가 있는 경로를 특정한다.

이 문서 작성 중 실제 외부 AI 호출·push·배포·PR 생성은 수행하지 않는다. 프론트엔드 코드는 수정하지 않는다. 공개 API 변경은 없지만 배포 후 화면이 기존 활동 상태 조회의 `COMPLETED`를 반영하는지는 종단 확인이 필요하다.

## 남은 정책·관측 작업

- S3 정답 제공 뒤 더 유도할 목표가 없는 경우의 종료·보상은 독립 달성으로 바꾸지 않으며, 별도 정책 확인 없이 새로운 완료 사유를 추가하지 않는다.
- 목표 판정의 세션별 보고서와 저장·완료 분기를 연결하는 관측 기능은 별도 구현 범위다. 현재 원문 수집 한도·컨테이너 교체 때문에 자료가 없으면 과거 판정의 세부 이유를 복구할 수 없다.
- 실제 대화 원문과 수집 보고서는 Git에 포함하지 않는다.
