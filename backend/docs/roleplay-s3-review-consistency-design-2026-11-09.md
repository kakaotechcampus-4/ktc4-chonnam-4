# S3 생성·검수 정합성 수정 설계

상태: 2026-11-09 사용자 승인 후 구현·로컬 검증 완료. 실제 모델 재측정·push·배포는 미실행이다. 추가 성능 변경은 별도 범위다.

## 1. 해결할 문제와 확인한 근거

Dev 배포 `ccb95d8`, GPT-6 Luna, reasoning `low`에서 아동 입력 `도와줘야해?`가 약 60초 뒤 재입력 경로로 끝났다.

직전 캐릭터 대사는 `응, 안녕… 뚜껑이 꿈쩍 안 해서 풀을 못 바르고 있어.`였다.

| 순서 | 처리 | 시간 | 결과 |
|---|---|---:|---|
| 1 | 입력 판정 | 1.442초 | 유효 |
| 2 | 원인 분석 | 12.274초 | 유효, ADVANCE_GOAL·S3 |
| 3 | 후보 1 생성 | 5.611초 | 유효, GUIDING_QUESTION·S3 |
| 4 | 후보 1 검수 | 15.368초 | REGENERATE, ANSWER_TOO_DIRECT 등 |
| 5 | 후보 2 생성 | 5.713초 | 유효, GUIDING_QUESTION·S3 |
| 6 | 후보 2 검수 | 8.716초 | REANALYZE, 발화 해석 거절 |
| 7 | 원인 재분석 | 10.365초 | 유효, 전략·목표·S3 유지 |
| 8 | 후보 3 생성 | 0.341초 | 남은 턴 예산 소진 |

첫 검수는 원래 분석을 승인했고, 두 번째 검수는 같은 분석을 거절했다. 원래 분석에는 ‘물었다’는 근거와 ‘도움이 필요하다는 말을 했다’는 해석이 함께 있었다. 따라서 단순히 두 번째 검수가 틀렸다고 확정할 수 없다.

현재 코드에서 확인한 사실:

- 생성 지침은 일반 S3 설명에서 ANSWER_REVEAL을 요구하지만, PROBE_ACTION·ADVANCE_GOAL 설명에서는 GUIDING_QUESTION을 지정한다.
- 후보 파서는 분석과 후보의 지원 수준 일치를 검사하지만, S3·전략·응답 유형의 조합은 일반적으로 강제하지 않는다.
- 검수 지침의 ANSWER_TOO_DIRECT는 ‘S3가 아닌데 답을 직접 제공함’ 또는 ‘마스코트가 정답을 제공함’이다. 모델이 이 근거를 따랐는지는 서버가 별도로 검사하지 않는다.
- RoleplayGoalResponseHistory와 RoleplayGoalObservationHistory는 response_type=ANSWER_REVEAL을 정답 제공 이력에 반영한다. 잘못된 응답 유형은 후속 학습 판단에 영향을 줄 수 있다.
- JSON 구조상 정상인 REGENERATE·REANALYZE도 VALID로 기록된다. 이번 주요 지연은 이러한 의미 판정에 따른 추가 호출이었다.

후보 1을 반드시 통과시켜야 한다는 결론은 아니다. 목표 행동의 주체, 실제 목표 기준, 반복 여부 등은 여전히 검수해야 한다. 첨부한 발췌에는 승인된 목표 기준 전체가 없으므로 후보의 교육적 정답 여부는 확정하지 않는다.

## 2. 유지할 확정 기획

`03_MVP_기능_명세.md`의 역할극 지원 정책을 따른다.

- S3 정답 제공과 아동의 독립 달성을 구분한다.
- 목표에는 고정 순서가 없다. 현재 목표는 질문의 초점이다.
- 기술 오류는 지원 상승·학습 실패의 근거가 아니다.
- 지원 이력은 실제 전달이 확정된 후보를 기준으로 갱신한다.

S3는 해당 목표의 직접 표현을 허용하는 수준이지, 목표 행동의 주체를 바꾸거나 모든 목표의 답을 무제한 제공해도 된다는 뜻이 아니다.

## 3. 제안하는 작은 구현 범위

### A. 서버에서 생성·검수의 공통 기준 구성

캐릭터 역할극에 한정해 작은 불변 값 객체 `CharacterResponseContract`를 추가한다.

- 검증·지원 보정을 거친 분석의 target_micro_goal_id
- 보정 후 recommended_support_level
- 전략과 지원 수준으로 결정한 expected_response_type
- 해당 목표의 직접 답 제공 허용 여부: S3에서 true
- 마스코트 정답 제공 허용 여부: false

목표의 내용·행동 주체는 승인된 시나리오의 기존 기준을 사용한다. 서버가 자연어에서 새로운 교육 정책을 추측하거나 목표 순서를 만들지 않는다.

이 값을 RoleplayPromptFactory에서 생성·검수 양쪽에 동일하게 넣고 후보 파서도 같은 값을 사용한다. 모델의 원래 지원 제안이나 후보가 주장한 support_level을 기준으로 허용 범위를 다시 계산하지 않는다.

응답 유형 제안:

| 캐릭터 전략 | S0~S2 | S3 |
|---|---|---|
| PROBE_EVENT·PROBE_EMOTION·PROBE_CAUSE·PROBE_ACTION·ADVANCE_GOAL | GUIDING_QUESTION | ANSWER_REVEAL |
| 그 외 전략 | 현재 전략별 유형 유지 | 현재 전략별 유형 유지 |

이는 일반 S3 지침과 정답 제공 이력의 의미를 맞추는 제안이다. S3인데 GUIDING_QUESTION인 후보를 서버가 조용히 ANSWER_REVEAL로 바꾸지는 않는다. 잘못된 조합은 생성 출력 실패로 처리하고 기존 재시도 안에서 구체적인 수정 조건을 전달한다.

실제 대사가 해당 목표의 답을 제공하는지는 의미 검수가 담당한다. 유형만 ANSWER_REVEAL로 맞춘 간접 단서를 자동으로 정답 제공으로 승인하지 않는다.

### B. ‘너무 직접적’ 거절에 구조화된 근거 요구

기존 검수 JSON에 작은 nullable 필드 `answer_directness_violation`을 추가한다.

ANSWER_TOO_DIRECT가 있을 때는 다음을 필수로 받는다.

- reason: TARGET_ANSWER_BEFORE_S3 또는 MASCOT_ANSWER_REVEAL
- speaker_role: DIALOGUE 또는 HINT
- quote: 해당 후보의 실제 대사 또는 마스코트 힌트에서 인용한 연속 구절

서버 검증:

1. TARGET_ANSWER_BEFORE_S3는 해당 목표의 적용 수준이 S0~S2일 때만 허용한다. S3에서는 허용하지 않는다.
2. MASCOT_ANSWER_REVEAL은 실제 mascot_hint가 있고 인용이 그 힌트에 존재할 때만 허용한다.
3. reason과 speaker_role, 실패 코드, difficulty_appropriate의 조합이 일치해야 한다.
4. 코드가 없으면 근거 필드는 null이어야 한다.
5. 기존 안전·입력 확인 우선 경로는 일반 후보 거절 근거를 강요하지 않도록 별도로 유지한다.

요청별 JSON Schema에서 가능한 사유를 좁히고 수신 후 같은 조건을 검사한다. 스키마에 맞더라도 인용의 위치·지원 수준과 모순되면 검수 출력 실패로 처리한다.

잘못된 검수는 같은 후보의 검수 재시도로 보낸다. 실패 코드를 지우거나 checks를 true로 바꾸거나 PASS로 덮어쓰지 않는다. 같은 60초 예산과 기존 검수 시도 상한 안에서만 재시도한다.

다른 목표의 답 노출이나 행동 주체 오류를 무조건 허용하지 않는다. 그런 문제는 실제 승인 기준과 대사를 대조해 기존 목표 정합성·대화 정합성 등의 해당 검사로 판단한다. 이번 변경에서 목표별 공개 순서나 새 금지 정책을 만들지 않는다.

이 구조는 모델의 의미 판단 자체가 참임을 증명하지 않는다. S3인데 ‘S3 이전 답 노출’이라고 거절하는 모순, 존재하지 않는 마스코트의 정답 노출 등 서버가 판별할 수 있는 오류를 차단한다.

### C. 질문 해석 기준 정리, 재분석은 유지

분석·검수 지침에 같은 사례를 넣어 사실과 추정을 구분한다.

- `도와줘야해?`에서 도움 여부를 물었다는 사실과 도움 필요성을 확정적으로 진술했다는 해석을 구분한다.
- 물음표만으로 QUESTION_BACK을 강제하지 않는다. 맥락상 질문 형태의 답변도 학습 근거가 될 수 있다.
- 후보를 바꿨다는 이유만으로 원래 아동 발화의 의미를 바꾸지 않는다. 분석 검수는 아동 발화·이전 대화·승인 기준으로 판단한다.
- 기존 분석에 실제 오류가 있으면 REANALYZE를 유지한다. 첫 SUPPORTED를 캐시해 이후 거절을 막지 않는다.

이 부분은 자연어 의미 판단이므로 서버의 문자열 규칙으로 확정하지 않는다. 공통 계약·구조 검증만으로 이번 재분석까지 없어질 것이라고 약속하지 않는다.

## 4. Spring AI 적용 방식

- 기존 검수 호출의 provider-native JSON Schema 경로를 재사용한다. 요청별 enum과 nullable 근거 구조를 그 스키마에 추가한다.
- 수신 후 구조 검증과 업무 규칙 검증을 모두 통과해야 유효한 검수로 인정한다.
- StructuredLlmExecutor·EvaluationRetry의 기존 오류 전달 경로를 확장한다.
- 별도의 StructuredOutputValidationAdvisor 재시도 루프는 추가하지 않는다. 현재 실행기의 호출 수·시간 예산 밖에서 숨은 재시도가 생기지 않도록 한다.
- Spring AI 업그레이드와 ChatClient 전환은 이번 수정 범위에 넣지 않는다. 현재 프로젝트는 2.0.1이며 아래 웹 문서는 현재 2.0.2이므로, 문서 예제를 그대로 복사하지 않고 설치된 API를 기준으로 구현한다.

공식 근거:

- [Provider-Native Structured Output](https://docs.spring.io/spring-ai/reference/api/structured-output/native.html): API 수준 스키마 제약과 제공자별 지원 한계.
- [Schema Validation & Self-Correction](https://docs.spring.io/spring-ai/reference/api/structured-output/validation.html): 수신 검증, 구체적인 실패 조건을 전달하는 제한된 재시도.

| 위치 | 변경 |
|---|---|
| ai/application/prompt/CharacterResponseContract.java 신규 | 적용 수준·목표·전략별 응답 유형의 공통 계산 |
| RoleplayPromptFactory.java | 생성·검수에 동일 계약 전달, 버전 갱신 |
| RoleplayOutputParsers.java 및 생성 재시도 피드백 | 유형 조합 검증, 자동 의미 변경 없이 수정 조건 전달 |
| EvaluationOutput.java·EvaluationOutputSchema.java·EvaluationRetry.java | 직접성 거절의 근거 필드, 요청별 스키마, 수신 검증·피드백 |
| 캐릭터 생성·분석·검수 프롬프트 및 검수 출력 계약 | S3 유형 충돌 해소, 발화 해석 기준 통일 |
| 관련 파서·스키마·프롬프트·재시도·학습 이력 테스트 | 아래 회귀 검증 |
| 검수 계약 문서 | 새 내부 모델 출력 버전·실험 조건 기록 |

검수 출력 evaluation-output/v5는 v6로 올린다. 캐릭터 생성·분석·검수 프롬프트도 변경된 버전을 기록한다. 외부 HTTP 응답·DB 스키마는 변경하지 않는다. 과거 확정 이력을 소급해서 다시 분류하지 않는다. 프론트엔드 수정은 예상하지 않는다.

## 6. 검증 순서와 완료 기준

1. **외부 AI 없는 회귀 검사**
   - S0~S3 × 다섯 학습 전략의 유형 조합을 검사한다.
   - S3/GUIDING_QUESTION은 생성 단계에서 거절하고, 구체적인 수정 조건을 전달한다.
   - S3 캐릭터 직접 표현만으로 ANSWER_TOO_DIRECT를 내린 검수는 무효 처리한다.
   - S0~S2의 직접 답 제공, 마스코트 정답 제공의 유효한 거절은 유지한다.
   - 잘못된 인용·없는 힌트·코드와 근거의 충돌을 거절한다.
   - 다른 목표·행동 주체·안전 문제는 별도로 거절할 수 있고, PASS 요구 조건은 유지된다.
   - 실제 분석 오류의 REANALYZE와 안전·입력 확인 우선 경로를 보존한다.
   - 검수 재시도 횟수와 공유 예산이 늘지 않는지 검사한다.
   - 전달 확정된 ANSWER_REVEAL만 정답 제공 이력에 반영되며, 아동의 독립 달성과 구분되는지 기존 이력 검사를 연결한다.
2. **관련 검사 후 전체 필수 검사 한 번**
   - 새 변경·실패가 없으면 같은 검사를 반복하지 않는다.
   - 이 검사는 코드의 제약·분기 검증이며 실제 모델의 교육적 판단 품질 검증과 구분한다.
3. **사용자와 실제 모델 실험 조건 확정 후 소량 재측정**
   - 같은 직전 대화·아동 입력·목표 기준·지원 이력을 재현한다. 문장만 같은 새 세션은 동일 조건으로 취급하지 않는다.
   - 승인된 목표 기준 전체를 확인해 행동 주체와 실제 정답을 사람이 먼저 판정한다.
   - 실제 모델 실행은 승인 후 진행한다. 설계 중 유료 호출은 하지 않는다.
   - 기존 60초 결과와 새 결과의 전달 여부, 단계별 호출 수·시간, 직접성 거절 근거, 재분석 사유, 원문 품질을 비교한다.
   - 적은 표본으로 p95·안정성·모델 우열이나 속도 개선을 확정하지 않는다.
4. **커밋·배포 단계**
   - 코드 수정 전 이번 설계를 승인받는다. 공식 develop 반영 상태와 작업 트리를 확인하고 기존 사용자 변경을 보존한다.
   - 검증 후 목적별 커밋과 PR 본문 초안을 준비한다.
   - 공식 upstream의 refactor/ 브랜치로 push하기 직전에 별도 승인을 받는다. PR 작성은 사용자가 한다.
   - Dev 배포 후 같은 입력으로 관측한다. 배포나 AWS 설정 변경을 임의로 수행하지 않는다.

성공 기준은 ‘무조건 PASS’가 아니다. 생성 계약과 검수 근거의 명확한 모순을 서버가 차단하고, 실제 의미 오류는 계속 거절하며, 정답 제공 이력을 올바르게 남기는 것이다. 재시도 감소와 처리 시간 개선은 실제 모델 재측정으로 확인한다.

## 7. 서비스 전반의 지연 개선 제안

이 절은 추가 설계 제안이며 앞 절의 구현 승인을 받았다는 뜻이 아니다. 판정 오류 수정과 성능 변경을 구분해 비교한다.

### 현재 관측으로 확인한 범위

- 이전 캐릭터 P1 세 건은 분석·생성·검수를 각각 한 번 수행해도 19.137~22.218초, 평균 21.161초였다. 실제 HTTP 입력 판정·TTS·저장은 이 실행기 범위에 포함되지 않는다.
- 이번 Dev 요청은 입력 판정부터 첫 후보 검수까지 외부 호출 합계만 34.695초였다. 이 시점은 PASS 시점이 아니라 첫 거절 판정 시점이다.
- 이번 요청의 전체 LLM 호출 구간은 약 59.834초/60.010초였다. 큐 대기는 0ms, 컨텍스트 준비는 35ms였다. 이 한 요청에서 DB·스레드 큐가 주된 병목이었다고 보기는 어렵다. 동시 부하 상황까지 검증한 것은 아니다.
- 제공자 메타데이터 기준 첫 분석 입력은 15,602토큰, 첫 검수 입력은 18,946토큰이었다. 이전 P1의 분석은 7,137~8,550, 검수는 10,011~10,106이었다. 입력·이력·시나리오 등이 달라 직접적인 성능 비교나 인과 판단에는 사용할 수 없다.
- 검수 입력에는 goal_observation_context, goal_evidence_so_far, observation_tasks, current_goal_assessment가 함께 있다. 서로 겹치는 근거가 있으나 각 필드는 범위 검증과 근거 참조 역할도 하므로 바로 삭제하지 않는다.
- 캐릭터 검수 시스템 지침에는 약 7,245자의 캐릭터 규칙과 약 4,491자의 출력 계약이 합쳐진다. 문자 수는 토큰 수와 다르며 이 값만으로 병목을 확정하지 않는다.
- 최근 대화에는 이미 MAX_DIALOGUE_LINES 제한이 있다. 대화 전체를 무제한 전송한다고 진단하지 않는다. 확정 관찰·지원 이력의 전달량은 별도로 확인한다.

### 우선순위

| 순서 | 작업 | 검증할 결과 | 범위 |
|---|---|---|---|
| 1 | 앞 절의 생성·검수 모순 수정 | 불필요한 재생성·재분석 감소, 잘못된 후보 거절 유지 | 우선 구현 제안 |
| 2 | 단계별 입력 구성·출력 길이 조사 | 지침·대화·관찰·지원 근거·스키마·출력 설명의 크기와 증가 원인 파악 | 같은 검증 과정에 포함할 읽기·집계 작업 |
| 3 | 중복 입력 표현과 장황한 출력 설명 축소 | 동일한 근거·결정·안전 검사 보존, 토큰·시간 감소 | 조사 후 별도 작은 변경으로 설계·승인 |
| 4 | 단계별 모델·추론 설정 비교 | 같은 검증 세트에서 품질·재시도·총시간·비용 비교 | 별도 실험 승인 후 수행 |
| 5 | 실제 HTTP의 TTS·저장 및 동시 부하 관측 | 정상 PASS 요청의 전체 대기와 부하 시 큐·DB 점유 파악 | 위 개선 이후 관측 |

단계별 입력 조사에서는 원문을 지표 태그에 넣지 않는다. 로컬 합성 케이스와 제한된 Dev 진단에서 구성별 크기·목록 개수만 집계한다. 공급자가 제공한 토큰 사용량과 로컬 문자 수를 구분한다.

축소 후보는 동일 사실의 중복 직렬화, 반복된 계약 설명, 불필요하게 긴 사유다. 승인 목표 기준, 사실·금지 추론, 안전 판단, 독립 달성/정답 제공 구분, 근거 참조는 보존한다. 전체 이력을 LLM으로 다시 요약하는 추가 호출은 이번 단계에서 도입하지 않는다.

모델 경로는 AiRouteProperties와 OperationRoutingLlmProvider가 이미 지원하지만, application.yml의 명시적 환경변수 연결은 현재 리포트 생성·검수 위주다. 역할극 단계별 경로를 운영에서 쓰려면 환경변수·배포 전달 설정을 별도로 연결하고 시작 로그로 실제 적용을 확인해야 한다. 기존 기본 AI_MODEL 변경과 혼동하지 않는다.

reasoning 설정을 더 낮추거나 다른 모델을 사용하는 실험은 Elice의 해당 모델·엔드포인트가 옵션을 지원하는지 확인한 뒤 한다. 형식 통과뿐 아니라 의미 판단과 잘못된 후보 거절을 함께 비교한다. 출력 상한을 무작정 줄이면 과거 LENGTH·빈 출력 문제가 재발할 수 있다.

### 호출 구조의 제약과 개선 해석

분석 결과로 생성하고, 생성한 후보를 검수하므로 세 호출을 그대로 동시에 실행할 수 없다. 입력 판정과 안전 경로도 임의로 생략하지 않는다. 미검수 대사를 스트리밍해 사용자에게 전달하는 방식은 현재 승인 후 전달 계약과 충돌하므로 이번 제안에 넣지 않는다. 분석·생성 통합은 호출 수를 줄일 수 있지만 독립 검수의 신뢰와 계약을 다시 검증해야 하는 별도 구조 변경이다.

성능 비교에는 전체 시간뿐 아니라 첫 후보까지 걸린 시간, 첫 검수까지 걸린 시간, 재시도 추가 시간, 단계별 호출 수·토큰, 최종 전달·복구 여부, TTS 시간을 나란히 본다. 실패가 빨라진 것을 속도 개선으로 보고하지 않는다.

먼저 서비스가 요구하는 응답 시간의 시작·끝을 정한다. 예를 들어 ‘텍스트 제출부터 검수 완료 텍스트 표시’와 ‘음성 재생 가능’은 다른 목표다. 목표값은 사용자·팀이 정하며 기존 60초 제한은 응답 속도 목표로 간주하지 않는다.

위 측정 방향은 [Spring AI Observability](https://docs.spring.io/spring-ai/reference/observability/index.html)의 호출 시간·토큰·모델 정보와 연결된다. 기존 요청별 관측으로 시작하고 대시보드나 새 관측 프레임워크 설치 자체를 먼저 목표로 삼지 않는다.
