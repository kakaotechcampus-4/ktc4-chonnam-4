## 1. 제안하는 S0 단서 수용 기준

S0는 아동이 단서를 보고 스스로 반응할 여지를 주는 단계로 취급한다. 현재 맥락에서 다음 목표와 연결되는 캐릭터의 소리·행동 단서가 하나 이상 있으면 목표 연결을 충족할 수 있다. 감정 이름·이유 해설·명시적 질문·한 가지 감정으로의 유일한 추론은 요구하지 않는다. 더 좋은 표현으로 고칠 수 있다는 선호와 전달을 차단할 실제 결함을 구분한다.

| P1 대사 | 제안하는 목표 단서 판단 | 이유 |
|---|---|---|
| 응… (손을 만지작거리며 작게 숨을 내쉰다) | 충족 | 발표 후 맥락에서 관찰할 수 있는 몸·소리 단서가 있음 |
| 응. | 부족 | 다음 감정 목표를 살펴볼 새로운 단서 없이 동의만 함 |
| 정답을 맞혀 봐. 발표할 때 내 감정은 무엇일까? | 별도 역할 검사에서 거절 | 단서의 유무와 관계없이 교사식 문답임 |
| 나 발표하기 싫어서 일부러 멈췄어. | 별도 시나리오 검사에서 거절 | 승인되지 않은 의도·원인을 추가함 |

첫 행은 승인받을 기준 사례다. 아직 전문가가 확정한 정답 자료로 취급하지 않는다. 특정 문장을 서버의 PASS 목록에 넣거나 운영 프롬프트에 이 실험의 정답으로 삽입하지 않는다. 다른 맥락에서 손을 만지작거린다는 사실만으로 불안이라고 단정하지 않는다.

S0 단서 충족은 해당 후보의 목표 연결에 관한 판단이다. 아동의 목표 달성·독립 수행을 뜻하지 않으며 안전·지원 적정성·대화 정합성 등 다른 검사를 생략하지 않는다. S1~S3의 도움 강도를 이 설계에서 다시 정의하지 않는다.

## 2. 목표 단서 검수를 구조화

일반 캐릭터 학습 전략(PROBE_EVENT/EMOTION/CAUSE/ACTION, ADVANCE_GOAL)에 대해 기존 검수 출력에 작은 `target_cue_review`를 추가한다. 안전·입력 의미 확인 우선 경로와 종료/전환 등 이 검수의 대상이 아닌 전략은 null로 둔다. S0의 세부 수용 기준을 우선 명시하고 다른 지원 수준은 기존 정책을 따른다.

제안 형태:

```json
{
  "target_micro_goal_id": "서버가 고정한 다음 목표 ID",
  "verdict": "SUPPORTED",
  "reason_code": "MATCHED_BEHAVIOR_CUE",
  "quote": "손을 만지작거리며 작게 숨을 내쉰다"
}
```

허용 사유는 작게 유지한다. 긍정은 MATCHED_BEHAVIOR_CUE, MATCHED_SOUND_CUE, MATCHED_CHARACTER_EXPRESSION, 거절은 NO_TARGET_CUE, WRONG_TARGET_CUE, NO_REACTION_TO_INPUT, 정보 부족은 INSUFFICIENT_CONTEXT로 구분한다. 실제 적용 가능한 사유는 지원·전략에 맞춰 제한하며, 감정 이름의 직접 표현이 허용되는지는 기존 지원·직접성 검사에서 별도로 확인한다.

서버가 검사할 내용:

- 목표 ID가 서버에서 지원 보정한 next_strategy.target_micro_goal_id와 같은가. 현재 평가 초점의 ID를 잘못 복사하지 않았는가.
- 인용이 실제 후보 text의 비어 있지 않은 연속 구절인가. 아동 발화·생성되지 않은 문장·마스코트에서 가져오지 않았는가.
- NO_TARGET_CUE로 후보 전체의 단서 부재를 주장하면 quote가 후보 text 전체인가. 일부 구절만 인용해 다른 단서를 무시하는 자료를 받지 않는다.
- 긍정 사유와 SUPPORTED, 거절 사유와 UNSUPPORTED가 일치하는가. INSUFFICIENT_CONTEXT에는 기존 판단보류 경로를 적용하고 근거 인용은 null로 둔다.
- 목표 연결을 SUPPORTED로 검수하면서 analysis_response_consistent=false 또는 ANALYSIS_RESPONSE_MISMATCH로 거절하지 않는가. UNSUPPORTED이면 해당 검사 false와 실패 코드가 함께 있는가.
- 일반 학습 경로에서 목표 연결 실패 코드·검사만 남기고 이 검수를 생략하지 않았는가.

모순·잘못된 인용은 새 고정 오류 분류로 같은 후보를 다시 검수한다. 기존 검수 시도 상한·공유 예산 안에서 처리하고, PASS로 변환하거나 바로 새 후보를 만들지 않는다. 다른 유효한 거절은 기존 복귀 위치와 우선순위를 유지한다.

이 검증은 목표·인용·사유·판정의 정합성을 보장한다. 모델이 행동의 의미를 잘못 분류하는 것까지 서버가 증명하지는 못한다. 정책 기준과 사례의 반복 관측이 함께 필요하다. 후보가 행동을 포함했다는 정규식만으로 PASS시키지 않는다.

## 3. 재생성 required는 서버가 구성

현재 캐릭터 모델 출력의 revision_instruction은 keep/change/avoid/required 네 개의 자유 문자열 배열이다. 이 중 required를 모델 출력에서 제거하고, 캐릭터 모델용 스키마에는 keep/change/avoid만 받도록 한다. 제공자가 required나 다른 추가 속성을 보내면 native 스키마·수신 검증으로 거절한다. 안내자용 기존 출력 계약은 이번 범위에서 유지한다.

수신 스키마 검증을 마친 뒤 서버가 적용 지원·목표·역할 계약에서 required를 복원한다. 예를 들어 역할 유지, 해당 목표 단서, 적용 지원 유지, 승인 사실 준수, 교사식 감정 맞히기 금지를 고정된 짧은 한글 조건으로 구성한다. 목표 ID·지원 수준 등은 기존 구조화 계약과 연결하며 모델이 덮어쓰지 못하게 한다. 조건을 과도하게 반복하지 않는다.

내부 RevisionInstruction과 기존 HTTP/DB의 keep/change/avoid/required 형태는 유지한다. 서버가 복원한 내부 수정 조건을 GenerationRetry에 전달하므로 생성기는 기존 인터페이스를 계속 사용한다. 모델의 keep/change/avoid는 서버 필수 조건 안에서만 사용하는 참고 자료다. 모든 자연어 수정 지시의 충돌이 사라졌다고 보장하지 않는다.

이 방식은 관측된 검수 필드명이 required로 넘어가는 경로를 직접 차단한다. 단순 금지 단어 치환, 내부 필드명 목록을 늘려가며 자유 텍스트를 수정하는 방식은 사용하지 않는다.

## 변경 예상 범위

- CharacterResponseContract: S0 단서 정책 버전 또는 식별자 전달. 목표·지원은 기존 값 재사용.
- 새 TargetCueReview 및 EvaluationOutputSchema/EvaluationOutput: 요청별 native 제약, 인용·사유·검사 연결. 제공자 출력 스키마·영향받는 프롬프트 버전 갱신.
- RoleplayOutputParsers/EvaluationRetry: 캐릭터 모델용 수정 조건을 내부 형태로 복원하고 검수 모순을 기존 한도 안에서 피드백.
- RoleplayPromptFactory: 생성과 검수가 같은 정책을 보고 서버가 만든 required를 생성에 전달하도록 연결.
- 캐릭터 생성·검수 지침, 계약 회귀 검사, 고정 후보 진단 실행기와 백엔드 계약 문서.

새 DB 테이블·마이그레이션·캐시·worker 구조·모델 교체·timeout 확대·재시도 추가는 없다. 프론트엔드 수정은 필요 없을 것으로 예상하며, 내부 수정 조건을 복원해 외부 계약을 유지하는지 검사한다. 프롬프트 전체 재작성이나 관측 전반의 리팩터링은 하지 않는다.

## 구현과 검증 순서

1. 사용자 승인으로 위 S0 수용 기준과 기준 사례를 확정한다. 확정 전 현재 A 기대값을 바꾸거나 과거 보고서를 덮어쓰지 않는다.
2. 목표 단서의 바인딩·인용·사유·검사 정합성과 서버 required 복원을 로컬 검사로 구현한다. 정상 단서/무단서, 잘못된 목표·인용, 모순된 PASS, 안전 우선, 안내자 경로, 상한 소진을 확인한다. 가짜 모델 분류를 실제 의미 정확도의 증거로 쓰지 않는다.
3. 변경 경로의 관련 검사 후 필요한 전체 회귀를 한 번 마무리한다. 입력·출력 길이를 비교하고 추가 필드·같은 후보 재검수 횟수도 확인한다. 스키마 필드 추가가 오히려 출력 토큰을 늘릴 수 있음을 측정한다.
4. 별도 실제 호출 승인 후 고정된 네 후보를 각각 한 번 평가한다: 기준 행동 단서, 단순 맞장구, 교사식 문답, 금지 추론. 최대 4회·공유 60초·자동 재시도 없음. 정확한 이유의 거절과 정상 승인을 함께 집계한다.
5. 첫 결과가 기준과 일치하면 동일 기준 후보의 추가 반복과 다른 맥락을 작은 범위로 별도 측정한다. 한 번의 성공으로 일관성·일반적 품질을 확정하지 않는다. 근거 없이 반복 호출하거나 통과할 때까지 수정하지 않는다.

실제 Dev의 `도와줄까` 실패 맥락과 전체 HTTP 지연 검증은 후속 단계다. 이번 설계의 승인으로 실제 AI 추가 호출·push·배포가 승인되는 것은 아니다.

## Spring AI 적용 방식과 한계

[Provider-Native Structured Output](https://docs.spring.io/spring-ai/reference/api/structured-output/native.html)에서 설명하는 API 수준 스키마 제약과 [Schema Validation & Self-Correction](https://docs.spring.io/spring-ai/reference/api/structured-output/validation.html)의 수신 검증·오류 피드백 원리를 기존 구현에서 재사용한다. 공식 문서 확인 버전은 2.0.2이며 프로젝트 2.0.1을 업그레이드하지 않는다.

기존 JSON Schema validator와 턴 오케스트레이터가 업무 정합성을 검사한다. 새 Advisor의 중첩 재시도나 추가 판정 에이전트를 도입하지 않는다. 위 문서의 스키마 검증을 감정 단서의 의미가 항상 올바르게 분류된다는 보장으로 해석하지 않는다.
