# Dev 서버 요청별 원문 진단 설계

상태: 설계 승인 후 구현·로컬 검증 완료. push·서버 배포·실제 입력 관측은 미수행.

## 목적과 현재 진행 상태

모델의 판단 오류는 시간·토큰·성공 코드만으로 설명할 수 없다.
오늘 팀원이 Dev 서버 화면에 직접 입력하는 테스트에서 모델이 실제 받은 요청과 반환한 응답을 검증 결과와 함께 확인한다.
이미 구현한 기술 관측은 X-Trace-Id→AI 호출→출력 검증→HTTP 결과를 연결하며 관련 검사 88개가 통과했다.
이 기술 관측은 원문을 포함하지 않는다. 원문은 아래 별도 진단 파일로 보완한다.
기술 관측 변경과 추가 원문 기능의 최종 전체 검사는 변경을 모두 마친 뒤 한 번 수행한다.

## 확인할 원문

요청별로 다음 사건을 순서와 시도 번호를 붙여 저장한다.

1. 모델 요청: 실제 systemPrompt·userPrompt, 전송한 네이티브 JSON schema가 있으면 해당 schema.
2. 모델 응답: LlmCompletion.content의 가공 전 문자열. 허용되지 않은 JSON도 문자열로 보존.
3. 응답 메타데이터: 모델, 단계, 시간, 토큰, 종료 이유, 프롬프트·스키마 버전.
4. 서버 검증: 통과/형식 오류/판단보류/제공자 오류, 정제된 검증 이유. 유효한 평가라면 decision·retryTarget도 연결.
5. 최종 요청 처리: HTTP 상태·역할극 결과·checkpointVersion·replayed·전체 시간.

전체 provider 설정 객체나 HTTP Authorization 헤더를 직렬화하지 않는다.
수집하는 입력은 모델에 실제 전달된 내용이며, 개인정보 마스킹 전 사용자 입력·음성 파일은 이번 수집 범위에 포함하지 않는다.
모델이 공개하지 않은 내부 추론을 제공하는 기능도 아니다.
정상·재시도·실패 응답을 그대로 보존하며 필드나 거절 코드를 수정하지 않는다.

## 활성화 범위와 저장 위치

- 기본 비활성화. dev 프로필에서 명시적으로 켠 경우만 허용한다.
- 오늘은 팀원 테스트 계정의 직접 입력을 관측하는 제한된 시간에 사용한다. 일반 이용자 전체의 상시 원문 수집으로 확대하지 않는다.
- 기존 기술 관측(neuringo.ai.call-log)을 함께 켜서 브라우저 X-Trace-Id로 찾는다.
- 진단 시간 창은 앱 시작 후 기본 15분, 최대 요청 수는 기본 10건으로 제한한다.
- 설정 만료나 한도 도달 시 수집 종료를 기술 로그로 기록하며 사용자 응답 흐름은 유지한다.
- 서버 컨테이너 내부 /tmp/neuringo-diagnostics/<서버 생성 요청 UUID>/diagnostics.jsonl에 저장한다.
- 디렉터리 0700·파일 0600, HTTP 다운로드 엔드포인트는 추가하지 않는다.
- 파일별·전체 크기를 제한한다. 기본 총 20MiB·사건당 1MiB이며 초과는 truncated/skipped로 명시하고 전체 원문 보존 성공으로 집계하지 않는다.
- 별도 영구 볼륨을 추가하지 않아 컨테이너 재생성 시 제거된다. 실험 종료 시 명시적 삭제 절차도 제공한다.

기술 로그에는 수집 상태와 요청 식별자만 남기고 원문을 중복 출력하지 않는다.
운영자는 기존 AWS Session Manager 접근으로 컨테이너 내부 파일을 확인한다.
브라우저 응답 X-Trace-Id를 확인해 그 UUID 디렉터리만 읽으면 된다.
요청/재시도 동시 처리 시 다른 파일로 섞이거나 한 사건의 JSONL 쓰기가 중간에 섞이지 않아야 한다.

## 구현 범위

운영과 분리된 테스트 실행기의 P1Diagnostics를 서버에서 직접 실행하지 않는다.
원문 수집은 기본 no-op인 진단 기록 인터페이스와 dev 파일 구현으로 구성한다.
실제 provider 호출 경계와 StructuredLlmExecutor 검증 경계에 연결해 추가 모델 호출 없이 기록한다.
HTTP 관측 필터는 최종 기술 결과를 같은 파일에 연결한다.
기존 서비스의 분석·생성·검수·저장·시간 제한과 반복 횟수는 변경하지 않는다.

기존 관측 코드의 논리를 재사용하고 전면적인 관측 프레임워크나 외부 저장 서비스는 도입하지 않는다.
서버 Parameter Store 전달 목록에 진단 활성화·시간 창·한도에 필요한 설정을 추가한다.
로컬 .env.local을 서버로 복사하거나 git에 커밋하지 않는다.
지원하지 않는 프로필에서 활성화를 요청하거나 저장 경로 설정이 부적합하면 원문 수집을 시작하지 않는다.
저장 실패·한도 초과는 원문 없는 기술 사유로 표시하며 정상 AI 결과를 실패로 바꾸지 않는다.

## 검증과 운영 절차

외부 AI 호출 없이 가짜 provider로 다음을 확인한다.

- 기본/비dev 비활성화, 시간 창·요청/크기 한도, 저장 실패 시 사용자 결과 유지.
- 요청 UUID 경로 제한·파일 권한·동시 요청 격리.
- 잘못된 JSON 원문 보존, provider OK와 parser 실패 분리, 재시도 사건 순서.
- 원문이 기술 콘솔 로그·응답 본문으로 유출되지 않음.
- 프롬프트/결과에 키를 넣지 않은 가짜 provider 설정에서 API 키·Authorization이 진단 파일에 수집되지 않음.
- HTTP 응답 X-Trace-Id와 파일·AI 단계 상관키 일치.
- 진단 비활성 상태에서 기존 기능·재시도·기한·저장 정합성 유지.

관련 검사 후 최종 전체 build/형식 검사·커밋 준비를 진행한다.
이번 기능 확인을 위한 추가 유료 호출은 제안하지 않는다. 서버 배포 후 사용자가 직접 수행할 테스트에서 확인한다.
실험 종료 시 설정을 끄고 진단 파일을 삭제하는 순서를 실행 절차에 포함한다.
원문을 PR 본문·공개 이슈·공용 로그에 일괄 첨부하지 않고 필요한 합성 재현 사례로 정리한다.

## 승인 요청 범위

승인 요청은 위 dev 한정 요청별 원문 파일 수집·관련 서버 설정 전달·로컬 검증·운영 절차 문서다.
별도 유료 호출·push·PR·배포·일반 이용자 원문 수집·음성 원본 수집은 포함하지 않는다.

## 구현·검증 결과

- 기본 no-op 진단 포트, dev 파일 구현, provider/출력 검사/HTTP 완료 경계 연결을 적용했다.
- 가짜 provider로 실제 파일·JSONL 원문 보존·권한·동시 요청 격리·한도·저장 실패 격리·HTTP 식별자 연결을 확인했다.
- 전체 검사에서 DEBUG 예외 메시지가 일반 로그에 나올 수 있음을 검출했다. 고정 오류 코드만 남기도록 수정하고 DEBUG를 강제하는 회귀 검사를 추가했다.
- 공식 develop `d6f7e06` 동기화 후 `./gradlew --no-daemon build` 성공: 총 2,855개, 통과 2,849개, opt-in 제외 6개, 실패 0개(2분 56초).
- 마이그레이션 가드·서버 배포 자체 검사는 Linux 환경에서 통과했다. macOS 기본 Bash 3/GNU sed 차이로 실행 실패한 결과와 구분한다.
- 이 기능을 검증하는 과정에서 실제 외부 AI를 추가 호출하지 않았다. 모델 판단 품질·AWS 파일 접근은 서버 관측에서 별도로 확인한다.
- 시간 창 만료는 파일 삭제가 아니다. 프로세스/컨테이너 재시작 후 파일이 남을 수 있으며 컨테이너 재생성 또는 명시적 삭제가 필요하다.

설정·실제 입력·파일 확인·해석·종료 절차는 [Dev 서버 관측 실행 절차](roleplay-dev-observation-runbook-2026-11-08.md)에 정리했다.
