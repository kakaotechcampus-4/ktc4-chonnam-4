## 구현 경계

`ScenarioApprovalRegistry`는 최종 승인·배정 처리에서 사용할 내부 저장 경계다. 현재 develop에는 강사 승인 API가 없으므로 아직 운영 요청 경로에 연결하지 않았다. 이 변경만으로 기존 후보 조회나 퀴즈 완료 후 자동 배정 동작이 바뀌지는 않는다.

호출자는 인증 정보로 강사 ID를 결정하고 활동 접근 권한·검토 버전·콘텐츠 적합성을 검사한 뒤, 최종 배정과 같은 트랜잭션에서 `recordApproval`을 호출해야 한다. 트랜잭션 없이 호출하면 거부한다. 이 메서드 자체가 HTTP 인증이나 교육적 적합성을 판정하지는 않는다.

## 저장 계약

- `scenario_approval`에 시나리오 ID당 승인자 한 명과 확인한 조건을 INSERT한다. 수정한 콘텐츠는 새 시나리오 ID로 기록한다.
- 학습 목표, 난이도, 확인한 범주·상황·등장인물 역할 구성·필수 행동, 검증 규칙 버전, 최초 승인 시각을 저장한다. 생성 요청 조건을 그대로 복사해 검증된 사실로 취급하면 안 된다.
- 역할 목록은 같은 역할의 인원수를 보존한다. 필수 행동은 중복을 제거한다. 텍스트의 앞뒤 공백과 연속된 유니코드 공백만 정규화하며, 의미 비교는 하지 않는다.
- 목록의 SQL NULL은 확인 정보 없음, JSON 빈 배열은 해당 항목이 없음을 확인했다는 뜻이다. 범주·상황의 NULL은 확인 정보 없음이다. 이후 후보 판정에서 요청한 조건의 정보가 없으면 제외해야 한다.
- 동일 승인자·동일 조건의 재호출은 최초 행과 승인 시각을 반환한다. 다른 승인자나 조건으로 덮어쓰려 하면 거부한다. DB에서도 UPDATE를 차단한다.
- 시나리오 행을 짧게 잠그고 APPROVED 상태와 난이도를 확인한다. 최종 배정 서비스에 연결할 때 활동·아동·검토·시나리오의 잠금 순서를 일관되게 유지해야 한다.
- `findOwnedApproved`는 해당 강사의 승인 기록과 현재 APPROVED 상태만 확인한다. 학생 배정 이력과 요청 조건 비교를 포함한 전체 후보 자격 판정은 다음 구현 단위에서 추가한다.
- 기존 승인본에는 승인자를 추정하는 INSERT를 하지 않는다. RETIRED 상태가 되면 기록은 유지하지만 위 조회에서는 반환하지 않는다.
- 강사 계정 또는 시나리오가 물리 삭제되면 해당 승인 기록은 FK의 ON DELETE CASCADE로 삭제한다. 계정 상태만 변경하는 탈퇴 흐름은 별도 정리 경로와 함께 확인해야 한다.

기존 조건 해시·시나리오 콘텐츠는 변경하지 않는다. 마이그레이션 V25는 현재 develop V24 다음 번호이며, 열린 PR 통합 시 번호 충돌을 다시 확인해야 한다.

## 두 번째 구현 단위 — 조건별 후보 조회

`ScenarioCandidateQueryService.select(activityId, authentication)`가 기존 `InitialScenarioPreparationService`로 목표·최초 난이도·담당 강사 권한을 확인한다. 승인자 필터에는 로그인한 강사 ID를 사용한다. 기존 활동 중복 판정용 전체 조건 해시는 변경하지 않는다.

`ScenarioCandidateRepository`는 한 SQL 문장에서 본인 승인 기록을 분류하고 후보 ID·버전과 제외 집계를 함께 반환한다. 검사 순서는 현재 승인 상태 → 검증 규칙 버전 → 난이도 → 목표 문구 → 범주 → 상황 → 등장인물 → 필수 행동 → 학생 배정 이력이다. 한 후보는 최초 실패 사유에 한 번만 집계된다. 뒤 조건의 숨은 실패까지 전부 측정한 통계로 해석하면 안 된다.

- 목표는 공백 정규화 후 문구가 같아야 하며 난이도는 일치해야 한다.
- 범주·상황은 지정했으면 일치해야 한다. 미지정 조건은 제한하지 않는다.
- 등장인물은 역할과 인원수 구성이 같아야 한다. 요청의 빈 목록은 제한 없음이다.
- 요청한 필수 행동은 확인된 행동의 부분집합이어야 한다. 확인된 추가 행동은 허용한다.
- 지정한 조건의 확인 정보가 NULL이면 `*_UNVERIFIED`, 정보가 있으나 다르면 `*_MISMATCH`로 분류한다.
- 학생에게 동일 시나리오 ID를 배정한 활동이 하나라도 있으면 모든 활동 상태에서 제외한다. 원본을 사용했더라도 수정 후 새 ID는 별도로 판정한다.

금지 표현이 있으면 조건을 통과한 후보들의 표시 필드를 한 번에 읽는다. PostgreSQL UUID 배열을 사용해 후보 수만큼 바인드 변수가 증가하지 않도록 했다. 제목·요약·등장인물 역할·사실·시작 질문·작은 목표 설명·근거·달성 예시를 각각 검사한다. 공백 제거와 영문 대소문자 무시 후 부분 문자열로 비교하며, 서로 다른 필드를 이어 붙이지 않는다. ID·금지 추론 지침은 검사 대상에서 제외한다. 표시 필드의 구조나 현재 콘텐츠를 확인할 수 없으면 `CONTENT_UNVERIFIED`로 제외한다. 제시 직전 자격 재검사는 검토 저장 단계에서 연결할 예정이다.

후보 조회는 읽기 전용이며 승인·활동·제시 통계를 쓰지 않는다. 반환 순서는 현재 ID 순으로만 고정했으며, 강사별 마지막 제시 시각의 순환 정렬과 고정 검토 목록은 아직 구현하지 않았다. 운영 컨트롤러 연결, 후보 없음·소진 시 자동 생성, 기존 자동 배정 제거도 후속 구현 단위다.

`scenario_reuse_selection` 로그에 규칙 버전·활동 ID·본인 승인 기록 수·통과 수·제외 사유별 수와 조회/콘텐츠 검사/전체 소요 시간을 기록한다. 조건 원문·이름·이메일은 기록하지 않는다. 본인 승인 기록이 0인 경우와 조건에서 탈락한 경우를 구분할 수 있다. 승인자가 없는 과거 자료는 특정 강사의 통계에 포함하지 않는다. 목표 문구 불일치는 의미상 적합한 후보를 놓쳤다는 증거가 아니므로 별도 표본 검토가 필요하다.

## 세 번째 구현 단위 — 순환 정렬·검토 시작·복원

`ScenarioReviewStartService.startOrResume(activityId, requestId, authentication)`를 추가했다. 아직 운영 컨트롤러에는 연결하지 않았다. 기존 검토가 있으면 그 목록과 현재 위치를 복원한다. 없을 때만 조건 조회·콘텐츠 검사·순환 정렬을 수행하고 검토를 생성한다.

- 후보 정렬은 강사별 미제시 → 마지막 제시 시각이 오래된 순 → 시나리오 ID 순이다. SQL에서 제시 통계를 LEFT JOIN하며, 검토 생성 시의 순서를 고정한다.
- `scenario_review`는 활동당 한 행으로 입력 지문·현재 순번·수정 번호를 저장한다. `scenario_review_candidate`는 고정 순번·시나리오 ID·버전을 일괄 INSERT한다. 콘텐츠 사본은 저장하지 않는다.
- 후보 ID에는 원본 FK를 걸지 않아 원본 삭제·폐기 후에도 목록을 보존한다. 복원 시 승인 상태·강사 소유권·버전·학생 배정 이력을 다시 검사하고, 현재 순번 이후의 유효 후보를 찾는다. 현재 순번은 고정 목록의 실제 행을 가리키도록 지연 FK로 검증한다.
- 검토 중 추가된 승인본은 현재 목록에 포함하지 않는다. 자동 만료는 없다. 현재 후보 한 개와 순번·수정 번호·후보 수를 내부 결과로 반환한다.
- 첫 후보 또는 무효화 후 새 후보를 선택하면 `scenario_presentation_stat`을 UPSERT해 마지막 제시 시각·누적 제시 횟수를 갱신한다. `scenario_presentation_daily`의 서울 날짜별 제시 횟수도 같은 트랜잭션에서 갱신한다. 마지막 시각은 동시 처리로 과거 값으로 돌아가지 않도록 GREATEST를 사용한다.
- 여기서 제시는 서버가 현재 후보로 확정했다는 뜻이다. 화면 표시를 확인한 이벤트가 아니며, 화면 응답 시간·실제 노출 측정은 프론트엔드 연동 후 별도로 확인해야 한다.
- 단순 복원은 제시 시각·횟수를 변경하지 않는다. 처리한 요청의 재전송 중 후보 무효화가 확인되면 `SCENARIO_REVIEW_CHANGED` 충돌로 이동을 막고, 새로운 복원 요청에서만 다음 유효 후보를 선택한다.
- `scenario_review_request`는 시작/복원 요청 ID와 대상 검토·종료 결과를 저장한다. 검토 삭제와 독립적으로 활동 삭제까지 보관한다. 종료 표시된 옛 요청으로 검토를 재생성할 수 없다. 취소·최종 승인 API에서 종료 결과 갱신과 목록 삭제를 연결하는 작업은 남아 있다.

시작 조정 서비스는 외부 트랜잭션을 허용하지 않는다. 후보 조회·콘텐츠 검사는 쓰기 잠금 밖에서 실행한다. `ScenarioReviewTransactions`가 계정 KEY SHARE → 활동 FOR UPDATE → 검토 FOR UPDATE → 선택 시나리오 FOR SHARE 순으로 짧게 잠근다. 계정 잠금은 탈퇴 시 계정부터 잠그는 기존 삭제 경로와 FK 확인의 교착을 피하기 위한 것이다. 저장 직전에 권한·목표/난이도 입력 지문·기존 검토·활동의 미배정 상태를 재확인한다.

동시 시작은 목록 계산이 중복될 수 있지만 활동 잠금과 UNIQUE 제약으로 목록 하나만 커밋한다. 나중 요청은 먼저 생성된 검토를 복원한다. 목록·현재 순번·요청 기록·누적/일별 통계는 함께 커밋하거나 함께 롤백한다. 활동 삭제 시 임시 목록과 요청 기록은 FK로 삭제되고, 제시 통계는 해당 활동에 종속되지 않으므로 유지한다.

후보가 없거나 모두 무효화되면 내부 결과의 현재 후보가 null이다. 이를 사용자에게 후보 없음으로 반환하는 API를 만든 것이 아니다. 이후 준비 조정 경로에서 신규 생성을 자동 호출해야 한다. 명시적 거절/NEXT, 취소 API, 신규 생성, 최종 배정은 아직 미구현이며, 큐·워커·병렬 실행 제어는 이번 Task 범위에 추가하지 않는다. V26도 열린 PR 통합 시 번호 충돌을 재확인한다.

세 번째 단위 검증: `ScenarioReviewStartIntegrationTest` 13개, 후보 검사 32개, 구조 검사 11개, Flyway 검사 2개가 통과했다. PostgreSQL에서 순환 순서·고정 목록·새 서비스 인스턴스/인증 세션으로 복원·현재 위치 복원·무효 후보 건너뛰기·동시 시작·입력 변경 경쟁·쓰기 잠금 밖 조회·통계 실패 시 전체 롤백·활동 삭제 FK·종료 기록의 재생성 방지·동일 요청 재전송의 추가 이동 방지를 확인했다. 종료 기록과 이동 후 상태는 fixture로 공급했으며, 실제 취소/NEXT API를 검증한 것은 아니다. 최초 난이도 계약만 mock으로 공급했다. 실제 프로세스 재시작·로그아웃 API·프론트엔드·부하 테스트는 실행하지 않았다. 최종 변경 코드·SQL 10개 파일과 검사 복사본의 바이트 일치를 확인했다. 운영 DB·LLM 호출과 전체 회귀 검사는 실행하지 않았다.

## 네 번째 구현 단위 — 거절·다음 후보 전환

`ScenarioReviewTransactions.next(activityId, requestId, reviewId, expectedRevision, authentication)`를 추가했다. 같은 POST 준비 API의 NEXT 동작에 연결할 내부 경계이며 새 API를 추가하지 않았다.

1. 기존 순서로 계정·활동을 잠그고 목표 조회의 담당 강사 권한을 확인한다.
2. 같은 요청 ID의 기록을 먼저 조회한다. NEXT·검토 ID·요청 수정 번호가 같으면 최초 내부 결과를 반환한다. 내용이나 동작이 다르면 `IDEMPOTENCY_KEY_REUSED`, 종료된 요청이면 `SCENARIO_REVIEW_CLOSED` 충돌이다.
3. 새 요청은 검토 ID·현재 수정 번호·입력 지문·미배정 상태를 검사한다. 같은 수정 번호의 다른 요청이 먼저 처리됐으면 `SCENARIO_REVIEW_CHANGED` 충돌로 추가 이동을 막는다.
4. 현재 순번의 `scenario_review_candidate.rejected_at`만 UPDATE한다. 원본 시나리오의 APPROVED 상태는 변경하지 않는다.
5. 다음 순번부터 거절되지 않았고 현재 승인·소유권·버전·학생 미배정 조건을 통과하는 후보를 찾는다. 폐기·물리 삭제·학생에게 배정된 후보는 건너뛰며 거절로 기록하지 않는다. 고정 목록 밖의 새 승인본은 조회하지 않는다.
6. 현재 순번과 수정 번호를 UPDATE하고 새로 제시한 후보의 누적/일별 통계를 갱신한다. 최초 결과는 `scenario_review_request.expected_revision`과 `result_snapshot`에 저장한다. 거절·위치·통계·요청 결과는 같은 트랜잭션으로 커밋하거나 롤백한다.

재전송 조회가 현재 수정 번호 비교보다 앞서므로, 수정 번호 1로 처리된 NEXT를 재전송해도 낡은 번호 오류가 발생하지 않는다. 더 나중의 NEXT가 성공한 뒤에도 예전 요청은 예전 결과를 재사용한다. 소비자는 현재 화면보다 낮은 수정 번호의 응답으로 상태를 덮어쓰지 않도록 해야 하며, 이 사항은 프론트엔드 최종 전달 항목에 포함한다.

후보 소진 시 현재 순번과 후보가 null인 내부 결과를 저장한다. 이후 복원 조회도 rejected_at 조건을 적용해 거절한 후보를 처음부터 다시 제시하지 않는다. 이 결과를 사용자에게 후보 없음으로 종료시키는 API는 추가하지 않았다. 신규 생성 자동 연결은 준비 조정 단계에 남아 있다. 별도 요청으로 다음 후보를 다시 거절하려고 해도 현재 후보가 없으면 `SCENARIO_REVIEW_NO_CANDIDATE` 충돌로 추가 변경을 막는다.

종료 처리 구현 시 모든 해당 검토의 요청 기록을 CANCELLED/CONFIRMED로 갱신하면서 expected_revision·result_snapshot을 NULL로 지우고 임시 검토 목록을 삭제해야 한다. 활동 삭제까지 유지할 최소 종료 기록과 검토 중 재전송 결과를 구분한다. 이 정리의 DB 호환성과 옛 NEXT 재생성 방지는 fixture로 검증했으며 실제 취소·최종 승인 경로 연결은 남아 있다.

검증: 검토 시작·복원·NEXT 통합 검사 26개(이번 추가 13개), 구조 검사 11개, Flyway 검사 2개가 통과했다. 동일 요청/서로 다른 요청의 동시 처리, stale 수정 번호, 요청 ID 내용 충돌, 원본 승인 유지·검토별 거절, 후보 무효화 세 유형, 소진 후 순환 방지, 실패 시 전체 롤백, 권한·입력 재검사를 확인했다. 검사한 코드·SQL·테스트 4개 파일과 작업 복사본의 바이트 일치를 확인했다. 기존 후보 조건 검사 32개는 해당 경로 변경이 없어 이전 결과를 재사용했다. 운영 DB·LLM·프론트엔드·부하·전체 회귀 검사는 실행하지 않았다. V27 번호는 PR 통합 시 재확인한다.

## 다섯 번째 구현 단위 — 취소·종료 기록 정리

`ScenarioReviewTransactions.cancel(activityId, requestId, reviewId, expectedRevision, authentication)`를 추가했다. 운영 DELETE API 연결은 아직 하지 않았다. 계정 → 활동 → 검토 순서로 잠그고 담당 강사 권한을 확인한다. 취소는 입력이 바뀌었거나 최초 난이도 근거가 없어도 임시 검토를 정리할 수 있도록, 준비 입력의 동일성 대신 권한·검토 ID·수정 번호·미배정 상태를 검사한다.

같은 트랜잭션에서 다음 작업을 수행한다.

1. 해당 검토의 ACTIVE 요청 기록을 CANCELLED로 UPDATE하고 closed_at을 기록한다. expected_revision과 result_snapshot은 SQL NULL로 비운다.
2. CANCEL 요청 ID·요청 지문·검토 ID·종료 결과·종료 시각을 INSERT한다. 취소 요청 지문은 활동 ID·검토 ID·요청 수정 번호의 SHA-256이며, 삭제한 수정 번호 값을 보관하지 않고 재전송 내용의 일치를 확인한다.
3. scenario_review 행을 DELETE한다. 후보 ID 목록·현재 위치·거절 시각은 FK의 ON DELETE CASCADE로 함께 삭제된다. 원본 승인 시나리오와 누적/일별 제시 통계는 변경하지 않는다.
4. activity.scenario_review_epoch를 1 증가시킨다.

시작 서비스는 후보 조회 전에 활동의 epoch를 읽고, 저장 직전에 같은 번호인지 확인한다. 취소 전에 시작됐으나 아직 요청 기록을 INSERT하지 않은 조회도, 늦게 끝나면 SCENARIO_REVIEW_CHANGED 충돌로 저장을 거부한다. 새로 시작한 요청은 새 epoch로 진행할 수 있다. epoch는 내부 동시 처리 정보이며 API 입력으로 요구하지 않는다.

취소 재전송은 저장된 종료 결과·시각을 반환하며 epoch를 다시 증가시키지 않는다. 새 검토가 생성된 뒤 옛 취소를 재전송해도 새 검토를 삭제하지 않는다. 같은 요청 ID에 다른 검토 ID·수정 번호·동작을 사용하면 IDEMPOTENCY_KEY_REUSED 충돌이다. 수정 번호가 오래된 취소와 NEXT/취소의 동시 요청에서는 먼저 처리된 변경 하나만 성공한다.

종료 기록은 활동 삭제까지 유지한다. 활동 삭제 시 종료 기록도 FK로 삭제된다. closed_at 이전 기록은 종료 시각을 추정해 채우지 않으며, 새 취소 처리는 정확한 종료 시각을 저장한다. closeRequests는 최종 승인에서도 사용할 수 있는 정리 경계지만, 실제 CONFIRMED 배정 경로는 아직 연결하지 않았다. 신규 생성 결과·미승인 초안의 취소 정리는 생성 저장 경로를 구현할 때 함께 확인한다.

검증: 검토 통합 검사 36개(이번 추가 10개), 구조 검사 11개, Flyway 검사 2개가 통과했다. 기존 수동 종료 fixture 두 곳도 실제 cancel 호출로 바꿨다. 결과 정리·통계 보존·취소 재전송·새 검토 보호·오래된 수정 번호·권한·난이도/목표 변경과 독립적인 정리·중복/서로 다른 취소의 동시 처리·NEXT와의 경쟁·늦은 시작 요청 차단·정리 실패 시 전체 롤백·활동 삭제를 확인했다. 검사한 코드·SQL·테스트 7개 파일과 작업 복사본의 바이트 일치를 확인했다. 운영 DB·LLM·HTTP/프론트엔드·부하·전체 회귀 검사는 실행하지 않았다. V28 번호는 PR 통합 시 재확인한다.

## 여섯 번째 구현 단위 — 재사용에서 신규 생성으로 자동 연결

`ScenarioPreparationService.prepare`와 `next`가 운영 준비 API에 연결할 조정 경계다. 재사용 후보가 있으면 반환하고 LLM을 호출하지 않는다. 없거나 소진됐으면 같은 호출에서 `ScenarioGenerationCoordinator` → `ScenarioGenerationService` → 기존 `ScenarioPromptFactory`·`StructuredLlmExecutor`·`LlmProvider`를 실행한다. 후보 없음만 반환하는 성공 API를 만들지 않았다. 아직 운영 컨트롤러에는 연결하지 않았다.

생성 입력은 저장된 목표·범주·상황·등장인물·필수 행동·금지 표현과 최초 난이도다. 추적 ID·아동 이름을 프롬프트에 넣지 않는다. 기존 파서가 난이도·스키마·사실·작은 목표·근거·시작 질문·안전 규칙을 검사한다. 추가로 요청한 등장인물 역할 구성을 정규화해 비교하고 금지 표현을 유니코드 공백 제거·영문 대소문자 무시로 필드별 검사한다. 생성 스키마의 고정 LEARNER는 강사가 지정한 상대 등장인물 구성과 구분한다. 목표·필수 행동의 교육적 충족을 기계 검증했다고 주장하지 않으며, 승인된 조건 기록도 아직 생성하지 않는다.

생성한 결과는 다음 짧은 트랜잭션에서만 저장한다.

- 현재 권한·검토 ID·수정 번호·입력 지문·취소 epoch·미배정 상태를 다시 확인한다. 달라졌다면 결과를 저장하지 않는다.
- `scenario`에 DRAFT/AI_GENERATED로 INSERT하고 `scenario_micro_goal`의 모델 키 MG-01 등을 UUID로 바꿔 INSERT한다. starting_questions는 opening_prompts에 저장한다. 입력 조건을 검증된 승인 메타데이터로 복사하지 않는다.
- 고정된 재사용 후보 부분은 유지하고, 생성 초안은 별도 candidate_source=GENERATED 행으로 검토 뒤에 추가한다. 현재 위치를 해당 행으로 바꾸고 제시 통계를 갱신한다. 이 내부 준비가 완료될 때까지 수정 번호는 같은 논리 동작의 번호를 유지한다.
- NEXT의 미완료 내부 결과에 후보가 없었다면, 같은 수정 번호의 최초 결과를 완성된 생성 후보로 갱신한다. 완료 이후 재전송은 같은 초안을 반환한다.

LLM 호출 중에는 DB 트랜잭션·활동/검토 잠금을 유지하지 않는다. 동일 서버 인스턴스에서 같은 검토·수정 번호의 겹친 생성은 CompletableFuture로 결과를 공유한다. 완료·실패하면 메모리 항목을 제거한다. 다른 검토의 호출을 직렬화하거나 전역 실행 수를 제한하지 않는다. 이 메모리는 후보 목록·복원의 저장소가 아니며, 복원은 PostgreSQL의 현재 초안을 사용한다.

여러 서버 인스턴스에서는 외부 생성 호출이 중복될 수 있다. 저장 직전 동일 검토를 재검사해 이미 저장된 후보를 반환하므로 초안은 하나만 커밋한다. 서버 중단 후 아직 결과가 저장되지 않았다면 다음 요청에서 다시 생성한다. 외부 호출의 정확히 한 번 실행이나 생성 작업 자동 복구를 보장하지 않는다. 전역 큐·워커·병렬 제한 정책은 후속 논의 그대로다.

생성 초안도 강사가 거절하면 다음 생성으로 자동 연결된다. 직전에 거절한 생성 초안을 revision.previous_scenario와 새 내용 요청으로 전달한다. 공급자 실패·시간 초과·검사 실패는 오류이며, 응용 계층 자동 재생성 루프는 추가하지 않았다. 공급자 SDK 재시도는 기존 설정을 따른다. 실패 후 같은 준비 요청으로 재시도해도 후보 이동을 추가하지 않는다. 공급자 미설정은 503, 시간 초과는 504, 잘못된 출력 등은 502로 처리한다. 로그에는 생성 결과/실패·전환 사유·소요 시간·제공된 토큰 수를 기록하되 프롬프트와 출력 본문은 기록하지 않는다. CANDIDATES_EXHAUSTED는 거절뿐 아니라 후보 무효화로 더 제시할 수 없는 경우도 포함한다.

검토 삭제 트리거는 해당 검토에 속하고 다른 활동·버전에서 참조하지 않는 DRAFT 생성 초안을 DELETE한다. 작은 목표와 해당 미승인 초안의 제시 통계도 FK로 삭제된다. 기존 APPROVED 원본과 그 제시 통계는 보존한다. 취소와 활동 삭제 모두 이 정리를 적용한다. 최종 승인한 생성본은 APPROVED가 되므로 정리 대상에서 제외한다. 편집본의 원본으로 참조되는 초안도 보존한다.

검토 DTO의 참조는 DRAFT도 표현하므로 ScenarioVersionRef를 사용한다. 재사용 조회에서 승인 상태를 보장하는 ApprovedScenarioVersion과 구분하며 JSON 식별자 필드 형태는 유지한다. 최종 승인·편집·배정과 opening focus/역할극 검증 경로 연결은 아직 남아 있다.

검증: 검토 통합 51개(이번 추가 15개), 구조 11개, Flyway 2개를 실행했다. 첫 묶음은 63개 통과·재시도 fixture 설정 오류 1개 실패였고, fixture만 수정해 해당 검사 1개를 재실행하여 통과했다. 나머지 통과 결과는 재사용했다. 실제 PostgreSQL·파서를 사용하고 LlmProvider 응답만 대체했으며 실제 유료 호출은 하지 않았다. 재사용 시 호출 생략, 최초/소진/생성본 거절 후 자동 생성, 저장·복원·재전송, 호출 중 쓰기 잠금 없음, 생성 중 취소/입력 변경/활동 삭제, 동시 요청, 검사 실패·시간 초과·저장 실패와 재시도, 초안 삭제를 확인했다. 검사한 13개 코드·SQL·fixture 파일과 작업 파일의 바이트 일치를 확인했다. 실제 제공자·HTTP/프론트엔드·부하·전체 회귀 검사는 실행하지 않았다. V29 번호는 PR 통합 시 재확인한다.

## 일곱 번째 구현 단위 — 수정 없는 후보 승인·활동 배정

사용자는 이번 단계의 질문에서 시작 질문별 목표 ID도 AI가 생성하고 서버가 검증하는 방식을 확정했다. 기존 V23은 목록 순서만으로 시작 목표를 추측하는 것을 금지한다. 생성 출력에 starting_question_goal_ids(S0·S1·S2 → 실제 micro_goal id)를 추가하고 프롬프트/스키마 버전을 v2로 올렸다. 각 지원 키와 목표 ID의 존재를 검사하고, 모델 키를 저장 UUID로 바꿔 DRAFT 상태에서 scenario_opening_focus에 INSERT한다. 질문과 목표의 교육적 의미 일치까지 기계 검증했다고 주장하지 않는다. 구버전 데이터의 연결을 임의로 채우지 않는다.

`ScenarioConfirmationService.confirm`은 먼저 권한을 확인하고 요청 재전송 여부를 조회한다. 새 요청은 REPEATABLE_READ 읽기 전용 트랜잭션에서 현재 후보·조건·콘텐츠·질문별 목표 연결을 함께 검사한다. 재사용 판정은 현재 후보 한 개에 한정하고, PREPARE/CONFIRM 로그를 구분한다. 생성 초안은 현재 출력 파서와 요청 조건으로 다시 검사한다.

최종 저장은 계정 → 활동 → 학생 → 검토 → 시나리오 순서로 잠근 뒤 수행한다. 준비 입력 지문·검토 수정 번호·후보 ID/버전·콘텐츠 본문이 사전 검사 때와 같은지 확인한다. 학생 행을 잠근 상태에서 모든 상태의 배정 이력을 다시 조회해, 다른 활동이 동일 시나리오 ID를 동시에 배정하는 것을 차단한다.

- GENERATED: scenario를 APPROVED로 바꾸고 scenario_approval에 해당 강사와 확인 조건을 INSERT한다. 구체적인 역할 구성은 실제 콘텐츠에서 확인하며, 지정하지 않아 확인되지 않은 필수 행동은 NULL로 둔다. 목표·행동의 학습 적합성은 강사가 현재 조건과 콘텐츠를 보고 확정한 사실에 근거한다.
- REUSE: 기존 원본과 최초 승인 조건·시각은 유지한다. 실제 활동 배정이 성공할 때만 누적/일별 reuse_count와 마지막 재사용 시각을 갱신한다. 최초 생성본의 배정은 재사용으로 집계하지 않는다.
- activity에 현재 시나리오 ID와 source(REUSE/GENERATED)를 UPDATE한다. activity_scenario_approval에 활동·학생·목표 ID/해시·승인 강사·시나리오 ID/버전/난이도·콘텐츠 지문·승인 시각을 INSERT한다. source 승인자와 활동 승인자의 관계는 FK로 검증한다.
- 요청을 CONFIRMED로 종료하고 임시 응답·수정 번호를 비운다. CONFIRM 요청 지문과 종료 시각을 저장한 뒤 검토·후보 목록을 DELETE하고 epoch를 올린다. 승인된 생성본은 정리 트리거가 삭제하지 않는다.

이 작업들은 함께 커밋하거나 롤백한다. 동일 확정 요청은 검토 삭제 후에도 최초 종료 결과를 반환하며 재사용 횟수를 증가시키지 않는다. 같은 요청 ID의 다른 내용, 바뀐 후보, 오래된 수정 번호, 취소된 검토, 다른 강사의 요청은 거부한다.

역할극 조회는 activity_approved_scenario 뷰로 승인 근거를 공통 검증한다. 새 경로는 활동·학생·목표 ID와 현재 전체 목표 해시·시나리오 ID/버전/난이도를 모두 확인한다. 따라서 원본의 전체 조건 해시가 이번 요청과 달라도 정당하게 재승인한 배정을 사용할 수 있고, 다른 목표로 변경한 활동이 그 근거를 재사용할 수는 없다. 최초 역할극 준비·시작 질문·대화 컨텍스트·진행 조회에 연결했다.

기존 배정 데이터는 활동별 승인 근거가 없을 때만 기존 class_id/전체 해시 일치 검증을 유지한다. 이 호환 경로를 기존 승인 기록의 승인자를 추정해 채우는 근거로 사용하지 않는다. **기존 퀴즈 완료/결과 재조회에 의한 자동 배정 서비스는 아직 제거하지 않았다. 운영 준비/승인 API를 연결할 때 반드시 제거해야 하며 현재 실서비스 흐름 전체가 새 정책으로 교체된 상태는 아니다.** 편집 후 새 ID 확정도 다음 구현 단위에 남아 있다.

검증: 관련 검사 238개에서 230개가 통과했고, 새 승인 검사 8개가 순수 재검사 호출의 추적 classId 누락으로 실패했다. 저장-읽기-재검사 회귀 검사 1개를 추가해 원인을 확인하고 필수 추적 ID를 보완했다. 이후 검토/생성/승인 통합 검사 61개가 모두 통과했다. 다른 통과 결과 178개는 재사용했으며 서로 다른 검사 총 239개의 결과가 유효하다. 생성본 승인 후 실제 역할극 시작/질문별 목표 연결, 다른 전체 목표 해시로 재사용 승인, 중복 확정의 통계 불변, 학생 동시 중복 배정 차단, 콘텐츠/입력/질문 연결의 경쟁 변경, 저장 실패 시 전체 롤백, 권한과 취소 상태를 확인했다. 수정 없는 승인 경로만 구현했다. 검사한 변경 파일 25개의 바이트 일치를 확인했다. 실제 LLM·운영 HTTP/프론트엔드·부하·전체 회귀 검사는 실행하지 않았다. V30 번호는 PR 통합 시 재확인한다.

## 여덟 번째 구현 단위 — 수정 후보를 새 ID로 확정

`ScenarioConfirmationService.confirm`에 선택적 ScenarioEdits를 받는 내부 호출을 추가했다. 기존 수정 없는 호출은 유지한다. 별도 수정 저장 API는 추가하지 않았으며, 검토 중 입력한 수정은 확정 요청에서만 반영한다.

- 수정 가능한 필드는 title, summary, microGoals의 기존 microGoalId에 대한 description/requiredEvidence다. null은 유지이며 작은 목표 추가·삭제·순서 변경, 등장인물·사실·시작 질문·달성 예시 변경은 이 모델로 수행할 수 없다.
- 빈 문자열, 중복 UUID, 현재 원본에 없는 목표 UUID, 빈/과도한 근거 목록을 거부한다. 앞뒤 공백을 정리하고 목표 수정 목록을 UUID 순으로 정규화한다. 수정본도 기존 난이도별 콘텐츠·근거·안전·금지 표현 규칙을 통과해야 한다.
- 허용 필드만 원본 콘텐츠에 적용해 검사한다. 실제 본문이 같으면 새 ID를 만들지 않고 기존 승인 경로로 처리한다. 이 경우 기존 재사용본 배정이면 정상 재사용으로 집계한다.
- 실제 변경이 있으면 새 scenario ID와 작은 목표 UUID를 INSERT하고 원본 ID를 source_scenario_id에 기록한다. 새 버전 번호는 부모 버전 + 1이며 분기된 버전의 정체성은 고유 scenario ID로 구분한다. origin은 INSTRUCTOR_EDITED, 프롬프트/정책 버전은 원본의 이력을 보존한다.
- 시작 질문과 목표 연결은 원본의 명시적 연결을 새 목표 UUID로 옮긴다. 배열의 첫 목표를 임의로 선택하지 않는다. 사실·등장인물·시작 질문·달성 예시는 원본 값을 유지한다. 목표 설명을 바꿀 때의 교육적 적합성은 강사가 전체 콘텐츠를 보고 확정한다.
- 원본의 콘텐츠·승인 상태·최초 승인 조건과 과거 활동 배정은 변경하지 않는다. 생성 초안 원본은 새 승인본의 계보 참조가 있으므로 DRAFT로 보존되며 재사용 후보로 등록하지 않는다.

최종 트랜잭션은 원본의 현재 검토 ID/수정 번호·소유권·버전·본문을 재확인한 뒤 새 사본을 승인하고 활동별 승인 근거와 배정을 저장한다. 새 본문에 대해 현재 강사가 확인한 조건만 새 승인 기록으로 남기며, 원본의 추가 검증 조건을 그대로 복사하지 않는다. 활동의 scenario_source는 EDITED다. 원본의 실제 재사용 횟수는 증가시키지 않는다. 제시 통계도 기존의 서버 제시 기준을 유지한다.

학생의 과거 배정 제외는 최종 배정 ID에 적용한다. 제공 이후 원본 S1이 다른 활동에 먼저 배정됐더라도, 실제 수정한 새 ID S2의 배정은 허용한다. 변경 없는 요청은 S1 자체로 판정하므로 이를 우회할 수 없다. 동일 원본의 새 사본이 같은 수정 요청에서 중복 생성되지 않도록 요청 지문에 정규화한 수정 내용을 포함한다. 같은 요청 ID의 다른 수정은 충돌이며 목표 수정 목록의 순서만 다른 요청은 같은 결과를 반환한다.

같은 요청이 사전 검사 도중 먼저 확정돼 검토 목록이 사라지는 경쟁도 처리한다. 사전 검사 실패 시 종료 요청을 다시 확인해 같은 요청의 최초 결과가 있으면 복원한다. 복사본·작은 목표·질문 연결·승인 기록·배정·종료 처리 중 실패하면 전체를 롤백한다.

검증: 검토/생성/승인/수정 통합 검사 74개(이번 추가 13개), 구조 검사 11개가 통과했다. 원본/과거 배정 보존, 새 ID·버전·목표 UUID, 질문별 목표 보존과 실제 역할극 시작, 수정 재전송·순서 정규화·내용 충돌, no-op 재사용, 원본 사용 후 새 버전 배정, 잘못된 목표/근거/금지 표현/길이 거부, 동시 재전송의 단일 사본, 실패 후 롤백·재시도를 확인했다. 검사한 변경 파일 8개의 바이트 일치를 확인했다. 실제 LLM·운영 HTTP/프론트엔드·부하·전체 회귀 검사는 실행하지 않았다. 다음 단위에서 운영 API 연결과 기존 자동 배정 제거가 필요하다.


## 아홉 번째 구현 단위 — 운영 API 연결과 자동 배정 제거

이 절은 앞선 단위의 'API 미연결/자동 배정 제거 필요'라는 진행 상태를 대체한다. 기존 문서 initial-difficulty-scenario-handoff.md의 자동 배정 설명도 아래 명시적 승인 흐름으로 대체한다.

### 공개 계약

담당 강사의 인증과 변경 요청의 CSRF 토큰이 필요하다. 모든 요청은 UUID인 `Idempotency-Key` 헤더를 사용한다. 응답은 기존 `{data, meta}` 형식이며 아래 성공은 모두 HTTP 200이다.

| 동작 | 요청 | 본문 |
| --- | --- | --- |
| 시작·복원 | POST /api/v1/activities/{activityId}/scenario-review | `{"action":"START_OR_RESUME"}` |
| 현재 후보 거절·다음 제공 | 같은 POST | `{"action":"NEXT","reviewId":"UUID","revision":1}` |
| 수정 없이 확정 | PUT /api/v1/activities/{activityId}/scenario | `{"reviewId":"UUID","revision":1,"scenarioId":"UUID","scenarioVersion":1}` |
| 수정하여 확정 | 같은 PUT | 위 본문에 선택적 `edits` 객체 추가 |
| 취소 | DELETE /api/v1/activities/{activityId}/scenario-review | `{"reviewId":"UUID","revision":1}` |

START_OR_RESUME에는 reviewId/revision을 보내지 않는다. NEXT에는 두 필드가 모두 필요하다. 별도 GET 복원·NEXT·초안 저장 API를 추가하지 않았다. DELETE도 위 JSON 본문을 보낸다. 실제 확정과 취소의 반환 data는 `{reviewId, activityId, outcome, closedAt}`다. outcome은 CONFIRMED/CANCELLED다. 수정 후 최종 배정 ID는 기존 GET /api/v1/activities/{activityId}의 data.activity.scenarioId로 확인한다.

POST 응답 data는 다음 필드만 반환한다.

- reviewId, activityId, revision: 현재 검토 식별자와 수정 번호.
- conditions: title, category, situationType, characters, requiredElements, forbiddenExpressions, scenarioLevel. 저장된 현재 학습 목표와 최초 난이도이며 강사가 전체 적합성을 확인한다.
- scenario: scenarioId, scenarioVersion, scenarioLevel, title, summary, characters(id/role), scenarioFacts, microGoals(microGoalId/description/requiredEvidence/achievementExample), startingQuestions, startingQuestionGoalIds.

전체 후보 ID·순서·개수나 생성 제공자·프롬프트는 응답에 포함하지 않는다. microGoalId는 scenario_micro_goal의 실제 UUID다. startingQuestionGoalIds도 S0/S1/S2에 대응하는 실제 목표 UUID를 반환하며 모델 내부 MG-01 키를 응답하지 않는다. 필수 조건에 맞는 재사용 후보가 없거나 고정 목록이 소진되면 같은 POST에서 신규 생성을 호출한 후 콘텐츠를 반환한다. 후보 없음만 뜻하는 정상 200을 반환하지 않는다.

수정 예시:

```json
{
  "reviewId": "검토 UUID",
  "revision": 1,
  "scenarioId": "제시된 시나리오 UUID",
  "scenarioVersion": 1,
  "edits": {
    "title": "수정 제목",
    "microGoals": [
      {"microGoalId": "응답의 목표 UUID", "description": "수정 설명", "requiredEvidence": ["확인할 행동"]}
    ]
  }
}
```

edits의 title/summary, 기존 microGoalId의 description/requiredEvidence만 수정 가능하다. 없는 항목·null은 유지한다. 허용하지 않은 JSON 필드는 조용히 무시하지 않고 400으로 거부한다. 원본 승인 콘텐츠의 불변성, 새 ID·버전·질문별 목표 연결 및 재전송 처리는 앞선 단위를 따른다.

### 호출과 DB 동작

ScenarioReviewController.prepare → ScenarioPreparationService.prepare/next가 기존 검토·동결 목록·생성 흐름을 실행한다. 다음 ScenarioReviewViewService.response가 별도 읽기 전용 REPEATABLE_READ 트랜잭션에서 담당 강사 권한과 현재 입력 지문을 다시 확인한다. ScenarioReviewViewRepository는 activityId/reviewId/instructorId 및 반환할 후보의 ID/버전/위치를 조건으로 scenario_review → scenario_review_candidate → scenario를 JOIN하고 작은 목표·질문 연결을 읽는다. 임의의 미승인 초안 ID로 본문을 조회할 수 없다. 이 응답 조립 단계는 FOR UPDATE나 통계 갱신을 수행하지 않는다.

검토가 종료되거나 입력이 바뀌어 응답할 수 없으면 409를 반환한다. NEXT의 오래된 완료 요청을 재전송한 경우에는 같은 후보·revision의 결과를 복원할 수 있다. 화면은 이미 받은 최신 revision보다 낮은 늦은 응답을 반영하지 않아야 한다. 종료 후에는 과거 준비 요청으로 새 검토를 만들지 않는다.

PUT은 ScenarioConfirmationService.confirm, DELETE는 ScenarioReviewTransactions.cancel로 연결했다. 최종 승인 트랜잭션에서만 activity.scenario_id와 활동별 승인 근거를 저장하고 scenario_review·scenario_review_candidate를 DELETE한다. 취소도 임시 검토·목록과 참조 없는 미승인 생성 초안을 DELETE하며 배정하지 않는다. 재전송 방지용 최소 종료 요청은 활동 삭제까지 유지한다.

ScenarioAttachmentService와 그 서비스만 사용하던 자동 선택/배정 쿼리를 삭제했다. QuizAttemptService.result는 권한 확인 후 저장된 퀴즈 결과만 조회하고 FirstQuizCompleted를 재발행하지 않는다. 실제 최초 퀴즈 완료 이벤트 발행은 유지한다. 퀴즈 완료·결과 조회·새 승인본 추가만으로 activity.scenario_id가 채워지지 않는다. 이미 배정된 과거 활동은 계속 역할극을 시작할 수 있다.

### 오류·프론트엔드 연동

- 인증 누락 401, CSRF 누락 403, 타 강사의 활동 404.
- 필수 헤더/UUID/JSON/알 수 없는 동작·필드 오류 400. 필수값/양수 버전/동작별 필드 조합·유효하지 않은 수정은 422.
- 현재 상태·revision·시나리오 버전·입력 변경, 종료된 준비 요청, 요청 키 재사용 충돌은 기존 서비스의 409 코드로 반환한다.
- 생성 공급자 미설정/실패/시간 초과는 기존 503/502/504이며 서버에서 자동 재생성 루프를 돌리지 않는다. 화면 재시도는 같은 요청 키로 전송한다.
- START_OR_RESUME는 새로고침/재접속 후 복원에도 사용한다. 사용자가 다른 후보를 요구할 때에만 새 키로 NEXT를 보낸다. 응답을 못 받아 같은 논리 동작을 재전송할 때에는 키와 본문을 유지한다.
- 화면에서 제목·요약·목표를 편집해도 별도 저장 요청은 없다. 확정 PUT에 edits를 포함한다. 거절·취소 시 저장하지 않은 편집은 폐기한다.
- 퀴즈 결과 조회만 기다려 역할극을 시작하던 화면은 강사 준비/확정 후 활동의 scenarioId를 재조회하는 흐름으로 바꿔야 한다. 프론트엔드는 수정하지 않았다. 파일별 연동 목록과 브라우저 검증은 4단계 최종 정리에서 다룬다.

### 이번 검증

PostgreSQL Testcontainers·실제 인증 토큰/쿠키 CSRF·MockMvc를 사용하는 새 HTTP 검사 20개, 기존 퀴즈/역할극 회귀 85개, 검토·생성·확정·편집 통합 74개, 구조 검사 11개, 총 190개가 실패·오류·건너뛰기 없이 통과했다. 새 HTTP 검사는 저장된 최초 퀴즈 결과를 DB 픽스처로 준비하며 LlmProvider만 모의 응답으로 대체한다. 실제 퀴즈 완료 회귀는 기존 QuizFlowIntegrationTest에서 검증했다.

첫 실행 116개 중 5개가 실패했다. 결과 GET 이벤트 중복 기대 3개와 읽기 요청의 쓰기 잠금 대기 기대 1개는 바뀐 정책에 맞춰 수정했다. 나머지 1개는 Mockito 기존 응답이 재설정 중 null로 호출되던 테스트 설정 문제로 doAnswer를 사용했다. 수정 후 위 190개를 실행해 통과했다. 이미 배정된 과거 역할극 자료는 명시적으로 배정하는 픽스처로 준비하며, 자동 배정 정책 검사는 계속 미배정임을 확인한다.

이 결과는 배포 서버·실제 LLM·프론트엔드·부하 측정이나 전체 저장소 회귀 완료를 뜻하지 않는다. 다음은 4단계 전체 검증과 측정/연동 한계 정리다. 아직 커밋·push하지 않았다.

## 4단계 — 최종 실행 흐름·회귀 검증·측정·연동 인계 (2026-11-04)

### 최종 실행 흐름과 정책 판정

강사가 저장된 학습 목표와 최초 퀴즈 난이도를 바탕으로 START_OR_RESUME를 요청한다. 본인의 승인 기록에서 조건을 만족하고 학생에게 배정된 적 없는 정확한 시나리오 ID들을 골라 강사별 제시 시각 순으로 고정한다. 현재 한 개를 반환하고 다음 후보를 요구하면 그 후보를 이번 검토에서만 거절한다. 고정 목록에 더 유효한 후보가 없으면 같은 POST에서 동기 생성한다. 강사가 수정 여부를 포함해 PUT으로 확정해야 활동 배정이 완료된다. 검토·후보 임시 행은 삭제하고 승인·배정 근거와 최소 종료 요청 기록은 유지한다. 취소는 배정하지 않고 임시 행을 정리한다. 최초 퀴즈 결과 GET은 저장된 결과만 반환한다.

| 확정 정책 | 반영·검증 |
| --- | --- |
| 강사별 승인 풀·제시 순환 | 다른 강사의 승인본 미사용, 강사별 제시 통계, 미제시/오래된 제시 우선 |
| 조건별 비교·미확인 제외 | 정확한 목표/레벨, 지정 조건, 금지 표현의 필드별 검사와 사유별 집계 |
| 학생의 동일 버전 ID 재배정 방지 | 상태 무관 과거 배정 제외, 최종 학생 잠금 뒤 재검사, 수정 새 UUID는 별도 판정 |
| 검토 목록 고정·복원 | 신규 승인본 중간 편입 없음, DB 위치 복원, 취소·입력 변경·삭제·늦은 생성 차단 |
| 재사용도 강사 확정 필요 | 준비·거절만으로 미배정, 명시적 확정 뒤 활동별 승인 근거 기록 |
| 수정본은 새 콘텐츠 | 원본 불변, 새 scenario/목표 UUID·부모+1 버전, 질문 연결 보존, 과거 배정 불변 |
| 요청 재전송 | 같은 키/본문은 최초 결과, 변경 내용 충돌, NEXT 중복 이동·확정 중복 생성/집계 방지 |
| 후보 소진 시 즉시 생성 연결 | 정상 후보 없음 응답 없음, LLM은 짧은 DB 쓰기 트랜잭션 밖에서 호출 |
| 횟수 제한 없이 순환 | 제시·실제 재사용 횟수 기록, 자동 폐기/은퇴 기준은 아직 적용하지 않음 |
| 큐·전역 실행 제한 | 이번 Task에서 추가하지 않음. 같은 검토/수정 번호의 단일 인스턴스 중복 호출만 공유 |

활동 유형 추가 허용, 다른 Task의 미구현 API나 역할극 전체 프론트 연동까지 이 Task에서 구현했다고 보지 않는다. PR #90은 통합 대상에서 제외한 상태다. #78/#93 전체를 병합하지 않았다.

> 2026-11-06 PR #90 통합: 후속(역할극 단독) 입력 어댑터를 이 경로에 연결했다. 공통 입력은 `ScenarioPreparationInput`(난이도 근거 `ScenarioDifficultyBasis`, 출처 INITIAL_QUIZ·FOLLOW_UP_PINNED)이고, `ScenarioReviewInputService`가 활동 유형으로 최초(`InitialScenarioPreparationService`)·후속(`FollowUpScenarioPreparationService`) 어댑터를 고른다. 후속 입력은 활동에 고정한 `roleplay_activity_difficulty`의 레벨·시작 지원과 `source_decision_id`의 정책 버전을 쓰고, 입력 지문에 결정 ID·시작 지원을 더한다(최초 결합 지문은 그대로). #90의 자체 후보 조회·배정 때 선택(`RoleplayScenarioSelectionService`·`RoleplayScenarioCandidateStore`·V27 `scenario.approved_at`)은 지웠고, #90 마이그레이션은 V41·V42로 옮겼다. 승인 대기함·아동 준비 판정도 역할극 단독을 고정 난이도로 판정한다.

### 검증 결과와 환경

기준은 develop 5d097a9의 작업본이다. 빠른 로컬 검증용 복사본에 동일한 backend 변경을 적용해 CI의 `./gradlew build --no-daemon`을 실행했다. 소유권 순찰 등록 누락 1개, 복사본의 deploy/compose.dev.yml 누락 1개로 전체 1,574개 중 2개가 실패했다. 전자는 세 API를 공통 CHECKED 및 실제 권한 밖/미존재 요청에 추가했다. 후자는 원본 배포 설정을 복사본에 포함해 검증 환경을 보완했다. 제품 코드를 바꾸거나 실패를 제외하지 않았다.

관련 OwnershipPatrolIntegrationTest와 RoleplayShutdownTest를 재실행해 통과했다. 새 순찰 검사 3개를 포함해 서로 다른 검사 총 1,577개, 101개 검사 묶음의 결과가 유효하며 실패·오류·건너뛰기가 없다. 재실행하지 않은 검사의 통과 결과를 재사용했다. 후속 build는 `-x test`로 이미 확인한 테스트를 반복하지 않고 패키징·형식 검사를 확인한다. 커버리지 비율이나 부하 성능 달성의 근거로 쓰지 않는다.

회귀에는 실제 PostgreSQL Flyway 적용, 조건 조회, 입력/콘텐츠 검증, 검토 복원·경쟁·롤백·삭제, 생성 모의 응답, 승인/수정/배정과 실제 역할극 시작 경계, API 인증/CSRF·다른 강사 404와 미존재 404 동일성, 기존 퀴즈·역할극 회귀, 구조 검사 및 공유 계약 검사가 포함된다. 실제 LLM·배포 서버의 cold start·브라우저·프론트엔드 종단·부하 성능은 검증하지 않았다. 실제 공급자 병렬 처리·한도는 이 테스트로 판정하지 않는다.

### 이후 측정 절차와 판단

초기 목표인 재사용 준비 응답 p95 500ms, 후보 조회 p95 100ms, 화면 표시 p95 1초는 **관측 전 목표**다. 실측 달성이나 확정 SLA로 보고하지 않는다.

1. 테스트 전용 강사·학생·승인본 자료를 준비한다. 후보가 없어 의도하지 않은 실제 유료 LLM 호출이 발생하지 않도록 제공자를 통제한다. 운영 사용자 입력을 성능 로그에 복사하지 않는다.
2. 최초 준비(선택·조건 검사·정렬·후보 INSERT 포함), 복원, NEXT, 신규 생성, 확정을 분리해 측정한다. 같은 Idempotency-Key 재전송만 반복한 결과로 최초 준비 성능을 판단하지 않는다. API 전체 시간은 부하 도구/HTTP 계측에서, queryMs는 선택 로그에서 따로 수집한다. 실패/시간 초과 비율도 함께 기록한다.
3. 승인본 수·동시 검토 수에 상한을 가정하지 않는다. 승인본 10/100/1,000개 등 증가하는 데이터 구간과 동시 요청 1/5/10개 등 여러 부하 구간을 테스트하고 실제 사용량에 맞춰 범위를 조정한다. 같은 강사의 많은 승인본·금지 표현 검사·다수의 미완료 검토가 함께 있는 경우를 포함한다. 수치는 부하 실험 구간 예시이며 실제 예상 사용자 수가 아니다.
4. 각 구간의 요청 수와 p50/p95/p99, 처리량, 오류율을 함께 기록한다. 수십 건의 p95만으로 결론내리지 않는다. 수백~수천 건과 반복 측정으로 tail/편차를 확인하되 표본 수가 통계적 보장을 자동으로 만들지는 않는다. 정상 요청만 남겨 시간 초과를 숨기지 않는다.
5. warm 요청과 장시간 미사용 후 서버 기동을 구분한다. 서버가 내려간 동안의 접속·기동 대기는 DB 조회 p95에 섞지 않지만 사용자 클릭 이후 총 대기는 별도 측정한다. 강사 화면의 생성/대기/재시도 표시, cold start 후 같은 검토 복원은 실제 배포 브라우저로 추가 검증해야 한다.
6. 느린 구간이 확인되면 PostgreSQL EXPLAIN (ANALYZE, BUFFERS), 실제 인덱스 사용·읽은 행 수, 잠금 대기, 커넥션 대기, 후보 INSERT/정리량을 테스트 DB에서 확인한다. ANALYZE가 실제 실행한다는 점을 고려해 읽기 쿼리부터 확인한다.

| 강사별 특정 후보 반복 제시/재사용 집중 | 날짜별 제시/재사용·승인 풀 크기로 판단. 일정 횟수 이후 제외는 관측 후 별도 확정하며 현재 자동 제외하지 않음 |

API 계측·운영 수집기를 실제로 연결한 뒤 같은 부하·자료로 전후를 비교한다. 지금은 Redis 없이 PostgreSQL을 기준 저장소로 사용하며, 속도 개선과 서버 재시작 후 복원을 별개로 판단한다.

### API 명세 반영과 다음 단계

별도 `느링고_API_개별_명세`와 저장소 `contracts/api/v1`의 SCN-01/04/06을 현재 세 API로 갱신했다. SCN-03/05/07은 준비 응답·확정으로 통합된 과거 제안, SCN-02 목록은 별도 미구현 설계로 표시했다. 목차·공통 규칙·퀴즈 결과·활동·역할극 시작의 선행 조건도 반영했다. 기존 공유 전송 fixture contracts/api-v1.json과 실제 FE 코드·예제는 수정하지 않았고 새 세 API의 계약은 HTTP 통합 검사에서 확인한다.

기능 회귀 결과, 성능 목표, 실제 배포/브라우저 미검증, 사용자의 이해 확인을 분리한다. 전체 서비스 E2E나 운영 성능 달성으로 보고하지 않는다. 다음 5단계에서 최신 upstream develop·사용자 fork를 확인하고 동기화/브랜치/커밋을 준비한다. 기존 적용 이력과 PR #78/#93의 마이그레이션 충돌은 통합 시 다시 확인한다. 아직 로컬 커밋·push를 수행하지 않았으며 최종 push는 구체적 대상·커밋을 보여주고 사용자 승인 후에만 진행한다.


최종 확인: 패키징·형식 검사 build(-x test)가 통과했다. 마이그레이션 가드는 macOS의 Bash 3 및 클라우드 동기화 경로의 컨테이너 읽기 문제를 피해 Linux Bash의 검증 전용 복사본에서 실행했다. 기준 HEAD의 V1~V24 SQL을 그대로 커밋한 검증 기준과 현재 V1~V30을 비교해 기존 SQL 수정 없음·새 버전 증가·중복 없음이 통과했다. 원본 저장소의 Git 이력/마이그레이션 파일은 이 환경 준비로 변경하지 않았다. ScenarioReviewRepository.firstAvailableFrom도 최초 승인자 일치를 요구하지 않으며, 최종 확정은 ScenarioApprovalRegistry.findApproved로 공통 승인 상태를 확인한다. 최초 승인자 조회용 findOwnedApproved는 내부 이력 검사에만 남아 있고 제공·재검사·확정 권한에 사용하지 않는다. 활동/학생/목표/검토의 담당 강사 권한과 미승인 초안 접근 제한은 유지한다.

공통 승인 근거의 최초 승인자와 확인 조건은 다른 강사의 확정으로 덮어쓰지 않는다. B의 수정 없는 재사용은 B의 활동별 승인 근거와 재사용 횟수만 저장한다. 실제 수정은 B의 새 승인 버전을 만들고 원본도 유지한다. 최초 승인자가 탈퇴해 NULL인 공통 승인 행도 조건에 맞으면 조회·NEXT·확정할 수 있다. 이번 검토 거절과 다른 강사/활동의 후보 자격을 분리하며 공통 제공 중지 API는 추가하지 않는다.

ScenarioCandidateSelection.ownedScenarioCount를 poolScenarioCount로, 구조화 로그 owned를 pool로 변경했다. query ruleVersion=2는 공통 조회 정책 버전이며 DB의 조건 확인 verification_rule_version=1과 구분한다. pool은 등록된 공통 승인 기록 수이고 퇴역/불일치 제외는 별도 집계한다. 개인 승인 풀 부족으로 원인을 설명하던 과거 측정 기록은 공통 풀 부족으로 대체한다. 공통 풀 확대로 첫 조회가 분류하는 행 수와 고정 목록 저장 비용이 커질 수 있으므로 조회/콘텐츠 검사/저장 시간을 분리해 이후 데이터 크기별 측정을 진행해야 한다. 이번 검사 결과를 p95 목표 달성으로 해석하지 않는다.

ScenarioPoolTestIsolation은 순차 실행 테스트에서 검사 시작의 승인 ID 집합을 기록하고, 종료 시 이번 검사가 생성한 활동별 승인 근거·공통 승인 행만 정리한다. 기존 행이나 다른 테스트 데이터 전체를 TRUNCATE하지 않는다. 공통 풀에서는 강사 UUID만 달리해도 테스트 데이터가 격리되지 않으므로 이 픽스처 정리가 필요하다. 운영 코드에는 테스트 격리 조건을 넣지 않았다.

실제 인증·CSRF HTTP 검사로 A 승인본의 B 재사용과 B 담당 승인, A의 B 활동 확정 거부, 최초 승인자 A 탈퇴 전/검토 중/탈퇴 후의 조회·NEXT·확정, B 거절이 C의 검토·제시 순서에 미치는 영향 없음, B 수정본의 C 공통 재사용을 확인했다. LlmProvider는 모의 응답이며 재사용 시 생성 호출이 늘지 않는지도 검사했다. 개인 데이터 없는 과거 승인 상태만으로 승인 조건을 추정해 후보로 편입하지 않는다.

이번 관련 검사 159개 통과(실패·오류·건너뛰기 0). 전체 시나리오 검사와 구조 검사를 실행했다. 이전 삭제·역할극 회귀 결과는 변경 영향에 맞춰 재사용하며 전체 회귀는 변경을 모아 다음 검증 단계에서 수행한다. 공통 후보 API의 기능 연결까지 반영했지만 전체 회귀·실제 LLM·브라우저·부하/운영 지표 수집 검증 완료로 보고하지 않는다. 추가 변경은 아직 커밋/push하지 않았다.


공통 풀 단위 문서 확인: 저장소 SCN-01/04/06·공통 규칙·변경 이력과 별도 API 개별 명세 5개 파일에 공통 풀 정책을 반영했다. JSON 예제 파싱, spotlessCheck 및 공백 검사가 통과했다. 프론트엔드 파일은 변경하지 않았다. 다음은 공통 풀 변경 후 전체 회귀와 정책·문서 최종 대조다.
